# 形式検証の全体地図 (The Formal Verification Landscape)

## 概要 (Overview)

並行アルゴリズムや分散プロトコルには、テストが原理的に届かない領域がある。バグが特定のスレッド交互配置・特定のメッセージ順序・特定の故障タイミングでしか発火しないとき、その組合せ空間は天文学的で、しかも再現不能である。既存文書はこの問題に繰り返し行き当たってきた。lock-free データ構造の線形化可能性、合意プロトコルの安全性、メモリモデルの許容実行、eBPF プログラムのカーネル内安全性がその例である。**形式手法 (formal methods)** は、この「実行して確かめる」の限界に対する「**数学的に言い切る**」側からの応答である: システムと性質を形式的に記述し、性質の成立を全状態の網羅検査（モデル検査）または演繹的証明（定理証明）で確立する。

本ドキュメントは形式手法の主要 3 系統である**モデル検査 (model checking)**、**演繹的検証 (deductive verification)**、**自動推論を核とする解析（SMT・抽象解釈・記号実行）** を、「表現力 vs 自動化」のトレードオフの上の点として Level 3 で整理する。強調点は2つ。第一に、産業で最も費用対効果が高いのは完全な証明ではなく**反例の生成**（TLA+ による設計検査）と**ツールに埋め込まれた軽量形式手法**（eBPF 検証器、Rust の型システム）である。第二に、「検証済み」は常に「**この仕様に対して、この前提の下で**」の主張であり、仕様の誤り・信頼計算基盤 (TCB)・物理側チャネルは証明の外に残る。限界の正確な理解までを含めて形式手法のリテラシーである。

## 方法論 (Methodology)

- 各手法を「**何を記述できるか**（表現力）」「**どこまで機械が自動でやるか**（自動化）」「**何が保証の外に残るか**（TCB・前提）」の3軸で比較し、単一の優劣ではなくトレードオフ面として提示する。
- 一次資料は各系統の原典 (Pnueli, Lamport, Hoare, Cousot) と、産業適用の代表報告 (AWS の TLA+ 実践、seL4、CompCert) に取る。検証コストの数値（人年・行数比）は各報告の自己申告であり、プロジェクト特性に強く依存する**一例**として扱う。
- 既存文書に散在する形式手法への言及（メモリモデルの herd、TLA+、eBPF 検証器、モデル検査）を明示的に回収し、「各文書が暗黙に使っていた道具の一般論」として位置づける。

## 発見事項 (Findings)

1. **3 系統は「表現力 vs 自動化」の交換で並ぶ。** モデル検査は有限状態に落とせる性質を全自動で検査し、反例を機械が吐く。演繹的検証は任意の数学的性質を扱えるが、証明は人間の労働である。SMT・抽象解釈はその中間で、決められた論理断片・抽象領域の範囲なら全自動で走る。「何でも証明できて全自動」の点は存在しない。これは計算可能性の限界（停止性問題）の帰結であり、願望では動かない。

2. **モデル検査の産業的価値は証明ではなく反例である。** AWS は DynamoDB・S3 のレプリケーションプロトコルを TLA+ で検査し、「35 ステップの故障シーケンスでしか発火しない」設計バグを実装前に検出した (Newcombe et al. 2015)。この種のバグはテスト・レビュー・カオス工学のいずれにも実質的に届かない。**設計段階の数日の仕様記述が、出荷後のデータ破損より桁で安い**。これが「証明の道具」を「設計デバッガ」として使う様式である。

3. **状態爆発が中心の敵であり、この分野の歴史は状態爆発との闘いの歴史である。** 状態数は並行度・変数域に対して指数的に増える。記号的モデル検査 (BDD)、有界モデル検査 (SAT)、部分順序簡約、対称性、抽象化といった主要技術はすべて「指数空間をどう踏まずに言い切るか」への応答であり、実務の技能は仕様の抽象度設計（何をモデルから捨てるか）に集約される。

4. **演繹的検証は「実装が仕様を満たす」を機械的証明にまで持ち込めるが、桁で高い。** seL4 は約 1 万行の C カーネルの関数的正しさを約 20 人年で証明し (Klein et al. 2009)、CompCert は C コンパイラの意味保存を証明して「ミドルエンドから miscompile バグが消えた」ことをファジング研究 (Csmith) が独立に裏づけた (Leroy 2009)。適用対象が「小さく・安定で・失敗が高価」な核（カーネル・コンパイラ・暗号実装）に集中しているのは、このコスト構造の合理的帰結である。

5. **SMT ソルバが自動化側の共通エンジンになった。** 充足可能性判定を算術・配列・ビットベクトルの理論と組み合わせる SMT (Z3 など) は、記号実行 (KLEE)、有界モデル検査、Dafny 型の検証言語、リファインメント型の背後で同じ役割を果たす。つまり **「この経路条件・この検証条件は成立しうるか」を訊く神託**である。形式手法の 2000 年代以降の実用化は、かなりの部分がソルバの性能向上そのものである。

6. **最も普及した形式手法は、形式手法と名乗っていない。** eBPF 検証器はロード時にプログラムの全経路を抽象値で検査する抽象解釈器であり、Rust の所有権・借用検査はアフィン型システムによるデータ競合の静的排除であり、メモリモデルのリトマステスト (herd) は公理的意味論のモデル列挙である。**コンパイラ・ローダに埋め込まれ、ユーザが「検証している」と意識しない形**が、採用障壁を消した最大の成功様式である。

7. **「検証済み」の主語と限界を正確に言えることが、形式手法リテラシーの核心である。** seL4 の証明は仕様に対する実装の正しさであり、仕様自体の妥当性・証明ツール・ハードウェアは TCB に残る。そして Spectre 級のマイクロアーキテクチャ側チャネルは、証明が立脚する抽象機械の**外**で起きる。検証済みカーネルもタイミングチャネルまでは塞がない。証明は保証の範囲を明確化する技術であって、安全の同義語ではない。

## アーキテクチャ (Architecture)

### 3 系統の地図 — 表現力 × 自動化

```text
 自動化 高
   ▲
   │  [型システム / eBPF 検証器 / 抽象解釈]      毎コンパイル・毎ロードで全自動。
   │      決められた性質(型安全・停止・資源)専用    健全(誤検出あり)・完全ではない
   │
   │  [モデル検査  TLC / SPIN / SMV]             有限状態モデルに対し全自動。
   │      safety/liveness を網羅検査、反例つき      敵は状態爆発
   │
   │  [SMT / 記号実行  Z3 / KLEE]                論理断片・経路単位なら自動。
   │      検証条件・経路条件の充足性判定             経路爆発・理論の限界
   │
   │  [演繹的検証  Coq / Isabelle / HOL]          任意の性質。証明は人間+補助。
   ▼      seL4, CompCert, 暗号実装                コストは桁で高い
 自動化 低                                → 表現力 高
```

### 検証は層をなす — どの成果物に何を言うか

```text
  設計 (プロトコル・アルゴリズム)   ← TLA+/SPIN: 交互配置・故障順序の網羅検査
        │ refinement (詳細化)
  仕様 (状態機械・事前事後条件)     ← 演繹的検証: 実装が仕様を満たす証明
        │ 実装
  ソースコード                     ← 型システム・抽象解釈・記号実行・(テスト/ファジング)
        │ コンパイル               ← CompCert: 意味保存の証明
  バイナリ / 実行                  ← eBPF 検証器: ロード時検査 / 実行時モニタ
```

層ごとに道具が違い、上の層ほど「安く・早く・設計バグに効く」。TLA+ の**詳細化 (refinement)** は「詳細なモデルが抽象モデルの振る舞いを含む」ことの検査であり、この階段を形式的に繋ぐ概念装置である。

## 技術詳細 (Technical Details)

### 1. 時相論理 — 「いつ」を論理にする

安全性 (safety: 悪いことは起きない) と活性 (liveness: 良いことはいつか起きる) の区別が出発点である（[`../distributed-systems/consensus.md`](../distributed-systems/consensus.md) が合意の性質をこの語彙で述べる）。線形時相論理 (LTL) は、□P (常に P)、◇P (いつか P)、□◇P (無限に何度も P) といった実行列の上の様相で性質を書く (Pnueli 1977)。安全性の反例は有限プレフィクス、活性の反例は**ループする無限実行**であり、モデル検査器が「反例: この 12 ステップの後、この 3 ステップを永遠に繰り返す」と出力できるのはこの構造ゆえである。公平性 (fairness) の仮定（「有効なプロセスは無限に無視されない」）なしに活性は普通成り立たない、という点は分散プロトコルの仕様で常に重要になる。

### 2. TLA+ とモデル検査 — 設計のデバッガ

TLA+ (Lamport 1994) はシステムを「状態と、状態遷移の論理式」として書く。これはプログラムではなく**状態機械の数学的記述**であり、メッセージ喪失・ノード故障・タイマ切れも「起こりうる遷移」として同格に列挙する。検査器 TLC は到達可能状態を幅優先で列挙し、不変式違反なら**最短反例**を返す。実務の型は: (i) 仕様は実装の 1/10 以下の行数の抽象に保つ、(ii) バグの大半は小構成で出る (small scope hypothesis) ので、まず小さな構成 (ノード 3, メッセージ 2) で回す、(iii) 検査済みの不変式は実装側のアサーション・テストオラクルに落とす。**「網羅した」の主語は常にそのモデル・その構成**であり、無限系そのものの証明には TLAPS (証明系) か §4 の演繹的検証が要る。

状態爆発への武器が系譜をなす: BDD による記号的検査 (状態集合を論理関数で持つ)、SAT ベースの有界モデル検査 (深さ k までをソルバに問う)、部分順序簡約 (交互配置の等価類から代表だけ探索; SPIN)、対称性・抽象化。[`../../hardware/cpu/memory-ordering-atomics.md`](../../hardware/cpu/memory-ordering-atomics.md) のリトマステスト検査 (herd) は、公理的メモリモデルの許容実行列挙という同族の技術であり、[`../concurrency/lock-free-data-structures.md`](../concurrency/lock-free-data-structures.md) の線形化可能性検査 (モデル検査による全交互配置探索) も同じ機械の応用である。

### 3. Hoare 論理と演繹的検証 — 証明としてのプログラム

Hoare の三つ組 {P} C {Q}（事前条件 P で C を実行すれば事後条件 Q が成り立つ）が演繹的検証の原子である (Hoare 1969)。ループには**不変式 (invariant)**、再帰には整礎な減少量を与え、プログラム全体の正しさを検証条件 (VC) の束に分解する。VC の払い出し先が SMT (自動) か対話的証明支援系 (Coq/Isabelle) かで、Dafny 型の「自動寄り」と seL4 型の「表現力寄り」に分かれる。ヒープを扱う現代の中核が**分離論理 (separation logic)** である。分離論理は「この述語はメモリのこの部分だけについて語る」を論理に組み込み、エイリアシングの推論を局所化する。Rust の借用検査はこの「所有の局所性」を型システムとして機械化したものと読める。

規模感の代表例: **seL4** は C 実装 (~10 kLoC) の機能的正しさ＋整数オーバーフロー・ポインタ安全の不在を Isabelle/HOL で証明し (~20 人年)、後に整合性 (integrity)・機密性の情報流性質、さらにバイナリレベルへの証明拡張が積まれた (Klein et al. 2009)。**CompCert** は「生成コードはソースの意味を保存する」を Coq で証明した C コンパイラで、Csmith によるファジングが「他のコンパイラでは多数、CompCert の検証済み部分ではゼロ」という独立検証を与えた (Leroy 2009)。**証明とテストが相互検証になった**教科書的事例である。

### 4. SMT・記号実行・抽象解釈 — 自動化の中間地帯

**SMT** は SAT 探索と理論ソルバ (線形算術・ビットベクトル・配列・未解釈関数) の協調 (DPLL(T)) であり、Z3 (de Moura & Bjørner 2008) がデファクトの共通基盤になった。**記号実行**は入力を記号のまま実行して経路条件を蓄積し、SMT に「この経路は到達可能か・ここでオーバーフローしうるか」を問う。網羅は経路爆発で諦め、高カバレッジのテスト生成・バグ発見に徹するのが現代の使い方で、ファジングとの融合 (concolic) は [`../security/fuzzing-program-analysis.md`](../security/fuzzing-program-analysis.md) が扱う。**抽象解釈** (Cousot & Cousot 1977) は具体状態の集合を抽象領域 (区間・多面体・ゼロ性) に写して不動点まで回す。健全 (見逃さない) だが不完全 (誤検出する) という非対称を明示的に選ぶ枠組みで、Astrée が A380 の飛行制御コードの実行時エラー不在を示した産業実績を持つ。

**eBPF 検証器はこの枠組みの大規模実戦配備である**。全経路を抽象値 (レジスタの型・範囲) で追跡し、メモリ安全・終了性をロード時に判定する ([`../operating-systems/ebpf-kernel-programmability.md`](../operating-systems/ebpf-kernel-programmability.md))。「カーネルに任意コードを入れる」が成立するのは検証器の健全性に賭けているからであり、その検証器自体のバグが特権昇格になる、という攻撃面の反転 (§セキュリティ考察) まで含めて象徴的な事例である。

### 5. どこに使うか — 選定の実務

費用対効果の経験則を1つの表に圧縮する。

| 状況 | 道具 |
|---|---|
| 分散プロトコル・並行アルゴリズムの**設計** | TLA+/SPIN で仕様＋モデル検査（数日〜数週間） |
| 「小さく・安定・失敗が高価」な核 (カーネル・コンパイラ・暗号) | 演繹的検証（人年単位の投資判断） |
| 既存 C/C++ の実行時エラー・攻撃面 | 抽象解釈・記号実行＋ファジング（全自動側） |
| 新規コードの並行性・メモリ安全 | 言語に埋める（Rust 型システム）——検証を日常化する |
| 安全規格 (ISO 26262 等) の高 ASIL | 形式手法が推奨手法として明記——規格駆動の採用経路 |

共通の失敗様式は「実装全体を証明しようとして頓挫する」ことであり、成功様式は**最も高価な失敗が起きる最小の核だけを形式化する**ことである。鉄道の連動装置はその早い産業応用例で、パリ地下鉄 14 号線の無人運転システム Météor の安全関連ソフトウェアは B メソッドで開発された ([`../../engineering/railway/railway-signaling-control.md`](../../engineering/railway/railway-signaling-control.md))。

## セキュリティ考察 (Security Considerations)

- **仕様の穴は証明を素通りする**: 検証は仕様に対する正しさしか言わない。「認証をチェックする」ことを証明しても、仕様が「どの経路で」を書き落としていれば脆弱性は残る。仕様レビューは証明後もなお第一級のセキュリティ活動である。
- **TCB は消えず、移動する**: seL4 の保証はハードウェア・証明支援系のカーネル・仕様の妥当性を信頼して成立する。検証は信頼の総量を減らすのではなく、**信頼を小さく明示的な場所へ圧縮する**技術と読むのが正確である。
- **検証器そのものが攻撃面になる**: eBPF 検証器の健全性バグ（範囲追跡の誤り）は、非特権ユーザからのカーネル権限昇格に直結してきた。「安全性を判定するコード」は、その判定の重みのぶんだけ最高価値の標的である。検証器を単純に保つ・非特権 BPF を無効化する運用は、この構造への応答である。
- **抽象機械の外側からの攻撃**: Spectre 系のマイクロアーキテクチャ側チャネルは、証明が立脚する意味論に存在しない状態（投機・キャッシュ）を使う。形式検証済みコンポーネントの隔離保証も、時間・電力のチャネルには別の対策（定数時間実装・パーティショニング）が要る。証明の適用範囲を抽象機械の境界で言い切る習慣が、過信を防ぐ。
- **証明の供給網**: 証明付きソフトウェアの再現ビルド・証明の再検査は、サプライチェーン検証の最も強い形になりうる。「このバイナリはこの証明済みソースから」を機械検査可能にする方向は `../security/software-supply-chain-security.md` の延長線にある。

## 結論 (Conclusions)

形式手法は「テストの限界」への一枚岩の代替ではなく、表現力と自動化を交換する道具の**スペクトラム**である。産業的な重心は完全証明ではなく、(1) 設計段階のモデル検査による**反例の早期入手**、(2) コンパイラ・ローダ・型システムに埋め込まれ意識されない**軽量形式手法**、(3) 「小さく・安定・失敗が高価」な核への**選択的な演繹的検証**、の3点に定まってきた。SMT ソルバの成熟がこの全域を底上げし、Rust と eBPF が「検証の日常化」の到達点を示している。同時に、「検証済み」は常に仕様・前提・抽象機械への相対的主張であり、その境界を正確に言えることが道具の使用資格である。既存文書に散在していたモデル検査・検証器・メモリモデルの語彙は、本地図の上ではすべて同じ数駅圏内にある。分散プロトコルの設計 (`../distributed-systems/`) や並行データ構造 (`../concurrency/`) の次の一本を書くとき、この地図が仕様記述という選択肢を標準装備にする。
