# 仮想化とコンテナ (Virtualization & Containers)

## 概要 (Overview)

1台の物理計算機の上で、**相互に信頼しない複数の OS／ワークロード**を同居させたい——これが仮想化 (virtualization) とコンテナ (container) に共通する出発点である。CPU・メモリ・デバイスはそれぞれ「自分が機械を独占している」前提で設計された特権機構（ring 0、ページテーブル、DMA）を持つため、素朴に同居させれば互いの状態を破壊し合う。この矛盾を吸収するのが**仮想マシンモニタ (Virtual Machine Monitor, VMM)**、別名**ハイパーバイザ (hypervisor)** であり、ゲスト OS よりさらに高い特権を持つ「もう一つの特権層」として、`../../hardware/hw-sw-interface/` が定めた HW/SW 境界と `../operating-systems/` の間に挟まる。

一方コンテナは同じ問題への対照的な解である。カーネルを共有したまま、**名前空間 (namespace)** で見える世界を、**cgroup** で使える資源を分割する。本ドキュメントは、VM 側の三本柱（CPU・メモリ・I/O の仮想化）を機構レベルで追い、コンテナ側の分割機構と対比した上で、両者の中間解 (microVM, gVisor, Kata) を「隔離・密度・互換性」のトレードオフとして位置づける。

## 方法論 (Methodology)

- 仮想化を **CPU（特権命令のトラップ）・メモリ（二段アドレス変換）・I/O（デバイスの多重化）** の3軸に分解し、各軸で「純ソフトウェア → ハードウェア支援 → ハードウェア直結」という同型の進化を追う。
- 判定基準として **Popek-Goldberg の仮想化可能条件**を最初に置き、以降のすべての機構を「この条件をどう満たしたか／回避したか」として説明する。
- VM とコンテナを**隔離境界 (isolation boundary) がどこにあるか**で対比する。境界の位置が、攻撃面・起動時間・密度のすべてを決めるという観点を貫く。
- 数値は桁感 (order of magnitude) であり、CPU 世代・VMM 実装・計測条件で大きく変動する。ベンダー公表値は「ベンダー実証値 (vendor-demonstrated)」と明示し、仕様値・実測値と区別する。
- 評価軸は終始 **VM exit の回数と隔離境界の面積**。性能最適化は前者を減らすこと、セキュリティ強化は後者を狭めることに帰着する。

## 発見事項 (Findings)

1. **仮想化可能性は命令セットの性質で決まる（Popek-Goldberg 基準）。** 「マシン状態を読む／変える**センシティブ命令 (sensitive instructions)** がすべて**特権命令 (privileged instructions)** に含まれる」とき、trap-and-emulate による仮想化が成立する。古典 x86 は `popf` や `sgdt` など「特権レベルで挙動が変わるのにトラップしない」命令を十数個持ち、この条件に**違反**していた。VMware のバイナリ変換 (binary translation) はソフトで、Intel VT-x / AMD-V はハードウェアで、この欠陥を後付け修復したものである。

2. **ハードウェア仮想化の基本単位は VM exit であり、その1回は桁感で数百〜数千サイクルかかる。** ゲスト実行 (VMX non-root) からホスト (VMX root) への遷移は、コンテキストの保存・復元と VMM 側処理を伴い、通常の関数呼び出しの数百倍のコストになる（世代・要因により大きく変動）。仮想化のオーバーヘッドはほぼ「exit 回数 × exit 単価」で決まり、KVM の最適化の歴史は exit を消す歴史である。

3. **メモリ仮想化は「更新コスト」と「参照コスト」のトレードオフを移動させた。** シャドウページテーブル (shadow page table) は参照時こそ一段変換で速いが、ゲストのページテーブル更新のたびに VM exit と同期が要る。EPT/NPT（二次元ページング）は更新を exit なしにした代償として、TLB ミス時の page walk が最悪 **24回のメモリアクセス**（4段×4段）に膨らむ。ヒュージページ (huge page) はこの二次元コストの緩和策として、仮想化環境で単段環境より効きが大きい（`../../hardware/cpu/virtual-memory-mmu.md` 参照）。

4. **I/O 仮想化は「エミュレーション → 準仮想化 (virtio) → ハード直結 (SR-IOV)」で exit を段階的に消してきた。** レジスタ1本ごとに exit する完全エミュレーションから、リング共有で通知を減らす **virtio** へ、さらに IOMMU 保護下でデバイスをゲストに直接見せる**パススルー (passthrough)** / **SR-IOV** へ。性能を上げるほどデバイスがハード実体に縛られ、ライブマイグレーションなどの可搬性を失うという対価がある。

5. **VM とコンテナの本質的な非対称は隔離境界の位置と面積である。** VM の境界は VMCS/EPT というハードウェア機構そのもので、ゲストから見える攻撃面は「VM exit を起こせる操作＋デバイスモデル」に限られる。コンテナの境界は**共有カーネルのシステムコール表面全体**（システムコール約400個＋procfs/sysfs 等）であり、カーネルの1つの権限昇格バグが全コンテナの隔離を破る。パブリッククラウドがコンテナを VM（や microVM）の中に入れて動かすのはこの非対称の直接の帰結である。

6. **中間解 (microVM, gVisor, Kata) は「隔離・密度・互換性」の三角形のどこを取るかの選択である。** Firecracker はデバイスモデルを最小化した VM で密度と起動速度を取り、gVisor はユーザ空間カーネルでカーネル攻撃面を狭める代わりに互換性と性能を削り、Kata はコンテナ体験のまま VM 境界を得る代わりにオーバーヘッドを払う。3頂点を同時に最大化する解は存在しない。

## アーキテクチャ (Architecture)

### VMX root/non-root と KVM/QEMU の分業

Intel VT-x は、既存の ring 0–3 と**直交する**新しい軸として **VMX root モード**（ホスト側）と **VMX non-root モード**（ゲスト側）を導入した。ゲスト OS は non-root の ring 0 で「自分がカーネルのつもり」で走り、センシティブな操作だけがハードウェアにより root へ**トラップ (VM exit)** される。

```
        ┌────────────────────────── ホスト ──────────────────────────┐
        │  VMX root モード                                            │
        │  ┌─────────────────────┐      ┌────────────────────────┐   │
 ring 3 │  │ QEMU (ユーザ空間)     │      │ 他のホストプロセス       │   │
        │  │ ・デバイスモデル       │      └────────────────────────┘   │
        │  │ ・ゲスト RAM 確保     │                                    │
        │  └───────┬─────────────┘                                    │
        │          │ ioctl(KVM_RUN)  ↑ I/O exit だけ折り返す           │
        │  ┌───────▼─────────────────────────────────────────────┐   │
 ring 0 │  │ KVM (カーネルモジュール)                                │   │
        │  │ ・VMCS 管理 ・EPT 構築 ・高頻度 exit をカーネル内で処理    │   │
        │  └───────┬─────────────────────────────────────────────┘   │
        └──────────┼──────────────────────────────────────────────────┘
             VM entry│      ↑ VM exit (exit reason 付き)
        ┌──────────▼──────┴───────────────────────────────────────┐
        │  VMX non-root モード（ゲスト）                               │
 ring 0 │  ┌─ ゲストカーネル（自分を特権と信じて実行）─┐                  │
 ring 3 │  └─ ゲストのユーザプロセス ────────────────┘                  │
        │     状態は VMCS に、変換は EPT に支配される                    │
        └──────────────────────────────────────────────────────────┘
```

KVM/QEMU の分業は「exit の頻度」で切られている。**高頻度・軽量な exit**（CPUID、MSR、多くの EPT violation、割り込み窓）は KVM がカーネル内で完結させ、**低頻度・重量な exit**（エミュレートデバイスへの MMIO/PIO）だけが `KVM_RUN` の ioctl 戻りとして QEMU に折り返される。カーネル内で済む exit と、ユーザ空間まで往復する exit では、コストが桁で違う。

### コンテナ：namespace と cgroup の積層

コンテナに「コンテナ」という単一のカーネルオブジェクトは存在しない。**namespace（見える範囲の分割）** と **cgroup（使える量の制限）**、それに攻撃面削減機構を1プロセス（群）に束ねた**構成物**である。

```
        ┌── コンテナ＝ただのプロセス群（カーネルから見れば） ──┐
        │   アプリのプロセス (pid 1 に見える)                  │
        └──────────────┬───────────────────────────────────┘
     見える世界の分割    │                     使える量の制限
   ┌───────────────────▼───────────┐   ┌─────────────────────────┐
   │ namespaces (8種)               │   │ cgroups v2 (統一階層)     │
   │  pid   : プロセス番号空間        │   │  cpu    : CPU時間の配分    │
   │  mnt   : マウントツリー          │   │  memory : 上限と回収圧     │
   │  net   : NIC/ルーティング表      │   │  io     : 帯域・IOPS       │
   │  uts   : hostname              │   │  pids   : fork 爆弾抑止    │
   │  ipc   : SysV IPC/POSIX MQ     │   └─────────────────────────┘
   │  user  : UID/GID の再マップ      │        攻撃面の削減
   │  cgroup: cgroup ツリーの視界     │   ┌─────────────────────────┐
   │  time  : 単調クロックのオフセット  │   │ seccomp-BPF / capabilities│
   └────────────────────────────────┘   │ / LSM (SELinux, AppArmor) │
                    │                     └─────────────────────────┘
   ═════════════════▼══════════ システムコール境界（唯一の壁）═════════
                共有カーネル（1つ。ここが破られれば全コンテナ陥落）
   ─────────────────────────────────────────────────────────────────
                ハードウェア
```

VM の図と見比べると非対称が際立つ。VM ではゲストとホストの間に**ハードウェアの遷移 (VM entry/exit)** が挟まるのに対し、コンテナではプロセスとカーネルの間に挟まるのは通常のシステムコール境界だけである。

## 技術詳細 (Technical Details)

### 1. Popek-Goldberg 基準と x86 の罪

Popek & Goldberg (1974) は、trap-and-emulate 型 VMM が構成可能な条件を定式化した：**センシティブ命令の集合が特権命令の集合の部分集合であること**。センシティブ命令とは、マシンの構成状態を変える (control-sensitive)、または特権レベルによって挙動・結果が変わる (behavior-sensitive) 命令を指す。この条件下では、ゲストを非特権で走らせるだけで、危険な命令はすべて自動的にトラップし、VMM がエミュレートできる。

古典 x86 (32bit, VT-x 以前) はこれに違反していた。例えば `popf` は非特権で実行すると**割り込みフラグの変更をエラーなしに無視**し（トラップしない）、`sgdt`/`sidt` は非特権のまま特権構造のアドレスを**読めてしまう**。ゲストカーネルを ring 1/3 に落として走らせても、これらの命令は「トラップせず、間違った結果を返す」ため、trap-and-emulate が成立しない。

- **ソフトウェアによる修復（VMware, 1999年頃〜）**: **バイナリ変換 (binary translation)**。ゲストカーネルコードを実行直前に走査し、問題のある命令列を安全な呼び出しに書き換えて実行する。変換済みコードはキャッシュされるため、定常状態のオーバーヘッドは小さいが、実装は極めて複雑。
- **ハードウェアによる修復（Intel VT-x / AMD-V, 2005–2006年〜）**: non-root モードでは、センシティブ命令が**設定に応じて必ず VM exit する**よう半導体レベルで保証。Popek-Goldberg 条件を事後的に成立させた。Adams & Agesen (2006) は初期のハード仮想化がバイナリ変換に必ずしも勝てなかった（exit 単価が高くメモリ仮想化支援も未搭載だった）ことを示しており、「ハード支援＝即高速」ではなく EPT 登場以降に逆転した経緯がある。

### 2. VMCS と VM exit の経済学

VMX の中核データ構造が **VMCS (Virtual Machine Control Structure)** である。vCPU 1個につき1つ置かれ、(a) ゲスト状態（レジスタ、セグメント、CR3 等）、(b) ホスト状態（exit 時に復元する側）、(c) **実行制御**（どの事象で exit するか：例 `HLT` で exit するか、CR アクセスをトラップするか）、(d) exit 情報（**exit reason** と修飾情報）を保持する。

```
// 例示 (illustrative)。KVM の vCPU 実行ループの概念形。実コードではない。
loop {
    vmlaunch/vmresume;              // VM entry: VMCS のゲスト状態をロードし non-root へ
    // ... ゲストが自由に走る（センシティブ操作まで）...
    // VM exit: ハードがゲスト状態を VMCS へ退避し、ホスト状態を復元
    switch (vmcs.exit_reason) {
    case CPUID:          // 仮想 CPU 像を返す（カーネル内で完結・軽い）
    case EPT_VIOLATION:  // ゲスト物理の未マップ → EPT 充填（demand paging 相当）
    case HLT:            // vCPU を眠らせ、他 vCPU/プロセスへ CPU を譲る
    case IO_INSTRUCTION: // エミュレートデバイス → QEMU へ折り返し（重い）
    case EXTERNAL_INT:   // ホスト側割り込みの処理へ
    }
}
```

exit 1回のハードウェア遷移コストは、桁感で**数百〜数千サイクル**（entry/exit 往復。世代で大きく改善してきたが「ただの分岐」には決してならない）、加えて VMM 側ハンドラの実行、TLB/キャッシュの汚染という間接コストが乗る。QEMU までの往復はさらに1桁以上重い。ゆえに KVM の最適化はすべて「exit を減らす・軽くする」に向かう。

- **exit をカーネル内で完結**させる（上記の分業）。割り込みチップ (LAPIC) のカーネル内エミュレーションもこの一種。
- **exit 自体を消す**: EPT によりページテーブル操作の exit を排除、**APICv / AVIC** で割り込みの受理・EOI を exit なしに、**posted interrupt** でデバイス割り込みをゲストへ直接配送。
- **exit の予兆で粘る**: `HLT` exit の直前にホスト側で少し**ポーリング (halt polling)** し、すぐ起きるゲストのスリープ往復を省く。

### 3. メモリ仮想化：シャドウページテーブル vs EPT/NPT

ゲストは「ゲスト仮想 → ゲスト物理」の変換を自分のページテーブルで管理するつもりでいるが、ゲスト物理はホストにとっては単なる論理番号であり、実際には「ゲスト物理 → ホスト物理」のもう一段が要る。二段をどう合成するかで2方式に分かれる。

| | シャドウページテーブル (shadow page table) | EPT / NPT（二次元ページング） |
|---|---|---|
| 仕組み | VMM が「ゲスト仮想→ホスト物理」を直接引ける合成表を裏で維持。MMU にはこれを見せる | MMU 自体が二段変換をサポート。ゲスト表＋EPT の両方をハードが辿る |
| ゲストのPT更新 | 検知のため書込保護 → **更新のたび VM exit** して同期 | exit 不要（ゲストは自分の表を自由に書く） |
| TLBヒット時 | 一段変換ぶんで速い | 同等（ゲスト仮想→ホスト物理が直接キャッシュされる） |
| TLBミス時 | 1回の walk（最大4〜5アクセス） | **二次元 walk**（下記、最悪24アクセス） |
| メモリ消費 | プロセス×VM ぶんのシャドウ表 | EPT は VM につき1組 |
| 現在 | ほぼ役割を終えた（無支援環境の遺産） | 事実上の標準 |

二次元 walk の展開：4段ゲスト × 4段ホストでは、ゲスト側 walk が参照する4つのゲスト物理アドレス＋最終データのゲスト物理アドレスの**計5つそれぞれ**が、EPT の4段 walk を要する。最悪 4×5 + 4 = **24回のメモリアクセス**が1回の TLB ミスの裏に隠れる（`../../hardware/cpu/virtual-memory-mmu.md` の「仮想化での二段変換」参照）。緩和策は同文書と同根で、(a) ゲスト・EPT 双方での**ヒュージページ**（段数自体を減らす）、(b) 結合 TLB とページウォークキャッシュ、(c) TLB ミスを起こさないアクセス局所性、である。仮想化環境で 2MiB ページの効果が素の環境より大きいのは、この掛け算構造ゆえである。

メモリ仮想化にはもう一つの顔——**過剰割当 (memory overcommit)** がある。ホストは VM 群に物理量以上のメモリを約束できる。

- **virtio-balloon**: ゲスト内のバルーンドライバがゲストからページを「膨らませて」確保し、ホストへ返す協調型回収。ゲストの合意が要る分、透過性は低いが安全。
- **KSM (Kernel Samepage Merging)**: ホストが VM 間の同一内容ページを走査し、書込時コピー (CoW) で1枚に統合する。同種ゲストが並ぶ環境で効くが、「共有されたか否か」が書込レイテンシで観測できるため、**VM 間のサイドチャネル**にもなる（セキュリティ考察参照）。多テナント環境では無効化が定石。
- ホスト側 swap・demand paging: ゲストに透過だが、ゲスト OS 自身のページ管理と二重に働くと性能が読めなくなる（二重ページング問題）。

### 4. I/O 仮想化：エミュレーション → virtio → パススルー

I/O は3世代で進化した。各世代は「exit の回数」と「ハード実体への依存」を交換している。

- **完全エミュレーション (full emulation)**: QEMU が実在デバイス（e1000 NIC 等）のレジスタ挙動を再現。ゲストの無改造ドライバがそのまま動くが、**MMIO/PIO アクセス1回ごとに QEMU までの exit 往復**が発生し、高速 I/O では破綻的に遅い。
- **準仮想化 (paravirtualization) — virtio**: 「ゲストが仮想化を自覚し、exit しにくいインタフェースで話す」方式。中核は共有メモリ上のリングバッファ **virtqueue (vring)** で、ディスクリプタ表＋avail リング（ゲスト→ホストの提出）＋used リング（ホスト→ゲストの完了）から成る。要求はメモリ書き込みで積み、**通知 (kick) だけが exit** になる。さらに通知抑制フラグやイベントインデックスで「処理側が起きている間は kick 自体を省く」ため、負荷が高いほど exit/要求 比が下がる。vhost はこの処理をホストカーネル（vhost-net）や別プロセス（vhost-user, DPDK 等）へ移し、QEMU 往復を消す発展形である。

```
// 例示 (illustrative)。virtqueue による要求提出の概念フロー。
//   ゲスト側 (ドライバ)                    ホスト側 (デバイス)
//   1. バッファを desc[] に記載
//   2. avail リングに index を積む          （共有メモリ。exit なし）
//   3. avail.flags を確認:
//        ホストが処理中 → kick 省略 ──────▶ ポーリング継続で拾う
//        ホストが休止中 → kick (MMIO 書込) ─▶ VM exit → 処理再開
//   4. …他の要求を積み続ける               5. 処理完了を used リングへ
//   6. used を見て完了回収                    （割り込み側も同様に抑制可）
// 要求 N 件あたり exit は最良で 0〜1 回。完全エミュレーションの
// 「レジスタ操作数回 × N 件ぶんの exit」と対照的。
```
- **パススルー (passthrough) と SR-IOV**: 物理デバイスの MMIO をゲストに直接マップし、ドライバをゲストに持たせる（VFIO）。DMA はゲスト物理アドレスで発行されるため、**IOMMU (Intel VT-d / AMD-Vi)** が「デバイス版 EPT」としてゲスト物理→ホスト物理を変換し、かつ他 VM のメモリへの DMA を遮断する（DMA と IOMMU の基礎は `../../hardware/hw-sw-interface/mmio-dma-interrupts.md` 参照）。**SR-IOV** は1つの物理デバイス (PF) がハードウェア内で複数の**仮想機能 (Virtual Function, VF)** を生やし、VF 単位で各 VM に配る規格で、データパスから VMM を完全に排除する。代償は、デバイス状態がハードの中にあるため**ライブマイグレーションが困難**になること、および VF 数・構成の柔軟性がハードに縛られることである。

### 5. KVM/QEMU 分業と最小 VMM の潮流：Firecracker

QEMU は数百種のデバイスと全アーキテクチャのエミュレーションを抱える巨大なコードベースであり、機能の豊かさがそのまま**攻撃面**になっている（セキュリティ考察参照）。この反省から「KVM はそのまま使い、ユーザ空間デバイスモデルを最小まで削る」**最小 VMM (minimal VMM)** の潮流が生まれた。

代表が AWS の **Firecracker** である。Rust 製、デバイスは virtio-net / virtio-block / シリアル / 最小キーボード程度に限定し、BIOS もエミュレートせずカーネルを直接ロードする。NSDI'20 論文 (Agache et al., 2020) では、**起動〜125ms 級、microVM あたりメモリオーバーヘッド〜5MiB 級、ホストあたり毎秒150 microVM 級の生成レート**が示されている——いずれも**ベンダー実証値 (vendor-demonstrated)** であり、ゲスト構成・世代で変動する桁感として読むべき数値だが、「VM は重い」という前提を桁で覆し、サーバレス基盤（AWS Lambda / Fargate）で「テナント境界は VM、パッケージングはコンテナ」という構成を実用化した。

### 6. コンテナ：namespace・cgroups v2・攻撃面削減

コンテナの分割は3系統の機構の合成である（アーキテクチャ図参照）。

- **namespaces（見える世界の分割）**: 8種——**pid**（プロセス番号空間。コンテナ内の pid 1）、**mnt**（マウントツリー。pivot_root で別ルート）、**net**（NIC・ルーティング表・ポート空間。veth で接続）、**uts**（hostname）、**ipc**（SysV IPC / POSIX MQ）、**user**（UID/GID の再マップ。コンテナ内 root ≠ ホスト root にできる、rootless コンテナの要）、**cgroup**（cgroup ツリーの視界の限定）、**time**（単調・起動時刻クロックのオフセット）。namespace は**可視性**の機構であり、資源量には何も言わない。
- **cgroups v2（使える量の制限）**: 統一階層 (unified hierarchy) の下で、cpu（重みと帯域上限）、memory（`memory.max` のハード上限と `memory.high` の回収圧、PSI による逼迫の観測）、io（帯域・IOPS）、pids（fork 爆弾抑止）等のコントローラが資源を配分する。v1 のコントローラごとにバラバラだった階層を単一ツリーに統一し、委譲 (delegation) を安全にしたのが v2 の本質的な改善である。
- **攻撃面の削減**: 隔離境界がシステムコール表面である以上、**表面積そのものを削る**しかない。**seccomp-BPF**（システムコールの許可リスト。ランタイム既定で数十個を遮断）、**capabilities**（root 権限を約40個に分割し大半を落とす。`CAP_SYS_ADMIN` はほぼ root 同義なので落とすことが重要）、**LSM (SELinux / AppArmor)**（ラベル・プロファイルによる強制アクセス制御）。これらは境界を「壁」にするのではなく、壁に開いた穴の数を減らす対症療法である点が VM と本質的に異なる。

「コンテナはただの構成物」であることは、生成手順がすべて既存システムコールの合成である点に現れる。

```
// 例示 (illustrative)。コンテナランタイムの生成手順の骨格。実コードではない。
clone(CLONE_NEWPID | CLONE_NEWNS | CLONE_NEWNET | CLONE_NEWUTS
      | CLONE_NEWIPC | CLONE_NEWUSER | CLONE_NEWCGROUP, ...);
                                    // namespace 一式を持つ子を作る
write("/sys/fs/cgroup/.../memory.max", limit);   // cgroup で資源上限
pivot_root(rootfs, old);            // mnt ns 内でルートを差し替え
capset(...);                        // 不要な capability を落とす
seccomp(SECCOMP_SET_MODE_FILTER, ...); // syscall 許可リストを適用
execve(entrypoint, ...);            // 以降は「隔離されたただのプロセス」
// VM と違い、新しい実行モードへの遷移はどこにもない。
```

### 7. 中間解と比較：隔離・密度・互換性のトライアングル

- **gVisor**: ユーザ空間に Go 製の「アプリケーションカーネル」(Sentry) を置き、コンテナのシステムコールを横取りして**自前で実装**する。ホストカーネルへは絞り込まれた少数のシステムコールしか到達しないため、カーネル攻撃面が激減する。代償は、システムコール横取りのオーバーヘッド（特に I/O・システムコール密度の高い負荷）と、Linux ABI の再実装ゆえの互換性の穴。
- **Kata Containers**: コンテナ (OCI) の体験・エコシステムを保ったまま、各ポッドを**軽量 VM の中で**動かす。境界はハードウェア (VMCS/EPT) になるが、VM ぶんのメモリ・起動オーバーヘッドを払う。Firecracker や Cloud Hypervisor を VMM として使う構成もあり、microVM と合流しつつある。

| | 従来型 VM (KVM+QEMU) | コンテナ (runc) | microVM (Firecracker) | gVisor |
|---|---|---|---|---|
| 隔離境界 | HW (VMCS/EPT) ＋ デバイスモデル | 共有カーネルの syscall 表面 | HW (VMCS/EPT) ＋ 極小デバイスモデル | ユーザ空間カーネル＋絞った syscall |
| 攻撃面 | 中（QEMU が大きい） | 大（カーネル全面） | 小 | 小〜中（Sentry 自体は露出） |
| 起動レイテンシ | 秒オーダ | 数十ms オーダ | 100ms 強オーダ（ベンダー実証値） | 100ms 前後オーダ |
| メモリオーバーヘッド | 数百MiB オーダ（ゲストOS込み） | ほぼゼロ（プロセス並み） | 数MiB オーダ＋ゲスト | 数十MiB オーダ |
| 互換性 | 完全（無改造 OS が動く） | 高（同一カーネル ABI） | ゲスト側に virtio 前提等の制約 | Linux ABI の部分実装 |

数値はいずれも桁感であり、ワークロード・構成で容易に1桁動く。読み取るべきは絶対値ではなく「どの頂点を取り、どの頂点を捨てたか」の構造である。

## セキュリティ考察 (Security Considerations)

仮想化の隔離保証は「境界の狭さ」に依存する。歴史的な破られ方は、境界のどこが実際に弱いかを教えてくれる。

- **VM エスケープはデバイスモデルから破られる**: VMX/EPT というハード機構そのものの脆弱性は稀で、実際の VM escape の主戦場は**ソフトで書かれたデバイスモデル**、すなわち QEMU である。象徴が **VENOM (CVE-2015-3456)**——フロッピーコントローラ (FDC) エミュレーションのバッファオーバーフローで、ゲストからホスト QEMU プロセスのコードを実行できた。教訓は二つ：(a) 攻撃面はゲストが**触れるコード全部**であり、使っていないレガシーデバイスのエミュレーションすら含まれる（VENOM はフロッピーを構成していなくても刺さった）、(b) ゆえにデバイスモデルの最小化 (Firecracker) と QEMU 自体のサンドボックス化（seccomp、権限降格）が本質的な緩和である。
- **コンテナエスケープは「カーネルの穴」か「設定の穴」**: 前者はカーネル権限昇格バグの直撃（共有カーネルゆえ1発で全コンテナ陥落。Dirty COW 級のバグが定期的に出続けている事実が前提になる）。後者は `--privileged`、`CAP_SYS_ADMIN` の付与、docker ソケットや procfs/sysfs の不用意なマウント、user namespace 未使用の root 実行など——機構は正しく動いているのに、束ね方の誤りで境界が消える。コンテナの隔離は「単一機構の保証」ではなく「多数の設定の合成」であるため、既定値と検証 (admission control) が安全性を左右する。
- **サイドチャネルは境界を透過する**: Spectre 系の投機実行チャネルや L1TF/MDS 級の CPU 脆弱性は、VMCS/EPT の論理的隔離を**マイクロアーキテクチャ状態経由で**すり抜け、VM 間・ゲスト→ホストの秘密漏洩を許した（機構は `../../hardware/cpu/branch-prediction-speculation.md` 参照）。より古典的には、KSM のページ統合状態（技術詳細3）を書込レイテンシで探る VM 間チャネルもある。緩和は L1D フラッシュ、コアスケジューリング（信頼境界を跨いで SMT 兄弟スレッドを共有しない）、機能側の無効化 (KSM off)、そして究極的には**物理コア・物理マシンの専有**であり、いずれも密度＝経済性と直接衝突する。
- **多テナントの実運用は「コンテナ in VM」に収束した**: 以上を合成すると、パブリッククラウドの設計が導かれる。カーネル共有のコンテナ境界は相互不信のテナント間には薄すぎ、かといってテナントごとの従来型 VM は重い。ゆえに GKE/EKS/Fargate/Lambda 級のマルチテナント基盤は、**テナント境界にはハードウェア仮想化（VM / microVM / Kata）を置き、その内側でコンテナを密度のために使う**二層構成を取る。コンテナは配布・運用の単位であって、敵対的テナント間のセキュリティ境界ではない——これが本ドキュメントの非対称（発見事項5）の実務上の帰結である。

## 結論 (Conclusions)

- 仮想化とは「特権機構をもう一段積む」ことであり、CPU (VMX root/non-root)・メモリ (EPT)・I/O (IOMMU) のすべてで**トラップと変換の間接層を追加する**という同一のパターンが貫かれている。Popek-Goldberg 基準はその成立条件を与え、x86 はソフト（バイナリ変換）とハード（VT-x）の二段階でそれを満たすに至った。
- 性能の会計単位は **VM exit** である。virtio・EPT・APICv・vhost・SR-IOV はすべて「exit を減らす・軽くする・消す」という同じ目的の異なる手段であり、exit をゼロに近づけるほどハード実体への依存（可搬性の喪失）という別の税を払う。
- VM とコンテナの対立軸は性能ではなく**隔離境界の位置**である。ハードウェアが強制する狭い境界 (VMCS/EPT) か、カーネルが提供する広い境界（syscall 表面）か。前者は堅牢で重く、後者は軽くて薄い。microVM・gVisor・Kata はこの間を埋める連続体であり、隔離・密度・互換性の三角形のどこに立つかという設計判断そのものである。
- 実運用の到達点は二層構成——**セキュリティ境界はハードウェア仮想化、パッケージング・密度はコンテナ**——であり、両者は競合技術ではなく役割分担に落ち着いた。この構図を理解することが、次のサンドボックス技術（WASM 等）を評価する際の座標軸になる。
