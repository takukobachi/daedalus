# サービスメッシュ (Service Mesh: Sidecars, mTLS Automation, L7 Policy & eBPF Meshes)

## 概要 (Overview)

モノリスをマイクロサービスに分割した瞬間、それまで関数呼び出しだったものが**ネットワーク RPC** になる——そして各呼び出しは、ネットワークの故障モデル (遅延・喪失・部分故障・「遅い」と「死んだ」の非区別性 [`../distributed-systems/consensus.md`](../distributed-systems/consensus.md)) を丸ごと相続する。リトライ・タイムアウト・TLS・認可・テレメトリという**横断的関心事 (cross-cutting concerns)** はすべてのサービスが必要とするが、言語とフレームワークごとに別々に (そして非一貫に) 再実装される。Hystrix (Java)・Finagle (Scala) に代表される**ライブラリアプローチ**はこれを最初に体系化したが、多言語 (polyglot) 組織では言語の数だけ実装とバージョンと挙動差が生まれる。

**サービスメッシュ (service mesh)** のテーゼは、この横断的関心事を**アプリケーションからインフラへ抽出する**ことである。各ワークロードの隣に**サイドカー (sidecar)** プロキシ (事実上の標準エンジンは **Envoy**) を置き、全通信を透過的に横取りし、**制御平面 (control plane)** が設定と証明書を全プロキシへ配る。アプリは localhost に話すだけで、mTLS・リトライ・カナリア・メトリクスを「無償で」得る——ただしその無償は、ホップ倍増とプロキシ運用という税で支払われている。本書はこの構造を、サイドカーモデル → mTLS 自動化 → L7 制御 → コストと eBPF 系の順に解体する。分析深度は Level 3。

## 方法論 (Methodology)

- メッシュを「機能の束」ではなく、**ライブラリ → サイドカー → ambient/eBPF という施行点 (enforcement point) の移動史**として読む。各世代を「ポリシーはどこに住むか × ホップあたりのコスト × 多言語対応 × 運用複雑性」の軸で比較する。
- データ平面は Envoy の公開アーキテクチャ文書 (listener/cluster/route、xDS) を規範とし、制御平面は Istio の公開アーキテクチャを代表例として扱う。いずれも**ベンダ/プロジェクト自身の文書**であることを明示する。
- ワークロードアイデンティティは SPIFFE 仕様の語彙 (trust domain, SVID) で記述し、特定製品の実装詳細には立ち入らない。
- リトライ・タイムアウト・外れ値排除は [`load-balancing-architecture.md`](load-balancing-architecture.md) が確立した制御工学の読み (正帰還とダンパ) を引き継ぎ、重複記述を避ける。
- 遅延・メモリのコスト数値は構成依存が激しいため桁感 (order of magnitude) に留め、個別ベンチマークの数値は断定しない。

## 発見事項 (Findings)

1. **サービスメッシュはライブラリの多言語問題をプロキシで解いた——機能の発明ではなく、施行点の移動である。** Hystrix/Finagle が実装したサーキットブレーカもリトライ予算も、メッシュは何も新しく発明していない。発明は「それをプロセス外のプロキシに置けば、言語の数 × フレームワークの数だけあった実装が 1 つになる」という配置の転換であり、サイドカーパターン (Burns & Oppenheimer 2016) の適用である。
2. **メッシュの本体はプロキシではなく、設定と証明書を配る制御平面である。** Envoy 単体は「よくできた L7 プロキシ」に過ぎない。数千のプロキシに一貫したルーティング表・ポリシー・証明書を**動的 API (xDS)** で配り続ける制御平面こそがメッシュを成す——これは [`virtual-networks-overlay.md`](virtual-networks-overlay.md) の「オーバーレイの本体はマッピング分配」と同型の結論であり、層が L2/L3 から L7 に上がっただけである。
3. **mTLS 自動化の実体は、ネットワーク位置から暗号学的アイデンティティへの認可の移行である。** 「どの IP/サブネットから来たか」(セキュリティグループの世界) ではなく「どの秘密鍵を持つワークロードか」(SPIFFE ID を担う証明書) で相手を識別する。IP はポッドの再スケジュールで変わるが、アイデンティティは変わらない——ゼロトラスト (zero trust) の実務形であり、境界防御の否定ではなく**境界の単位をネットワークからワークロードへ縮めた**ものである。
4. **リトライは可用性の道具であると同時に障害の増幅器である——予算のないリトライは攻撃と区別がつかない。** N 段のサービス連鎖で各段が 3 回リトライすれば、最下段には 3^N 倍の負荷が届き得る。過負荷で遅くなったサービスへのリトライ集中は、[`load-balancing-architecture.md`](load-balancing-architecture.md) のヘルスチェック正帰還と同じカスケード障害の力学である。メッシュはリトライ予算 (retry budget)・タイムアウトの段階的短縮・外れ値排除をプロキシ層で一律に施行できる——が、既定値のまま全サービスに配れば、増幅器を一律に配ったことにもなる。
5. **サイドカーは透過性を iptables 税とホップ倍増で買っている。** アプリを無改変に保つため、ポッドのネットワーク名前空間 ([`../virtualization/hardware-virtualization-containers.md`](../virtualization/hardware-virtualization-containers.md)) 内で iptables REDIRECT が全トラフィックをプロキシへ曲げる。1 つの RPC は送信側プロキシと受信側プロキシを必ず通り、ホップは 2 倍、各ホップでカーネル/ユーザ空間往復とプロトコル再解釈が走る——遅延はホップあたり ms 未満〜ms 級、メモリはポッドあたり数十〜百 MB 級が相場である。ポッド数 = プロキシ数というスケールで、この税は掛け算で効く。
6. **eBPF メッシュは「全部 L7 プロキシに通す」前提を解体する。** 観測すべき通信の大半は L3/L4 の識別 (誰が誰に接続したか) で足り、L7 解釈 (どの HTTP パスか) を要する通信は一部に過ぎない。Cilium はアイデンティティ付き L3/L4 ポリシーをカーネル内 eBPF ([`../ebpf/ebpf-kernel-programmability.md`](../ebpf/ebpf-kernel-programmability.md)) で施行し、L7 が必要な場合だけノード共有のプロキシへ委譲する——「ポッドごとのフル L7 プロキシ」から「必要な層だけ、必要な場所で」への再配分である。Istio ambient も同じ再配分を L4 ノードプロキシ + オンデマンド L7 で行う。
7. **テレメトリの均一性はメッシュの最も異論の少ない配当である。** 全 RPC が同じプロキシを通るため、リクエスト率・エラー率・遅延分布 (RED メトリクス) と分散トレースのスパンが、アプリのコードを 1 行も変えずに全サービスで同じ意味論で得られる ([`../observability/observability-performance-engineering.md`](../observability/observability-performance-engineering.md))。ただしトレースの文脈伝播 (trace context) だけはアプリがヘッダを引き回す必要があり、「完全に無償」ではない。
8. **「メッシュが要るか」は機能の問いではなく規模と組織の問いである。** サービスが数個・言語が 1 つなら、ライブラリ (あるいはゲートウェイ 1 段) で足りる。メッシュが利くのは、多言語・多チーム・数十以上のサービスで「全員に同じポリシーを配る」コストが「メッシュを運用する」コストを上回る点からである。マネージドメッシュの整理統合 (AWS App Mesh は 2024 年に新規受付終了・2026 年 9 月末サポート終了が告知された——本書執筆 2026-07 時点) は、この損益分岐が当初の期待より高い位置にあったことの傍証と読める。

## アーキテクチャ (Architecture)

### 全体像 — 2 つのポッド、1 つの制御平面

```
            制御平面 (control plane, Istio: istiod)
           ┌────────────────────────────────────┐
           │  サービスディスカバリ / 設定変換      │
           │  メッシュ CA (証明書発行・ローテーション)│
           └───────┬────────────────┬───────────┘
        xDS (設定) │ + SVID (証明書) │
     ┌─────────────▼──┐          ┌──▼─────────────┐
     │ Pod A          │          │ Pod B          │
     │ ┌────────┐     │          │     ┌────────┐ │
     │ │ アプリ  │     │          │     │ アプリ  │ │
     │ └───┬────┘     │          │     └───▲────┘ │
     │     │ localhost (平文)     │         │ localhost (平文)
     │ iptables REDIRECT         │     iptables REDIRECT
     │     ▼          │          │         │      │
     │ ┌────────┐     │  mTLS    │     ┌───┴────┐ │
     │ │sidecar │═════╪══════════╪════▶│sidecar │ │
     │ │(Envoy) │     │ (SVID 相互検証) │(Envoy) │ │
     │ └────────┘     │          │     └────────┘ │
     └────────────────┘          └────────────────┘
       データ平面 (data plane): 転送・リトライ・メトリクス採取
```

- 分業は明確である: **制御平面は配るだけ、データ平面は転送するだけ**。制御平面が落ちてもデータ平面は最後に受け取った設定で転送を続ける (静的安定性)——ただし新しいエンドポイントも新しい証明書も届かなくなるため、猶予は証明書の残存期間で上限される。
- アプリ↔サイドカー間は同一ネットワーク名前空間内の localhost 通信であり、暗号化はポッド境界 (サイドカー間) から始まる。つまり**ポッドが信頼の最小単位**である。

### 施行点の比較 — ライブラリからeBPF まで

| 軸 | ライブラリ (Hystrix/Finagle 型) | サイドカーメッシュ (Istio 型) | ambient (L4 ノード + L7 オンデマンド) | eBPF (Cilium 型) |
|---|---|---|---|---|
| ポリシーの居場所 | 各アプリのプロセス内 | ポッドごとのプロキシ | ノード L4 プロキシ + 名前空間単位 L7 | カーネル内 (L3/L4) + 共有プロキシ (L7) |
| ホップあたりコスト | ほぼゼロ (関数呼び出し) | プロキシ 2 段 + iptables | L4 のみ 1〜2 段、L7 は必要時のみ | カーネル内はコピーなし、L7 委譲時のみプロキシ |
| 多言語対応 | 言語ごとに再実装 | 完全 (プロセス外) | 完全 | 完全 |
| L7 機能の粒度 | 最も細かい (アプリ文脈を知る) | 全ホップでフル L7 | 選択的 | 選択的 |
| 運用複雑性 | ライブラリ更新 = 全サービス再デプロイ | プロキシ艦隊 + 制御平面の運用 | 中間 (プロキシ数はノード/NS 単位) | CNI と一体化、カーネル依存を持ち込む |

- 表の横読みが本書の主線である: 左から右へ、**ポリシーはアプリ→ポッド→ノード→カーネルへ降りていき**、その都度「アプリの文脈への近さ」を手放して「一律性と効率」を得る。

## 技術詳細 (Technical Details)

### 1. 前史 — ライブラリアプローチとその限界

- **Finagle** (Twitter) は RPC を「Future を返す関数」として抽象化し、リトライ・タイムアウト・負荷分散・回路遮断をその関数の合成として実装した。**Hystrix** (Netflix) は依存呼び出しをコマンドで包み、スレッドプール隔離とサーキットブレーカで「1 つの遅い依存が全スレッドを食い潰す」障害様式を遮った。横断的関心事の語彙——予算付きリトライ、隔壁 (bulkhead)、遮断器——は、この世代でほぼ出揃っている。
- 限界は 2 つ。第一に**多言語問題**: JVM 用に磨かれたライブラリは Go/Python/Node には存在しないか別物であり、ポリシーの一貫性は言語の数に反比例する。第二に**配布問題**: ライブラリの修正は全サービスの再ビルド・再デプロイを要し、「全社のタイムアウト既定値を直す」が数ヶ月仕事になる。クライアントサイド LB ([`load-balancing-architecture.md`](load-balancing-architecture.md) のルックアサイド構成) と同じ強み (アプリ文脈に最も近い) と同じ弱み (実装がアプリに癒着する) を持つ。
- メッシュはこの 2 つを「プロセス外に出す」の一手で同時に解いた——ただしアプリ文脈への近さ (どの呼び出しが冪等か、どの失敗が再試行可能か) は手放しており、プロキシは HTTP メソッドや設定からそれを**推測**するしかない。ライブラリの知識がタダで移植されたわけではない。

### 2. Envoy とxDS — データ平面の語彙

- Envoy の設定モデルは **listener** (どこで受けるか) → **filter chain** (どう解釈するか: TLS 終端、HTTP 接続管理) → **route** (どこへ振り分けるか) → **cluster** (バックエンド集合と負荷分散・ヘルスチェック方針) → **endpoint** (実アドレス) の連鎖である。この分解が重要なのは、各段が **xDS (\*-Discovery Service)** という gRPC ストリーミング API (LDS/RDS/CDS/EDS) で**動的に差し替え可能**だからである——再起動もリロードもなく、制御平面が push する設定で数千のプロキシが同時に挙動を変える。
- つまり Envoy は「設定ファイルを読むプロキシ」ではなく「**外部の制御平面に運転される汎用データ平面**」として設計されている。メッシュ制御平面 (istiod 等) の仕事は、人間が書く高水準の意図 (「v2 に 10% 流す」) を xDS の語彙へコンパイルし、該当する全プロキシへ配ることである。
- サイドカー間の輸送には HTTP/2 が使われることが多い ([`http-quic-evolution.md`](http-quic-evolution.md))——多重化により、ポッド間は少数の暖まった mTLS 接続に集約される。gRPC がメッシュと相性が良いのは、両者が同じ HTTP/2 の語彙で話すからである。

### 3. 透過的横取り — iptables という接着剤

- サイドカーの「アプリ無改変」は、ポッドのネットワーク名前空間内の **iptables REDIRECT** (または TPROXY) で実現される: 出ていく TCP を全部プロキシの inbound ポートへ、入ってくる TCP を全部プロキシへ曲げる。名前空間ごとに規則が閉じるため、ホストや他ポッドへ影響しない ([`../virtualization/hardware-virtualization-containers.md`](../virtualization/hardware-virtualization-containers.md) の net namespace / veth)。
- 対価は 3 つ。(1) パケットはカーネルのネットフィルタと**ユーザ空間プロキシを 1 RPC につき送受で 2 回**通る——カーネル/ユーザ境界のコピーとコンテキストスイッチが往復ごとに乗る ([`kernel-network-stack.md`](kernel-network-stack.md))。(2) iptables 規則とプロキシの起動順序・UID 除外 (プロキシ自身の通信を曲げない) といった**壊れやすい配管**が全ポッドに複製される。(3) プロキシが解釈できないプロトコルは素通しか遮断かの二択になる。eBPF 系がまず攻めたのはこの配管である——ソケット層フックで同一ノード内の横取りを短絡できる。

### 4. mTLS 自動化 — SPIFFE/SVID とゼロトラスト

- **ワークロードアイデンティティ**: SPIFFE は `spiffe://trust-domain/ns/foo/sa/bar` 形式の ID を定義し、それを X.509 証明書 (**X509-SVID**) の SAN に埋め込む。ワークロードは起動時にプラットフォームの証明 (Kubernetes の ServiceAccount 等) を提示し、メッシュの CA が短命 (時間単位) の SVID を発行、**ローテーションは全自動**である。人間が証明書を配らない・更新しないことが、mTLS を「理論上可能」から「既定で有効」に変えた——TLS ハンドシェイクと証明書検証の機構そのものは [`tls-internals.md`](tls-internals.md) の通りで、メッシュが足したのは**発行と配布の自動化**である。
- **認可の単位の移行**: セキュリティグループは「この IP 集合はこのポートに届く」という L3/L4 の位置ベース施行だった ([`virtual-networks-overlay.md`](virtual-networks-overlay.md) §4)。メッシュのポリシーは「サービス A の ID を持つ者だけがサービス B の `POST /orders` を呼べる」という L7 のアイデンティティベース施行である。ポリシーはネットワークファブリックからワークロードの隣へ移り、粒度はポートからメソッド/パスへ細かくなった。
- ただし後述 (セキュリティ考察) の通り、これは SG の置き換えではなく**上に積む層**である。

### 5. L7 制御 — トラフィック管理と故障の増幅

- **重み付きルーティング/カナリア**: route 段で「v1 に 90%、v2 に 10%」を宣言でき、デプロイ (バイナリの配置) とリリース (トラフィックの切替) が分離される。ヘッダベースの振り分けを重ねれば、社員だけ v2・特定テナントだけ旧版といった制御がアプリ改変なしで書ける。
- **タイムアウトとリトライ予算**: プロキシはリクエスト単位でタイムアウトを施行し、失敗を別エンドポイントへリトライできる——[`load-balancing-architecture.md`](load-balancing-architecture.md) の L7 リトライと同じ機構だが、メッシュではそれが**全ホップに**入る。ゆえに増幅も全ホップで起きる (発見事項 4)。定石は Google SRE 本の**リトライ予算** (リトライを全リクエストの数 % に制限) と、上流ほど長いタイムアウトの階段 (deadline propagation) であり、メッシュの価値は「これを全サービスに一律に施行できる」ことにある。
- **外れ値排除とサーキットブレーカ**: cluster 段は受動観測 (連続 5xx、遅延逸脱) でエンドポイントを一時除外し (outlier ejection)、接続数・保留リクエスト数の上限で過負荷の伝播を遮る (circuit breaking)。ここでも「一定割合以上を同時に外さない」下限が全滅への正帰還に対するダンパになる。
- **テレメトリ**: 全プロキシが同じ名前・同じ意味のメトリクス (リクエスト率・エラー率・遅延ヒストグラム) を吐き、トレースのスパンを自動生成する。サービス依存グラフが観測から自動的に描ける——多言語組織で計装の一貫性を人力で保つコストと比べると、これが実務上メッシュ導入の第一動機になることも多い ([`../observability/observability-performance-engineering.md`](../observability/observability-performance-engineering.md))。

### 6. コストの精算と eBPF 系 — サイドカーの後

- **サイドカー税の内訳**: (a) 遅延——ホップ 2 倍とプロキシ処理。p50 では ms 未満でも、テールでは GC・コンテキストスイッチと合成して効く。(b) メモリ/CPU——ポッドごとにプロキシ 1 つ。1000 ポッドなら 1000 個の Envoy が xDS 設定の複製を持つ。(c) 運用——プロキシのバージョン更新がアプリと独立に全ポッドの再起動を要る、起動順序の競合、非 HTTP プロトコルの例外処理。
- **ambient 型 (Istio ambient)**: サイドカーを捨て、L4 (mTLS とアイデンティティ) をノード単位の軽量プロキシ (ztunnel) で、L7 ポリシーが要るサービスだけ名前空間単位のプロキシ (waypoint) で処理する。「全ポッドにフル L7」から「L4 は薄く常時、L7 は選択的に」への再配分であり、プロキシ数はポッド数からノード数 + 選択的な数へ落ちる。
- **eBPF 型 (Cilium)**: CNI として各ノードのカーネルに eBPF プログラムを置き、ポッド間通信を**アイデンティティ番号付きで** L3/L4 施行する——SG と同じ層だが、単位が IP ではなくワークロードアイデンティティである点がメッシュ的である。同一ノード内はソケット層で短絡し、iptables の線形規則評価を回避する。L7 ポリシー (HTTP パス、Kafka トピック) が要るフローだけ、ノード共有の Envoy へ渡す。検証器・フック・マップという基盤機構は [`../ebpf/ebpf-kernel-programmability.md`](../ebpf/ebpf-kernel-programmability.md) の通りであり、本書の観点で重要なのは「**カーネルがアイデンティティを知っている**なら、ユーザ空間プロキシは L7 解釈が本当に要る時だけでよい」という前提の転換である。
- **「メッシュは要るか」**: 発見事項 8 の通り、答えは規模依存である。必要なのが mTLS だけなら CNI レベルの暗号化や SPIRE 単体で足りることがあり、必要なのがカナリアだけならゲートウェイ 1 段で足りる。メッシュは「その全部を、多言語で、一律に」が要件になった時の道具であり、複雑性の前払いである。

## セキュリティ考察 (Security Considerations)

- **メッシュ CA は王冠の宝石 (crown jewel) である。** CA 鍵の侵害は全ワークロードへの**普遍的ななりすまし**を意味する——任意の SPIFFE ID の SVID を発行できる者は、メッシュ内のあらゆる認可を通過する。短命証明書はローテーションを自動化する一方で、CA が常時オンラインで署名し続けることを要求し、オフライン保管という古典的防御を使えなくする。CA 鍵の HSM 格納・trust domain の分割・発行監査が対応する統制である。
- **mTLS ≠ 認可。** 相互 TLS が証明するのは「相手が主張する ID の秘密鍵を持つ」ことだけであり (認証)、「その ID がこの操作をしてよい」(認可) は別のポリシー層である。「mTLS を有効にしたから安全」は、全員に社員証を配って全ドアを開けたままにするのと同じである——既定拒否の認可ポリシーが伴って初めてゼロトラストになる。
- **横取り層は攻撃面である。** iptables 規則を書ける者 (ポッド内の root、特権コンテナ) は横取りを解除してメッシュを迂回できる——サイドカーの施行は**ポッド内の協力**に依存した施行であり、強制ではない。ノード/カーネルに施行点を持つ ambient/eBPF 型は、ポッド内から解除できない分だけ施行保証が強い。逆に言えば、サイドカーメッシュの「全トラフィックは mTLS」という主張は「ポッドが改竄されていない限り」という条件付きで読む必要がある。
- **プロキシのサプライチェーン。** 全ポッドに注入されるプロキシイメージは、組織で最も広く配布されるバイナリになる——その取得元・署名検証・CVE 追従は基盤の信頼性そのものである。Envoy の HTTP 解釈の脆弱性は全ホップに同時に存在するモノカルチャーでもあり、迅速な艦隊更新機構 (それ自体はメッシュが得意とする) が前提になる。
- **多層防御は残る。** L7 アイデンティティ施行は SG/NACL ([`virtual-networks-overlay.md`](virtual-networks-overlay.md)) を置き換えない。メッシュの誤設定・迂回・プロキシ脆弱性に対し、L3/L4 の位置ベース制限は独立した第二の網である——「ポリシーの単位」が違う 2 層は、同じ誤りで同時に破れにくい。
- **制御平面自体の認可。** xDS を注入できる者は全プロキシのルーティングを書き換えられる (トラフィックの複製・迂回・遮断)。制御平面 API への RBAC と設定変更の監査ログは、データ平面の mTLS と同等以上に重要である。
- **観測の集中は集積のリスクでもある。** 全 RPC のメタデータ (パス・ヘッダ・呼び出し元 ID) がプロキシとテレメトリ基盤に集まる構造は、[`load-balancing-architecture.md`](load-balancing-architecture.md) の L7 LB と同じく個人情報・機密パスの集積点を作る——アクセスログのマスキング方針はメッシュ導入時の決定事項に含まれる。
- **メッシュ外との境界。** メッシュに入っていないレガシーワークロードや外部サービスとの通信は mTLS もポリシーも受けない。「メッシュ内は全て mTLS」という不変条件は、非メッシュ通信を既定拒否にする (permissive モードを卒業する) まで成立しない——移行期間の permissive mTLS は、平文とmTLS の両受けという意図的な穴である。

## 結論 (Conclusions)

- サービスメッシュは機能の発明ではなく**施行点の移動**である。ライブラリが確立した横断的関心事の語彙 (リトライ予算・サーキットブレーカ・タイムアウト) を、多言語問題を解くためにプロセス外へ出し、その配布と一貫性を制御平面が引き受けた。本体はプロキシではなく、**設定と証明書を配り続ける制御平面**である。
- mTLS 自動化の意味は暗号ではなく認可の再定義にある——ネットワーク位置 (IP/サブネット) からワークロードアイデンティティ (SVID) へ。ポリシーはファブリックからワークロードの隣へ移り、[`virtual-networks-overlay.md`](virtual-networks-overlay.md) で始まった「ポリシーが箱からファブリックへ」の物語は、ここで「ファブリックからアイデンティティへ」と続く。
- サイドカーはこの全部を「アプリ無改変」で実現した第一世代の形であり、その税 (ホップ倍増・ポッドあたりプロキシ・iptables 配管) が第二世代を駆動した。ambient と eBPF は「全部 L7 プロキシに通す」前提を解体し、**L4 は薄く常時・L7 は必要な所だけ**へ再配分する——施行点はさらにカーネルへ降りた。メッシュを導入するかの判断は機能表ではなく、「一律性の価値が運用複雑性を上回る規模か」という損益計算である。
