# CDN とエッジ配信 (CDN & Edge Delivery: Cache Hierarchies, Anycast & Origin Shield)

## 概要 (Overview)

光は 1 ミリ秒に約 300 km しか進まず、ファイバ中ではその 2/3 に落ちる。太平洋横断の RTT が実測でおよそ 150 ms 前後になるのは経路や機器の不出来ではなく物理であり、プロトコルをどれだけ磨いてもこの床は下がらない。しかも TCP と TLS のハンドシェイクは初回リクエストの前に複数往復を要求するため ([`tcp-transport-congestion.md`](tcp-transport-congestion.md), [`tls-internals.md`](tls-internals.md))、体感遅延は RTT の**数倍**として現れる。**CDN (Content Delivery Network)** はこの物理への唯一の実務的回答である。データを速く動かせないなら、あらかじめ近くに置いておけばよい。

中心テーゼは二つ。第一に、CDN が売っている商品は**近さ (proximity)** と**オフロード (offload)** の二つであり、両者は別の機構である。前者はエッジの地理的配置と接続終端が、後者はキャッシュ階層と接続集約がもたらす。静的配信では両方が役立ち、キャッシュ不能な動的コンテンツでも前者だけは役立つ。この分離を理解しないと「キャッシュできないから CDN は無意味」という定番の誤解に落ちる。第二に、CDN の内部は本質的に**キャッシュの階層** (エッジ PoP → 中間層 → **オリジンシールド (origin shield)** → オリジン) であり、その設計を駆動しているのはコンテンツ人気の **Zipf 的な裾の重さ**である。単一 PoP のヒット率には収穫逓減の壁があり、階層はその壁への構造的応答である。

本書はリクエストルーティング (どうやって「最寄り」に着くか)、キャッシュ階層の意味論、接続最適化、エッジ計算までを解体し、AWS CloudFront を通奏低音の事例として参照する。分析深度は Level 3。

## 方法論 (Methodology)

- CDN の機能を「近さ」と「オフロード」のどちらの商品に属するかで一貫して分類し、機能の羅列ではなく二軸の構造として記述する。
- キャッシュの意味論は標準 (RFC 9110/9111) を規範とし、ヒット率の議論はキャッシュ研究の原典 (Breslau et al. の Zipf 分析、Akamai の設計論文) に接地する。
- 特定ベンダの内部構成 (CloudFront の PoP 構成、Cloudflare Workers の isolate 実行系など) は一次公開資料が自社ドキュメント・技術ブログに限られるため、**ベンダ自身の説明**であることを明示して扱い、検証不能な数値は桁感に留める。
- 隣接文書との重複を避ける: DNS の TTL/ECS の機構は [`dns-resolution.md`](dns-resolution.md)、BGP/anycast の経路側は [`ip-routing-bgp.md`](ip-routing-bgp.md)、PoP 内部の LB 積層は [`load-balancing-architecture.md`](load-balancing-architecture.md) に委ね、本書は CDN 固有の層に集中する。

## 発見事項 (Findings)

1. **CDN は光速に対する唯一の対抗手段である。データを動かせないなら置いておく。** RTT の床は物理定数で決まり、太平洋横断ならざっと 150 ms、そこに TCP 3 ウェイ + TLS ハンドシェイクが乗ると初回バイトまで数往復が必要になり、300〜600 ms 級が「何もしなくても」かかる。エッジが RTT を 150 ms から 10 ms に縮めると、**ハンドシェイクの往復数がそのまま乗算されるため利得は往復数倍**になる。近さは帯域ではなく往復を買う投資である。
2. **CDN の商品は近さとオフロードの 2 つであり、両者は別の機構である。** 近さはエッジの配置と接続終端 (ハンドシェイクを近距離で済ませる) が与え、キャッシュヒットを要求しない。オフロードはキャッシュと接続集約が与え、オリジンの帯域・計算・接続数を削る。動的 API には前者だけが、人気静的アセットには両方が役立つ。「ヒット率」だけを CDN の成績表にするのは、商品を一つ見落としている。
3. **「最寄りのエッジ」を見つけるのは配信ではなくルーティングの問題であり、DNS 方式と anycast 方式は正確さと単純さを交換する。** DNS 方式はリゾルバの位置からクライアント位置を推定するため粒度が粗く (パブリック DNS 利用時のずれを ECS が補うが、キャッシュ効率と引き換えになる。[`dns-resolution.md`](dns-resolution.md) を参照)、anycast は BGP に選択を委ねるため機構は単純だが、経路変動が TCP 接続の当たり先を変えて接続を壊し得る ([`ip-routing-bgp.md`](ip-routing-bgp.md))。実システムはほぼ例外なく両者を併用する。
4. **キャッシュ無効化は分散システムの難問なので、実務はバージョン付き URL で問題ごと消す。** 世界中の PoP に散った複製を「即時に」消すのは本質的に高価で非同期な操作である。対して `app.a3f9.js` のような**コンテンツハッシュ入り URL** は不変 (immutable) と宣言でき、無効化そのものを不要にする。これは「更新」を「別名での新規作成」に変換する、キャッシュ一貫性問題からの構造的な逃げ道である。無効化 API は緊急用の消火器であって日常の道具ではない。
5. **ヒット率の敵は Zipf の裾であり、階層はその裾への応答である。** アクセス頻度は Zipf 的に偏る。少数の人気コンテンツが大半のリクエストを占め、膨大な**ロングテール (long tail)** が残りを薄く分け合う (Breslau et al. 1999)。単一 PoP のキャッシュを拡大してもヒット率は対数的にしか伸びず、テールの初回アクセスは必ずミスする。中間層 (regional cache) は**複数 PoP のテールを合流させて再び「人気」を作る**ことでこの収穫逓減を救う。裾の重い分布が平均や単純な容量計画を裏切る構図は [`../../foundations/mathematics/probability-statistics/probability-random-variables.md`](../../foundations/mathematics/probability-statistics/probability-random-variables.md) の heavy-tail 論そのものである。
6. **オリジンシールドは thundering herd への防波堤である。** 人気コンテンツの TTL が切れるとすぐに、世界中の PoP が同時にオリジンへ殺到し得る。キャッシュがあるせいで平時のオリジンは小さく見積もられているから、この殺到は自傷的な DDoS になる。オリジン直前に単一のシールド層を置き、そこで**リクエスト合流 (request coalescing / collapsed forwarding)** (同一オブジェクトへの同時ミスを 1 本のオリジン取得に束ねる) を行うと、オリジンが見る同時リクエスト数は「PoP 数 × 同時ミス」から**高々 1** に減る。
7. **動的コンテンツでも CDN は有効である。終端と持ち回り接続で RTT を買い戻す。** キャッシュ不能なリクエストでも、(a) TCP/TLS ハンドシェイクを近距離エッジで終端し、(b) エッジ→オリジンは暖まった持続接続 (輻輳ウィンドウが開き、TLS が確立済み) を再利用し、(c) 経路を測定済みバックボーンに載せる、という三段でエンドツーエンド遅延は素の直行より確実に縮む。これが**動的アクセラレーション (dynamic acceleration)** の実体であり、商品としては純粋な「近さ」である。
8. **エッジ計算の実体は「どこまで状態なしで済むか」の切り分けである。** V8 isolate 型のエッジ関数はコンテナ/VM よりプロセスを立てない分だけコールドスタートが桁違いに軽く、数百 PoP への配置を経済的に成立させた。しかし置けるのは認可判定・リダイレクト・ヘッダ操作・A/B 振り分けなど**状態を持たない決定**までであり、一貫した状態が要る処理はデータの重力 (state gravity) に引かれて中央に残る。エッジ計算の設計とは計算の配置ではなく**状態の配置**の設計である。

## アーキテクチャ (Architecture)

### キャッシュ階層の全体像 — ミスの吸収と合流

```
 クライアント群 (世界各地)
   │  DNS 地理応答 + anycast で「最寄り PoP」へ (§1)
   ▼
 ┌─────────┐ ┌─────────┐ ┌─────────┐
 │エッジ PoP│ │エッジ PoP│ │エッジ PoP│ … ×数百   TLS 終端・HTTP/3 受け口
 │ hit≈人気 │ │         │ │         │           人気コンテンツはここで完結
 └────┬────┘ └────┬────┘ └────┬────┘
      │ miss      │ miss      │ miss   ← Zipf の裾: 単一 PoP では薄すぎる
      ▼           ▼           ▼
 ┌──────────────┐      ┌──────────────┐
 │ 地域中間キャッシュ │      │ 地域中間キャッシュ │  ×十数   複数 PoP のテールを合流させ
 │ (regional/mid-tier)│      │              │        「人気」を再生成する
 └──────┬───────┘      └──────┬───────┘
        │ miss                │ miss
        └──────────┬──────────┘
                   ▼
        ┌────────────────────┐   同一オブジェクトへの同時ミスを
        │ オリジンシールド      │   1 本に束ねる (request coalescing):
        │ (origin shield) ×1  │     req A ──┐
        └─────────┬──────────┘     req A ──┼──▶ オリジンへは 1 リクエスト
                  │ 持続接続プール    req A ──┘   残りは結果を待って共有
                  ▼
             ┌─────────┐
             │ オリジン  │  S3 型オブジェクトストア or アプリサーバ
             └─────────┘  平時の容量はキャッシュ前提で小さい → 防波堤が必須
```

### リクエストルーティングの二方式 — DNS 対 anycast

| 軸 | DNS ベース誘導 | anycast 誘導 |
|---|---|---|
| 決定の主体 | CDN のマッピングシステム (測定に基づく応答) | BGP (各 AS の経路選択の総和) |
| クライアント位置の解像度 | リゾルバ単位 (ECS で補正可、ただしキャッシュ効率低下) | パケット送信元そのもの (推定不要) |
| 制御の細かさ | 高い。PoP 単位・重み付き・負荷連動で応答を変えられる | 低い。経路広告の増減という粗い手段のみ |
| 切替の速さ | TTL 拘束 (勧告に過ぎない点も含め [`dns-resolution.md`](dns-resolution.md)) | 経路収束次第で数秒級、ただし制御外 |
| 長寿命接続との相性 | 良い (接続中は宛先固定) | **経路変動が接続を壊し得る** (別 PoP に着地し TCP 状態が無い) |
| 運用の複雑さ | マッピング基盤 (測定・推定) を自前で持つ必要 | BGP 広告だけで成立、機構は単純 |
| 典型 | Akamai 型 (Nygren et al. 2010) | 小規模 CDN・DNS サービス自身・DDoS 吸収 |

- 実システムは併用が常態である: anycast で「大陸・地域」レベルの吸引を行い、DNS で PoP・クラスタ単位の精密制御を重ねる。QUIC の接続 ID はトランスポート層での経路変動耐性を与え ([`http-quic-evolution.md`](http-quic-evolution.md))、anycast の弱点を将来的に緩和する位置にある。
- PoP の内側は本書の守備範囲外である。1 つの PoP はそれ自体が ECMP → L4 → L7 の積層を内蔵した小さなデータセンターであり、その構造は [`load-balancing-architecture.md`](load-balancing-architecture.md) がそのまま適用される。

## 技術詳細 (Technical Details)

### 1. リクエストルーティング — 「最寄り」の製造

- **DNS マッピング**: CDN の権威 DNS がクエリ元リゾルバの位置・負荷・ヘルスから最適 PoP の IP を応答する。粗さの源はクライアントではなく**リゾルバ**の位置しか見えないことで、パブリック DNS (8.8.8.8 等) 経由では推定が大きくずれる。**EDNS Client Subnet (ECS)** はクライアントのプレフィクスを権威まで伝えて補正するが、応答がサブネット別に分裂しリゾルバのキャッシュ効率を下げる。精度とキャッシュの明示的な交換である ([`dns-resolution.md`](dns-resolution.md))。
- **anycast**: 全 PoP から同一プレフィクスを BGP 広告し、各 AS の経路選択に「最寄り」を委ねる。BGP は遅延を知らず AS パス長と経路ポリシで選ぶため「ネットワーク的に近い ≠ 速い」の乖離が残り、また経路変動 (route flap) の途中で TCP フローが別 PoP に着地すると接続はリセットされる。短命接続 (DNS、小さな HTTP) には理想的で、長寿命接続にはリスクが残る。
- **実務の合成**: 「anycast で入口を拾い、応答内の URL/DNS で精密誘導し直す」「静的アセットは anycast、API は DNS 誘導」など、両方式は層として重ねられる。発見事項 3 の表の縦読みが示す通り、これは [`load-balancing-architecture.md`](load-balancing-architecture.md) の「上の層の誤差を下の層が吸収する」構図の CDN 版である。

### 2. キャッシュの意味論 — 鍵・鮮度・無効化

- **キャッシュキー (cache key)**: 既定は概ね「ホスト + パス + クエリ」だが、`Vary` ヘッダや設定により言語・デバイス・Cookie が鍵に入り得る。鍵の設計は分裂 (同一実体が別鍵で重複保存されヒット率が落ちる) と衝突 (別実体が同一鍵にまとめられ誤配信される) の間のダイヤルであり、**クエリ文字列の正規化** (順序整列・無関係パラメータの除去) は分裂側の、後述のキャッシュポイズニングは衝突側の病理である。
- **鮮度と再検証**: `Cache-Control` (max-age, s-maxage, immutable, stale-while-revalidate) が鮮度を宣言し、期限切れは即削除ではなく**条件付きリクエスト** (`If-None-Match`/ETag) による再検証に回る。実体が不変なら `304 Not Modified` の数百バイトで鮮度が更新され、オフロードは保たれる (RFC 9111)。`stale-while-revalidate` は「古い応答を返しつつ裏で更新する」ことで再検証の RTT すら利用者から隠す。
- **無効化 vs バージョン付き URL**: 発見事項 4 の通り、分散無効化は高価で非同期である。「全 PoP から消えた」保証は本質的に到達確認の全数集計を要する。実務の定石は **cache busting**: HTML (短 TTL・再検証) からハッシュ付きアセット (長 TTL・immutable) を参照する二層構造にし、更新は HTML の差し替えだけで完結させる。無効化 API の出番は誤配信・法的削除など「別名で逃げられない」場合に限る。

### 3. 階層とヒット率 — Zipf・中間層・シールド

- **Zipf 的人気**: k 番目に人気のオブジェクトへのアクセス頻度が概ね k^-α に従うとき (Web ワークロードで繰り返し観測されてきた形。Breslau et al. 1999)、キャッシュ容量を増やしてもヒット率は対数的にしか改善しない。1 PoP あたりの流量が少ないほどテールは薄く、**PoP を増やして近さを買うほど、各 PoP のヒット率は下がる**。これは、近さとオフロードが機構として別 (発見事項 2) であるだけでなく、素朴には互いに打ち消し合うことを意味する。
- **中間層 (mid-tier / regional cache)**: 数十 PoP のミスを十数箇所の大容量キャッシュに集約すると、各 PoP では薄すぎたテールが合流して再び濃くなる。つまり階層は「Zipf 分布に対する流量の再集約装置」である。Akamai の設計論文 (Nygren et al. 2010) が cache hierarchy を中核機構として置くのはこのためである。
- **オリジンシールドとリクエスト合流**: シールドはオリジン直前の「最後の 1 段」であり、価値はヒット率よりも**合流**にある。同一オブジェクトへの同時ミスのうち最初の 1 本だけをオリジンへ通し、残りを待機させて応答を共有する (collapsed forwarding)。これがないと、人気オブジェクトの TTL 失効・新規公開・パージ直後に全世界の PoP が同時にオリジンを叩く **thundering herd** が起きる (発見事項 6)。オリジン帯域の課金削減という経済的効果も、ベンダがシールドを有償オプションとして売れる理由になっている。

### 4. 接続の最適化 — 終端・プール・プロトコル変換

- **エッジでの TLS 終端**: ハンドシェイクの往復を近距離で済ませることが「近さ」の利得の過半を占める。対価は**証明書の配布問題**である。顧客の秘密鍵 (または短命な派生鍵) を数百 PoP に置く必要が生じ、鍵をエッジに置かずハンドシェイク時だけ中央に署名を委譲する keyless 型の設計も生まれた。機構の詳細は [`tls-internals.md`](tls-internals.md) に委ね、リスクはセキュリティ考察で扱う。
- **エッジ→オリジンの持続接続プール**: 無数のクライアント接続を、確立済み・輻輳ウィンドウが開いた少数の keep-alive 接続に集約する。オリジンはハンドシェイクと slow client から遮蔽され、スロースタートを毎回やり直さない ([`tcp-transport-congestion.md`](tcp-transport-congestion.md))。L7 LB の接続プーリングと同じ非対称吸収を、地球規模の距離で行っている。
- **プロトコル変換 (protocol upgrade)**: クライアント側は HTTP/3/QUIC (損失の多い無線・モバイルで利得最大)、オリジン側は枯れた HTTP/1.1 という非対称が普通に成立する。エッジが両者を仲介するため、**オリジンを一切変更せずに最新プロトコルの恩恵をクライアントに届けられる**。これが、CDN がプロトコル移行の実質的な展開装置になってきた理由である ([`http-quic-evolution.md`](http-quic-evolution.md))。

### 5. 動的アクセラレーションとエッジ計算

- **動的アクセラレーション**: キャッシュ 0% でも、終端 + プール + 測定済み経路 (混雑した公共インターネットではなく CDN 自身のバックボーンを通す) で往復は縮む。「CDN = キャッシュ」という理解では説明できない、純粋な「近さ」の商品である (発見事項 7)。
- **エッジ関数の実行モデル**: CloudFront Functions / Lambda@Edge / Cloudflare Workers はいずれも「リクエスト/レスポンスを書き換える小さなコードを PoP で走らせる」製品だが、実行系の選択が経済を分ける。コンテナ/VM ベース (Lambda@Edge 型) はフルランタイムを提供する代わりにコールドスタートが重く配置地点も限られる。**V8 isolate ベース** (Workers / CloudFront Functions 型) は 1 プロセス内に多テナントの isolate を同居させ、起動をミリ秒未満・メモリを MB 級に抑えて全 PoP 配置を成立させる。多テナント同居の安全性が V8 自身の隔離機構に賭けられている点は、V8 の内部構造とサンドボックス設計 ([`../browsers/v8-internals.md`](../browsers/v8-internals.md)) がそのままセキュリティの前提になることを意味する (Cloudflare のアーキテクチャ説明に基づく。ベンダ資料)。
- **何をエッジに置くか**: 置けるのは認可トークン検証・リダイレクト・ヘッダ正規化・A/B 振り分けなど、**ローカルな入力だけで決定できる処理**。カウンタ・在庫・セッションのような一貫した状態を要する処理は、状態を数百 PoP に複製するコスト (= 分散合意か結果整合の受容) に見合わず中央に残る。エッジ計算の境界線は CPU ではなく状態が引く (発見事項 8)。

### 6. CloudFront への写像 — ベンダ事例として

本節は AWS 自身の公開ドキュメントに基づく**ベンダ記述**である。CloudFront は本書の階層にほぼ 1:1 で写像できる: エッジロケーション (数百) が エッジ PoP、**リージョナルエッジキャッシュ (regional edge cache)** が中間層、オプションの **Origin Shield** (特定リージョンの 1 箇所を最終段に指定) がオリジンシールドに当たり、Origin Shield の説明にはリクエスト合流 (request collapsing) が明記されている。定番構成は S3 オリジン + **OAC (Origin Access Control)** である。これは S3 バケットを非公開にし、CloudFront からの署名付きリクエストのみを受理させるオリジン遮蔽 (後述) の実装である。オリジン側のオブジェクトストアの内部構造は [`../object-storage/object-storage-architecture.md`](../object-storage/object-storage-architecture.md) を参照。エッジ計算は 2 段構え (CloudFront Functions = 軽量・全 PoP / Lambda@Edge = フルランタイム・リージョナル層) で、前節の実行モデルの二択が製品ラインとしてそのまま現れている。

## セキュリティ考察 (Security Considerations)

- **証明書の散在 (cert sprawl)**: TLS をエッジで終端する以上、顧客ドメインの秘密鍵 (相当物) が世界中の PoP に存在する。1 PoP の侵害が全顧客ドメインのなりすまし能力に化ける**爆発半径**の問題であり、緩和は短命証明書・自動ローテーション・鍵を PoP に置かない keyless 設計・HSM 格納である ([`tls-internals.md`](tls-internals.md))。
- **キャッシュポイズニング (cache poisoning)**: 応答の生成には影響するがキャッシュキーには入らない**unkeyed input** (特定ヘッダ等) を細工した応答をキャッシュに固定させると、攻撃者の 1 リクエストが以後の全利用者への配信になる。キャッシュは攻撃の増幅器でもある。よく研究された攻撃クラスであり、対策は「応答に影響する入力はすべて鍵に入れる (か無視する)」という鍵設計の規律と、曖昧なリクエストの拒否である。
- **オリジン遮蔽 (origin cloaking)**: CDN を前置してもオリジンの IP が知られていれば攻撃は CDN を素通りして直撃できる。オリジンは CDN からの署名付きリクエスト (CloudFront の OAC が典型) や許可リスト以外を拒否し、**オリジンのアドレス自体を秘匿する**。CDN の防御価値は「オリジンへの唯一の入口である」ことに全面依存する。
- **署名付き URL / Cookie**: 非公開コンテンツをエッジから配るには、エッジが検証できる自己完結な認可が要る。期限とスコープを署名した URL/Cookie は、中央への問い合わせなしに PoP 単体で検証できる (エッジに置ける認可の教科書例であり、発見事項 8 の実装形)。
- **DDoS の吸収**: 数百 PoP の合計帯域は攻撃帯域を桁で上回り、anycast は攻撃を多地点に希釈する。つまりエッジは構造的な DDoS 吸収層である。ただしそれはオリジン遮蔽が完全な場合に限る (穴が 1 つあればそこが直撃される) し、キャッシュミスを強制するリクエスト群 (ランダムクエリ付き) は攻撃をオリジンまで貫通させる。
- **集中化という系統リスク**: 実効的な CDN 事業者は少数であり、その 1 社の設定ミス・ソフトウェア障害が「インターネットの広範な同時障害」として現象する事例は近年繰り返し観測されている。個々のサイトにとって CDN は可用性を上げるが、**生態系全体では相関故障の源**になる。これは DNS の DoH 集中 ([`dns-resolution.md`](dns-resolution.md)) と同型の、防御と集中の交換である。マルチ CDN はこの相関を切る保険だが、証明書・設定・無効化の二重管理という運用コストを伴う。

## 結論 (Conclusions)

- CDN は光速という交渉不能な床への構造的応答であり、その商品は**近さ** (終端と配置が買う往復) と**オフロード** (階層キャッシュと接続集約が買うオリジン容量) の二つである。両者は機構が別であり、素朴には打ち消し合いさえする。それを両立させる装置が中間層とシールドを含む**キャッシュ階層**である。
- キャッシュ運用の成熟は「無効化を上手くやる」ではなく「無効化を不要にする」方向に進んだ。バージョン付き URL は一貫性問題を命名で解消する。同様にエッジ計算の境界も「速い実行系」ではなく「状態なしで決定できる範囲」が引く。CDN 設計の要諦は一貫して、**動かせないもの (光速・状態・オリジン容量) の周りに動かせるものを配置し直す**ことにある。
- セキュリティ上、CDN は信頼の再配置である。TLS の終端点・認可の検証点・DDoS の吸収点がすべて第三者の数百拠点に移る。それは個々のサイトの防御を強くしつつ、鍵の散在と事業者集中という新しい相関リスクを生態系に積む。
