# ロードバランシングのアーキテクチャ (Load Balancing: DNS, L4, L7 & the Cloud Control Loop)

## 概要 (Overview)

「N 台の交換可能なバックエンドにトラフィックを届ける」という問題は、単一の装置で解かれることはほとんどない。実際には**層と時定数の異なる決定の積層**として解かれる——DNS が「どのサイトへ」を分単位で粗く決め、経路制御 (anycast/ECMP) がフロー単位で入口を選び、**L4 ロードバランサ (load balancer)** が接続単位でマシンを選び、**L7 ロードバランサ**がリクエスト単位で振り分ける。現実の大規模システムはこのうち複数を必ず併用している。

中心テーゼは二つ。第一に、現代の L4 LB の核心は専用アプライアンスではなく**コンシステントハッシュ (consistent hashing)** である——Google Maglev や Microsoft Ananta が示した「ECMP でパケットをばら撒いても、どの LB に当たっても同じバックエンドに写像される」構造により、状態表は正しさの条件から**最適化**へと降格した。第二に、クラウドの弾力性 (elasticity) は LB を**検知器 (sensor) かつ作動器 (actuator)** とする制御ループである——ヘルスチェックが状態を観測し、オートスケーリングが容量を操作し、LB が新しい容量へ流量を配る。この見方に立つと、AWS ELB ファミリ (NLB/ALB/GWLB) は「製品群」ではなく、積層の各層をマネージドに切り出したものとして統一的に読める。

本書はこの積層を上 (DNS) から下 (L7) へ順に解体し、AWS ELB を通奏低音の事例として参照する。分析深度は Level 3。

## 方法論 (Methodology)

- 分散の各手段を「粒度 (何単位で決めるか) × 時定数 (どの速さで変えられるか) × 状態 (何を覚える必要があるか)」の三軸で統一的に比較し、併用の必然性を導く。
- ソフトウェア L4 LB は原典論文 (Maglev: NSDI '16、Ananta: SIGCOMM '13) を規範とし、設計判断の「なぜ」を優先する。クラウド LB の内部 (AWS Hyperplane 等) は一次公開資料が講演に限られるため、**ベンダ自身の説明**であることを明示して扱う。
- ハッシュ配置の系譜は剰余 → リング → 有界負荷 → Maglev 表の順に「何が壊れて何が直ったか」で追い、分散ストレージとの同型性は [`../object-storage/object-storage-architecture.md`](../object-storage/object-storage-architecture.md) に接続して重複記述を避ける。
- 個別製品の料金・上限値など変動の激しい仕様値には立ち入らず、構造に集中する。
- ヘルスチェック・オートスケーリングは制御工学の語彙 (観測・制御則・作動・むだ時間・正帰還/負帰還) に写像して記述し、機能の羅列ではなく安定性の設計として読む。

## 発見事項 (Findings)

1. **ロードバランシングは単一の装置ではなく、時定数の異なる決定の積層である。** DNS (分〜時間、TTL 拘束)、anycast/ECMP (フロー単位、経路収束)、L4 (接続単位、ミリ秒)、L7 (リクエスト単位、マイクロ秒)。上の層ほど粗く・安く・遅く、下の層ほど細かく・高価で・速い。どの層も単独では不十分で、**上の層の誤差を下の層が吸収する**構造が常態である。
2. **DNS 分散は「勧告」であって「制御」ではない。** ラウンドロビン/重み付き/地理応答は安価な第一段だが、TTL を無視・上書きするリゾルバとクライアント側キャッシュが実在するため ([`dns-resolution.md`](dns-resolution.md) §TTL)、**流量の即時制御にも確実なフェイルオーバにも使えない**。DNS は「概ね正しい入口」を配るだけであり、精密さは下の層に委ねられる。
3. **L4 LB の核心はコンシステントハッシュであり、状態表は正しさではなく最適化である。** Maglev/Ananta 型の構成では、ルータが ECMP でパケットを LB 群へ疑似ランダムに撒くため、個々の LB は「自分が最初のパケットを見た保証」を持てない。**どの LB でも 5 タプルから同じバックエンドが計算できる**ことが正しさを担い、接続追跡表は計算の短絡とバックエンド増減時の既存接続保護に使われる。LB 自体がステートレス寄りになることで、LB の追加・故障が N+1 で吸収できる。
4. **一貫性ハッシュは LB とストレージに共通する同一の道具である。** 剰余ハッシュの「1 台の増減で大半が再配置される」問題への解として、Karger のリング、有界負荷付き変種、Maglev の順列充填表はいずれも「**メンバ増減時の再写像を最小化しつつ均等に配る**」という同じ関数を実装している。Ceph の CRUSH ([`../object-storage/object-storage-architecture.md`](../object-storage/object-storage-architecture.md)) が「索引を関数に置き換えた」のと同型であり、違いは配置対象がデータかフローかに過ぎない。
5. **HTTP/2 は L4 バランシングを静かに壊す。** L4 は接続単位で配るが、HTTP/2/gRPC は**1 接続に多数のストリームを多重化する** ([`http-quic-evolution.md`](http-quic-evolution.md))。少数の長寿命接続が少数のバックエンドに張り付き、リクエスト量の偏りが接続数に現れない——gRPC のロードが「効かない」定番の原因であり、解はストリームを見る L7 バランシング (またはクライアントサイド LB) への引き上げである。
6. **ヘルスチェックは可用性の道具であると同時にカスケード障害の増幅器である。** 遅いバックエンドを外すと残りに負荷が集中し、次のバックエンドが遅くなって外され——という**正帰還**が全滅 (cascading failure) まで走り得る。閾値のヒステリシス、外せる台数の下限 (パニックモード)、能動チェックと受動観測の併用は、いずれもこの正帰還に挿入されたダンパである。
7. **クラウドの弾力性は LB を検知器・作動器とする制御ループである。** ヘルスチェック＋メトリクスが観測、オートスケーリングが制御則、ターゲット登録と接続ドレイン (draining) が作動。「LB = 振り分け装置」ではなく「**容量制御ループの入出力段**」と見ることで、ウォームアップ・ドレイン猶予・スケールイン保護といった一見雑多な機能が制御工学の語彙 (むだ時間・ハンチング対策) に整列する。
8. **L7 終端は性能の道具であると同時に信頼境界である。** TLS 終端・接続プーリング (多数のクライアント接続 → 少数のバックエンド接続への集約) は遅延とバックエンド負荷を大きく下げるが、**平文が存在する地点**と**HTTP 解釈の主体**を LB に作る。この二重性がそのままセキュリティ考察 (後述) の主題になる。

## アーキテクチャ (Architecture)

### 積層の全体像 — 1 リクエストが通る決定の連鎖

```
クライアント
   │ (1) 名前解決 — 分〜時間の粒度・TTL 拘束
   ▼
  DNS ──── 重み付き/地理/ヘルス連動で「サイト・VIP」を返す
   │
   ▼ (2) 経路 — anycast された VIP へ、BGP/ECMP がフロー単位で入口を選ぶ
 ルータ群 ══ ECMP (5 タプルハッシュ) ══╗
   │              │                  ║ どの L4 LB に当たるかは不定 —
   ▼              ▼                  ║ だから LB 側が「誰でも同じ答え」を持つ
 ┌──────┐   ┌──────┐   ┌──────┐     ║
 │L4 LB │   │L4 LB │   │L4 LB │ ◀══╝  ステートレス寄りの艦隊 (Maglev/Ananta 型)
 └──┬───┘   └──┬───┘   └──┬───┘        コンシステントハッシュ: 5タプル → 同一バックエンド
    └──────────┼──────────┘
               ▼ (3) 接続単位
 ┌────────┐ ┌────────┐ ┌────────┐
 │ L7 LB  │ │ L7 LB  │ │ L7 LB  │   TLS 終端・Host/Path ルーティング・
 └──┬─────┘ └──┬─────┘ └──┬─────┘   接続プール・リトライ (ALB/Envoy 型)
    ▼ (4) リクエスト単位 ▼
 ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐
 │ BE │ │ BE │ │ BE │ │ BE │ │ BE │  ← ヘルスチェック → オートスケーリング
 └────┘ └────┘ └────┘ └────┘ └────┘    (制御ループ: 観測 → 増減 → 再配分)
```

### 三層の比較 — 粒度・状態・コスト

| 軸 | DNS 分散 | L4 (Maglev/NLB 型) | L7 (ALB/Envoy 型) |
|---|---|---|---|
| 決定の粒度 | 解決 1 回 (実質セッション群) | 接続 (5 タプル) | リクエスト (ストリーム) |
| 保持する状態 | ほぼなし (ゾーンデータ) | 接続表 = 最適化 (なくても正しい) | 接続・TLS・プール = 必須状態 |
| 追加遅延 | なし (解決時のみ) | µs 級・パケット書換のみ | ms 級・終端と再暗号化 |
| 障害検知→除外の速さ | TTL 拘束で分単位以上 | ヘルスチェック数秒〜十数秒 | 受動検知も併用で最速 (即時リトライ可) |
| 内容に基づく振り分け | 不可 (せいぜい地理) | 不可 (5 タプルのみ) | 可 (Host/Path/ヘッダ/メソッド) |
| 典型例 | Route 53、GeoDNS | Maglev、Ananta、AWS NLB、IPVS | AWS ALB、Envoy、NGINX、HAProxy |

- 表の縦読みが発見事項 1 の根拠である: 上に行くほど状態が軽く粒度が粗い。**「速い検知」と「細かい制御」は下の層でしか買えず、その対価が状態と遅延**である。

## 技術詳細 (Technical Details)

### 1. DNS 分散 — 粗い第一段とその限界

- ラウンドロビン (複数 A/AAAA を順繰りに返す)・重み付き応答・地理/遅延ベース応答・ヘルスチェック連動 (不健全な VIP を応答から外す) が基本語彙。マルチリージョン構成では**リージョン選択はほぼ DNS (または anycast) の仕事**であり、これより下の層は同一サイト内の分配を担う。
- 限界は [`dns-resolution.md`](dns-resolution.md) の TTL 論がそのまま適用される: TTL は勧告であり、無視するリゾルバ・OS/アプリ内キャッシュ・接続の使い回しにより、**「DNS から外した」あとも旧宛先へのトラフィックは長く尾を引く**。ゆえに DNS フェイルオーバは「数分でほぼ切り替わる」以上を約束できず、即時性が要る切替は VIP の付け替え (経路広告) か下位 LB で行う。
- anycast/ECMP は DNS と L4 の間の層である: 同一 VIP を複数地点から BGP 広告し、経路選択で最寄りへ吸わせる。フロー単位の粘着は ECMP のハッシュが与えるが、**経路変動でハッシュの当たり先が変わる**——この「入口の不安定さ」を前提にできるかが、次節の L4 設計の出発点になる (ECMP/anycast の経路側の機構は [`ip-routing-bgp.md`](ip-routing-bgp.md) を参照)。

### 2. L4 ロードバランシング — Maglev/Ananta 系譜

- **構成**: ハードウェア LB ペア (アクティブ/スタンバイ、垂直スケール) を、**ECMP + 汎用サーバ上のソフトウェア LB 艦隊**で置き換えたのが Ananta (2013)・Maglev (2016) の系譜である。ルータは VIP への等コスト経路を LB 台数分持ち、5 タプルハッシュでパケットを撒く。LB の増減は BGP の経路増減として扱われ、水平スケールと N+1 冗長が同時に得られる。
- **正しさの再配置**: ECMP は接続の途中でも当たり先 LB を変え得る (LB の増減・経路変動)。そこで各 LB は (a) まず接続追跡表を引き、(b) ミスなら**コンシステントハッシュで計算**してバックエンドを決め、表に記録する。全 LB が同じハッシュ表を持つ限り、**どの LB に流れても同じバックエンドに着く**——接続追跡は「バックエンド集合が変わった直後の既存接続を守る」ための最適化であり、正しさの前提ではない (発見事項 3)。
- **Maglev ハッシュの直観**: 各バックエンドが素数長の表のスロットを自分の好みの順列で「早い者勝ち」に埋めていく。全員がほぼ同数のスロットを取り (均等性)、1 台の増減で書き換わるスロットは僅かに留まる (最小攪乱)。リング法より攪乱最小性を少し緩めた代わりに、**均等性と表引き 1 回 O(1) の速度**を取った——パケット毎に走る L4 のホットパスに合わせた選択である。
- **戻り経路**: **DSR (direct server return)** はバックエンドが VIP を自分宛と扱い、応答をクライアントへ直接返す——応答が往路より太い Web 型で LB の帯域を節約できるが、バックエンドに VIP 設定を要求し L4 までしか使えない。**フル NAT/プロキシ**は往復とも LB を通り、構成は単純だがソース IP が失われがちで、帯域も往復分要る。Maglev は GRE カプセル化で届けて DSR で返す構成を採る。
- **接続ドレイン (connection draining)**: バックエンドを外す際、新規接続の割当だけを止め、既存接続は完了 (またはタイムアウト) まで生かす。デプロイ・スケールインを無停止にする必須機構であり、ハッシュ表から消したあとも接続追跡表が旧接続を旧バックエンドへ導く——「状態表 = 最適化」の状態が、ここでは移行の優雅さを買っている。

### 3. 一貫性ハッシュの系譜 — 剰余からMaglev 表まで

- `hash(key) mod N` は N の変化で**ほぼ全キーが再配置**される——LB なら全接続の張り直し、キャッシュなら全ミス。この一点が系譜全体の駆動力である。
- **Karger のリング (1997)**: ノードとキーを同じハッシュ空間の円周に置き、キーは時計回りで最初のノードへ。ノード増減の影響は隣接区間のみ (期待 K/N)。仮想ノードで均等性を補う。元は Web キャッシュ (後の Akamai) のための提案であり、「**メンバシップが動的な集合への安定写像**」という問題設定自体がここで確立した。
- **有界負荷変種 (bounded loads)**: リングは均等性が確率的で、裾では特定ノードに負荷が偏る。各ノードに容量上限 (平均の (1+ε) 倍) を課し、溢れたら次のノードへ流す変種が「攪乱最小」と「偏り上限」を同時に保証する——キャッシュ・LB 双方で実用化された。
- **鍵の選び方も設計である**: 5 タプル全体をハッシュすれば分散は最良だが、同一クライアントの別接続は別バックエンドへ散る。ソース IP のみを鍵にすれば粗い親和性 (affinity) が得られるが、NAT 背後の大集団が 1 バックエンドに落ちる。鍵の選択は「均等性 vs 親和性」のダイヤルであり、スティッキーセッション (後述 §4) はこの選択を L7 の語彙でやり直したものと言える。
- **Maglev 表**: 前節の通り、均等性と O(1) 参照を優先した順列充填。系譜のどれを選ぶかは「攪乱最小・均等性・参照速度」の三すくみのどこを立てるかであり、**分散キャッシュ・ストレージ (Dynamo リング、Ceph CRUSH) と LB は同じ設計空間の別の点を選んでいる**に過ぎない ([`../object-storage/object-storage-architecture.md`](../object-storage/object-storage-architecture.md))。

### 4. L7 ロードバランシング — 終端・多重化・ヘルスチェック

- **TLS 終端と HTTP ルーティング**: L7 LB は TLS を終端し ([`tls-internals.md`](tls-internals.md))、Host/Path/ヘッダでターゲット群を選ぶ。証明書管理・プロトコル移行 (HTTP/2, HTTP/3 の受け口) を一点に集約できるのが運用上の最大の利点であり、同時にそこが信頼境界になる (セキュリティ考察)。
- **接続プーリングと多重化**: クライアント側の何万本もの (遅い・細切れの) 接続を、バックエンドへの少数の暖まった keep-alive 接続に**集約**する。バックエンドは接続管理から解放され、slow client からも遮蔽される——L7 LB の性能貢献は「振り分け」より**この非対称の吸収**にあることが多い。
- **HTTP/2・gRPC の罠**: 発見事項 5 の通り、1 接続 = 多ストリームの世界では接続単位の分配が壊れる。L7 LB は**ストリーム単位で異なるバックエンドへ再多重化**できるため、gRPC には「L7 で捌く」か「クライアントにリゾルバ＋LB を持たせる (ルックアサイド)」が定石になる。
- **スティッキーセッション vs ステートレス**: Cookie 等で同一クライアントを同一バックエンドへ固定すればローカル状態 (セッション、キャッシュ温度) を活かせるが、そのバックエンドの故障・ドレインで状態が消え、負荷も偏る。原則は**状態を外部化 (共有ストア) してバックエンドを交換可能に保ち**、スティッキーはキャッシュ親和性の最適化に限る——「状態表は最適化」という L4 の教訓の L7 版である。
- **リトライと外れ値排除 (outlier detection)**: L7 はリクエスト単位で失敗を観測できるため、失敗した 1 リクエストを**別のバックエンドへ即時リトライ**できる——これは受動ヘルスチェックの最速形である。ただし過負荷時の無制限リトライは負荷を増幅するため、リトライ予算 (全体の数 % に制限) を課すのが定石であり、ここでも「可用性の道具が増幅器に転じる」構図 (発見事項 6) が繰り返される。
- **ヘルスチェックの二態と正帰還**: **能動** (LB が定期的に専用エンドポイントを叩く) は明快だが検知が周期に律速され、全 LB が同じ周期で叩くと**同期したチェックの嵐**がそれ自体負荷になる (ジッタ挿入が必須)。**受動** (実トラフィックのエラー・遅延を観測) は速いが誤検知しやすい。閾値には**ヒステリシス** (unhealthy 判定 N 回連続、healthy 復帰 M 回連続、N≠M) を入れ、さらに「一定割合以上を同時に外さない」下限を設ける——過負荷で全台が遅いとき、正直に全台を外すと全滅するからである (発見事項 6)。遅延分布 (p99) と負荷の観測は [`../observability/observability-performance-engineering.md`](../observability/observability-performance-engineering.md) の主題に接続する。

### 5. クラウド LB の姿 — ELB ファミリを積層に写像する

- **NLB 型 (L4)**: 接続単位・µs 級・ソース IP 保存・AZ ごとの静的 IP。AWS の説明では、内部は **Hyperplane** と呼ばれる分散システムがフロー状態を艦隊で共有分担する——本書の言葉では「Ananta 型の艦隊 + 分散フロー状態」であり、**ベンダ講演ベースの記述**である点は留保する。ソース IP がそのまま届くため、バックエンド側でのアクセス制御・ログがクライアント実 IP で行える。
- **ALB 型 (L7)**: TLS 終端、Host/Path ルーティング、**ターゲットグループ** (バックエンド集合 + ヘルスチェック設定の単位)、クロスゾーン負荷分散 (AZ を跨いで均す——AZ 間転送コストと均等性の取引)。WebSocket/HTTP/2 対応、認証オフロード等、「アプリの入口」機能が集約される。
- **GWLB 型 (透過ミドルボックス挿入)**: ファイアウォール・IDS のような検査アプライアンス群を、**Geneve カプセル化**で経路上に透過挿入し、その艦隊自体をスケール・ヘルスチェックする。「LB = バックエンド選択」ではなく「LB = 任意のパケット処理艦隊への安定写像」への一般化であり、コンシステントハッシュの適用先が「サーバ」から「機能」へ広がった形である。
- **AZ という故障ドメイン**: ELB ファミリは AZ ごとにノードを持ち、DNS が AZ 単位の入口 IP を返す——つまり**マネージド LB 自身が本書の積層 (DNS → 艦隊 → ターゲット) を内蔵している**。クロスゾーン分散を切れば AZ は独立した故障ドメインとして振る舞い、入れれば均等性と引き換えに AZ 間の結合が生じる。故障ドメイン境界と均等性の取引は、ストレージのレプリカ配置と同じ形の決定である。
- **制御ループとしての全体像**: ターゲットグループのヘルスチェックが観測を、CloudWatch 系メトリクス (リクエスト数、ターゲット応答時間) が誤差信号を、オートスケーリングが制御則を、登録/ドレインが作動を担う。むだ時間 (起動〜ウォームアップ) があるループなので、急峻なスケールインはハンチングを起こす——クールダウンやスケールイン保護は制御ループの安定化項として読める (発見事項 7)。ヘルスチェックによる生死判定は、分散システムの故障検知の非同期性の議論 ([`../distributed-systems/consensus.md`](../distributed-systems/consensus.md)) の実務形でもある——「遅いだけ」と「死んだ」は原理的に区別できず、閾値はその賭けの明文化である。

## セキュリティ考察 (Security Considerations)

- **DDoS の吸収点**: LB はインターネットに面する最前線であり、SYN flood にはバックエンドへ接続を張る前の **SYN cookie**・接続数/レート上限で応じる ([`tcp-transport-congestion.md`](tcp-transport-congestion.md))。anycast は攻撃トラフィックを**多地点に希釈する**構造的防御でもある——単一地点の帯域を狙う攻撃は、入口が地理的に分散していると成立しにくい。
- **TLS 終端 = 信頼境界**: 終端点の内側では平文が存在する。LB〜バックエンド間を平文で流すか、再暗号化 (可能なら **mTLS**) するかは「内部網をどこまで信頼するか」の明示的な決定であり、証明書と秘密鍵が LB に集中することは、それ自体が高価値標的を作る ([`tls-internals.md`](tls-internals.md))。
- **リクエストスマグリング (request smuggling)**: L7 LB とバックエンドが**同じバイト列を異なるリクエスト境界で解釈する**とき (Content-Length と Transfer-Encoding の優先順位差など)、前段の検査を潜るリクエストを密輸できる。LB の導入が新しい攻撃面を作る典型であり、緩和は境界の曖昧さが構造的に小さい HTTP/2 系フレーミングの採用 ([`http-quic-evolution.md`](http-quic-evolution.md)) と、曖昧なメッセージの拒否である。
- **ヘルスチェックエンドポイント**: 認証なしで詳細を返す `/health` は内部構成の偵察窓になり、重い依存チェックを含む実装は**それ自体が DoS の梃子**になる。LB からのアクセスに限定 (ネットワーク層 or 認証) し、軽量な応答に保つ。
- **観測点としての集中**: L7 LB は全リクエストのメタデータ (URL、ヘッダ、クライアント IP) を見る唯一の地点になりがちで、アクセスログは運用の宝であると同時に**個人情報の集積点**である。ログの保持・マスキング方針は LB 導入時に決めるべき事項に含まれる。
- **Slowloris 型資源枯渇**: ヘッダを 1 バイトずつ送る類の低速攻撃は接続スロットを占有する。L7 LB はタイムアウト・最小転送レート・同時接続上限でこれを吸収し、バックエンドを遮蔽する——接続プーリングの遮蔽効果は性能だけでなく防御でもある。

## 結論 (Conclusions)

- ロードバランシングは「装置」ではなく**積層された決定**である。DNS が粗く、経路がフローを、L4 が接続を、L7 がリクエストを決め、各層は上の層の粗さと誤差を吸収する。設計とは「どの決定をどの層に置くか」の配分である。
- 系譜の転換点は**正しさの状態からの解放**だった。コンシステントハッシュが「どの LB でも同じ答え」を保証したことで、LB は複製すべきステートフル装置から水平スケールする計算になり、ECMP という既存の道具の上に載った。これはストレージが索引を CRUSH の関数に置き換えたのと同じ手筋である。
- L7 への引き上げは多重化時代の必然である一方、終端・解釈という**信頼境界と攻撃面**を対価に払う。そしてクラウドにおいて LB は分配器を超え、ヘルスチェックとオートスケーリングを両端に持つ**弾力性の制御ループの中枢**として振る舞う——可用性設計とは、この正帰還 (カスケード) を負帰還 (自動回復) に保つダンパ設計に他ならない。
