# リンカとローダ (Linkers & Loaders) — ELF・動的リンク・ASLR

## 概要 (Overview)

「コンパイル」と呼ばれる工程は、実際には**翻訳単位 (translation unit)** ごとの独立した変換である。コンパイラは `foo.c` を処理するとき、`bar.c` に定義された関数の中身も、最終的に自分のコードがどのアドレスに置かれるかも知らない。知らないまま出力できるのは、「他所にあるはずのもの」を**シンボル (symbol)** という名前で参照し、「後で決まるアドレス」を**再配置 (relocation)** という穴として残せるからである。この借金を一括返済する場が**リンカ (linker)** であり、返済の中身は**シンボル解決 (symbol resolution)** と**再配置**の2つに尽きる。リンカの他のすべての機能——遅延束縛も LTO も——は、この2操作の周りの最適化にすぎない。

分割コンパイルという抽象の代金をリンカが支払う、という視点で本ドキュメントは構成される。`../../hardware/hw-sw-interface/abi-syscalls.md` は ABI を「見えない契約」と呼んだが、その契約を実際に履行させる主体がリンカとローダである。1つのシンボルが `.o` ファイルから実行中のプロセスに至るまでの旅を、静的リンク → 動的リンク → ロード → セキュリティ機構の順で追う。分析深度は Level 3。

## 方法論 (Methodology)

- リンカの機能を「シンボル解決」と「再配置」の2つの基本操作に還元し、他の機構（PLT/GOT、遅延束縛、RELRO、LTO）をこの2操作の変奏として位置づける。
- ELF を**リンク時の見方（セクション）** と**実行時の見方（セグメント）** の二重ビュー (dual view) として捉え、同じバイト列を2枚の地図で読む。
- 具体的な再配置型 (R_X86_64_PC32) と PLT/GOT の呼び出し列を、ステップ単位で機械的に追跡する。
- 性能数値は桁感 (order of magnitude) にとどめ、リンカ高速化の倍率は各プロジェクトの公称値 (project-reported) と明記する。
- プラットフォーム比較（Linux ELF / macOS Mach-O / Windows PE）は、同じ問題（システムライブラリの共有と束縛）への異なる解として対比する。
- セキュリティは一貫して防御的観点から扱う。xz/liblzma 事件 (2024, CVE-2024-3094) は公開分析に基づき、「リンク・ロード機構自体が実行可能な攻撃面である」という教訓の実例として参照する。

## 発見事項 (Findings)

1. **リンカの本質はシンボル解決と再配置の2操作であり、それは分割コンパイルの代金である。** コンパイラが翻訳単位ごとに独立して動けるのは、未知の参照をシンボル名で、未定のアドレスを再配置エントリで先送りできるからである。リンカはこの先送りを清算する場であり、「undefined reference」も「multiple definition」もこの清算の失敗として機械的に説明できる。

2. **ELF は同じバイト列に2枚の地図を持つ。** リンカは**セクション (section)**（`.text`, `.data`, `.symtab`, ...）という細粒度の地図で結合・再配置を行い、カーネルとローダは**セグメント (segment / program header)**（`PT_LOAD`, `PT_INTERP`, ...）という粗粒度の地図で mmap する。`.bss` がファイル上のサイズを持たないのは、この2枚の地図が「ファイル上のサイズ」と「メモリ上のサイズ」を独立に記述できるからである。

3. **遅延束縛 (lazy binding) は「関数呼び出しは1段の間接参照を挟める」ことに立脚し、データ参照には適用できない。** 関数は PLT スタブ経由の間接ジャンプに差し替えられるが、データへのアクセスは `mov` 1命令であり、間に解決コードを挟む場所がない。ゆえにデータの再配置（GOT 経由または COPY 再配置）は起動時に即時解決するしかなく、この非対称が動的リンクの設計全体を貫いている。

4. **動的リンクの柔軟性（シンボル介入、LD_PRELOAD、IFUNC）は、そのまま攻撃面である。** malloc 差し替えや計測ツールを可能にする介入機構は、同じ経路で悪意あるコードの注入を許す。xz 事件は、IFUNC リゾルバが `main` より前に、しかも RELRO 適用前の書き込み可能な GOT を前にして走ることを悪用した——リンク・ロード機構は「データ処理」ではなく「コード実行」の段階である、という教訓の決定的な実例となった。

5. **ASLR・PIE・RELRO は、動的リンク機構自体の防御的再設計である。** 位置独立コード (PIC) は ASLR の前提であり、x86-64 の RIP 相対アドレシングがそのコストをほぼ消したことで PIE が既定になった。full RELRO は遅延束縛を放棄して起動時に全シンボルを束縛し、GOT を読み取り専用にする——性能のための機構（遅延束縛）を、安全のために正確に反転させたトレードオフである。

6. **リンカは「結合装置」から「最適化基盤」へ進化し、並列化が世代交代を駆動した。** LTO はプログラム全体を初めて見渡せる地点がリンカであることを利用し、オブジェクトファイルに IR を格納して最適化をリンク時へ移した。一方でリンク時間はビルドのボトルネックとなり、BFD ld → gold → lld → mold の系譜は徹底した並列化により桁違いの高速化（各プロジェクト公称）を達成した。

## アーキテクチャ (Architecture)

### パイプライン全景

```
 foo.c ──cc──▶ foo.o ─┐
 bar.c ──cc──▶ bar.o ─┼──ld──▶ a.out (ELF 実行ファイル)──execve──▶ カーネル
 libc.so (DT_NEEDED) ─┘                                            │ PT_LOAD を mmap
        [リンク時: シンボル解決 + 再配置]                            │ PT_INTERP を見て
                                                                   ▼
                                                    ld.so (動的リンカ/ローダ)
                                                     │ 依存 .so を mmap・再配置
                                                     ▼
                                                   実行中のプロセス
        [ロード時: 残りのシンボル解決 + 再配置 ── 同じ2操作の後払い]
```

静的リンクと動的リンクは別種の機構ではない。**同じ2操作（解決と再配置）を、ビルド時に払うか、ロード時・初回呼び出し時まで先送りするかの支払時期の違い**である。

### ELF の二重ビュー (Dual View)

同一の ELF ファイルを、リンカは**セクションヘッダテーブル**で、ローダは**プログラムヘッダテーブル**で読む。

```
        リンク時ビュー (sections)        実行時ビュー (segments)
        ┌────────────────────┐
        │ ELF header          │◀── 両ビューの入口
        ├────────────────────┤          ┌──────────────────────────┐
        │ Program headers     │─────────▶│ PT_LOAD #1  (R-X)         │
        ├────────────────────┤          │   .text .rodata .plt      │ ← コード: 読み+実行
        │ .text   (コード)     │──┐       ├──────────────────────────┤
        │ .rodata (定数)      │──┤       │ PT_LOAD #2  (RW-)         │
        │ .plt    (スタブ)     │──┘       │   .data .got .bss         │ ← データ: 読み+書き
        │ .data   (初期値あり) │──┐       │   ↑.bss は filesz=0,      │
        │ .got                │──┤       │     memsz>0 (零初期化)     │
        │ .bss    (零初期化)   │──┘       ├──────────────────────────┤
        │ .symtab .strtab     │─── ×     │ PT_DYNAMIC (動的リンク情報) │
        │ .rela.text 等       │─── ×     │ PT_INTERP  ("ld.so のパス")│
        ├────────────────────┤          └──────────────────────────┘
        │ Section headers     │           × = 実行時ビューに存在しない
        └────────────────────┘               (ロードされない)
```

- **セクション**はリンカの作業単位。`.symtab`（シンボル表）や `.rela.*`（再配置表）はリンクの材料であり、実行には不要なのでどのセグメントにも属さない（`strip` で除去できるのはこのため。ただし動的リンク用の `.dynsym` は実行時も必要）。
- **セグメント**はカーネル・ローダの mmap 単位。属性の同じセクションが1つの `PT_LOAD` に束ねられ、ページ単位の保護 (R/W/X) が掛かる。
- **`.bss` がファイル容量を消費しない理由**: プログラムヘッダは `p_filesz`（ファイル上のサイズ）と `p_memsz`（メモリ上のサイズ）を別々に持つ。零初期化データは「メモリ上の大きさ」だけを宣言すれば、ローダが零ページを割り当てる。ファイルに数 MB の零を書き込む必要はない。

## 技術詳細 (Technical Details)

### 1. 静的リンク — シンボル解決の規則

リンカは全 `.o` のシンボル表を突き合わせ、各**未定義シンボル (undefined symbol)** を唯一の**定義 (definition)** に結びつける。規則は単純だが、単純さゆえに罠がある。

- **強シンボルと弱シンボル (strong / weak)**: 強シンボル（通常の関数・初期化済み大域変数）の定義は全体で1つでなければならない。2つあれば **multiple definition** エラー。弱シンボル（`__attribute__((weak))` 等）は強シンボルに黙って負け、弱同士なら任意の1つが選ばれる。C の「共通シンボル (common symbol)」（`int x;` のような仮定義）は歴史的に弱に似た併合をされてきたが、現代のコンパイラは既定で `.bss` の強定義にする (`-fno-common` が GCC 10+ の既定)。
- **アーカイブの意味論 (archive semantics)**: `libfoo.a` は `.o` の束であり、リンカは**その時点で未解決のシンボルを供給するメンバだけ**を取り出す。しかも走査は基本的に**一回通過 (single-pass)** で、コマンドラインの左から右へ進む。ゆえに `ld main.o -lfoo` は解決するが、`ld -lfoo main.o` は「`-lfoo` を見た時点では未解決シンボルが無い」ため何も取り出さず、後から現れた `main.o` の参照が未解決に終わる。**アーカイブは参照より後ろに置く**という規則は、この一回通過の直接の帰結である（循環依存には `--start-group` で再走査を強制する）。

2大失敗モードはこのモデルから機械的に導ける。

- **undefined reference**: 清算時に定義が見つからない。原因は綴りではなく大抵「供給者がコマンドラインで参照者より左にいる」「そもそもリンク対象に入っていない」「C++ の名前修飾 (name mangling) の不一致（`extern "C"` 漏れ）」。コンパイルは通る——コンパイラは定義の存在を検査しない——のがこのエラーの本質である。
- **multiple definition**: 同じ強シンボルが2つ。ヘッダに書かれた非 `inline` 関数定義や、`static` を欠いた大域変数が翻訳単位ごとに定義を生むのが典型。

### 2. 静的リンク — 再配置の機構

再配置エントリは「どこ (offset) に、どのシンボル (symbol) の値を、どの計算式 (type) で書き込むか」の3つ組である。代表として **R_X86_64_PC32**（PC 相対 32bit）を追う。

```
// 例示 (illustrative)。foo.o が bar() を call する場合。
// コンパイラ出力 (foo.o):
//   e8 00 00 00 00        call <bar>     ← オペランド4バイトは 0 の穴
//   再配置: offset=call命令+1, type=R_X86_64_PC32, symbol=bar, addend=-4
//
// リンカの計算:  値 = S + A - P
//   S = bar の最終アドレス       (例: 0x401200)
//   A = addend = -4              (オペランドの終端と次命令の差の補正)
//   P = 穴のアドレス             (例: 0x401085)
//   値 = 0x401200 + (-4) - 0x401085 = 0x177
//   → e8 77 01 00 00      call rip+0x177 相当
```

`call` のオペランドが「次命令の先頭からの相対距離」で解釈されるため、穴の位置 P と次命令のずれを addend (-4) が補正する。この式が示すとおり、**PC 相対参照はコード全体が一緒に平行移動しても壊れない**——後述の PIC/ASLR がこの性質の上に建つ。逆に絶対アドレス型 (R_X86_64_64 等) は移動すると壊れるため、実行時再配置か GOT 間接化が必要になる。

### 3. 動的リンク — PLT/GOT と遅延束縛

共有ライブラリ (shared library) の関数アドレスはロード時まで決まらない。呼び出し側の `.text` は複数プロセスで共有したい（書き換えたくない）ため、書き換えてよい間接テーブル **GOT (Global Offset Table)** と、そこを経由するスタブ列 **PLT (Procedure Linkage Table)** に間接化を集約する。

```
  ── 初回呼び出し (first call) ──────────────────────────────
   call printf@plt
        │
        ▼
   PLT[printf]:  jmp *GOT[printf] ──▶ GOT は最初 PLT の次行を指す
                 push  reloc_index  ◀─┘ (つまり自分に戻ってくる)
                 jmp   PLT[0]
                        │  共通スタブ: ld.so の resolver へ
                        ▼
   _dl_runtime_resolve: printf の実アドレスを検索し
                        GOT[printf] ← 0x7f..1234 に**パッチ**
                        そのまま printf 本体へジャンプ
  ── 2回目以降 (subsequent calls) ────────────────────────────
   call printf@plt
        │
        ▼
   PLT[printf]:  jmp *GOT[printf] ──▶ 0x7f..1234 (printf 本体へ直行)
                                       resolver はもう介在しない
```

- 解決コストは**初回の1回だけ**払い、以後は間接ジャンプ1回に落ちる。起動時に全シンボルを解決しない分、起動が速い——数千シンボルを持つ大型プログラムで、実際に呼ぶのは一部だけという典型に適合する。
- **データ参照が遅延できない理由**: `mov rax, [extern_var]` には PLT スタブに相当する「割り込み地点」がない。よって変数はロード時に即時解決される。方式は2つ——(a) PIC なら GOT 経由の間接参照にコンパイルする、(b) 非 PIC 実行ファイルが共有ライブラリの変数を直接参照する場合、**COPY 再配置**でロード時に変数の実体を実行ファイル側の `.bss` へ複製し、ライブラリ側の参照もそちらに向け直す（実体が「移住」する）。COPY 再配置はライブラリの変数サイズ変更を ABI 破壊にする古い仕組みで、PIE の普及とともに減っている。
- **シンボル介入 (symbol interposition)**: ELF の既定では、シンボル検索は大域スコープを検索順に走査し**最初の定義が勝つ**。`LD_PRELOAD` は任意のライブラリを検索順の先頭に挿入する環境変数であり、これで `malloc` を差し替えるのが jemalloc/tcmalloc の導入法、`open`/`connect` を包むのが計測・テストツールの常套手段である。正当な拡張点だが、後述のとおり攻撃経路と紙一重。
- **可視性とバージョニング**: `__attribute__((visibility("hidden")))` や版スクリプトで公開シンボルを絞ると、介入不能になる代わりに解決が速く ABI 面が小さくなる。glibc は**シンボルバージョニング (symbol versioning)** (`memcpy@GLIBC_2.14` のような版付きシンボル) で、同名関数の新旧意味論を1つの .so に共存させ、古いバイナリを壊さず挙動を変更してきた。「新しい glibc でビルドしたバイナリが古い glibc で動かない」のは、この版要求が満たせないからである。
- **依存グラフと検索順序**: 各 .so は `DT_NEEDED` で依存を宣言し、ld.so がグラフを幅優先で辿ってロードする。検索パスの優先順は概ね `DT_RPATH`（非推奨・グラフ全体に伝播）→ `LD_LIBRARY_PATH` → `DT_RUNPATH`（そのオブジェクトの直接依存にのみ効く）→ `/etc/ld.so.cache` → 既定パス。**RPATH は環境変数より強く、RUNPATH は弱い**という非対称、RUNPATH が推移的依存に効かないという仕様は、ビルド環境では動くのに配布先で違う .so を掴む、という事故の定番原因である。

### 4. ローダ — execve からプロセスへ

1. **カーネル**: `execve(2)` が ELF ヘッダを読み、`PT_LOAD` セグメントをアドレス空間に mmap する。`PT_INTERP`（通常 `/lib64/ld-linux-x86-64.so.2`）があれば動的リンカも mmap し、エントリポイントを **ld.so 側**に設定してユーザ空間へ戻る。カーネルの仕事はここまでで、以後のリンクはすべてユーザ空間で行われる。
2. **ld.so の自己再配置 (self-relocation)**: ld.so 自身も共有オブジェクトであり再配置を要するが、それを行うはずの動的リンカは自分自身である。よって起動直後の ld.so は「外部シンボル参照も未再配置の大域データも使えない」制約下の慎重なコードで**自分の再配置だけを先に済ませ**、しかる後に通常のリンカとして依存ライブラリの処理を始める。
3. **mmap とページ共有**: 各 .so の `.text` はファイル裏付きの読み取り専用 mmap なので、`../../hardware/cpu-architecture/virtual-memory-mmu.md` で見たページキャッシュ (page cache) の**クリーンな共有ページ**として全プロセスが同一物理ページを指す。libc の数 MB が 100 プロセスにあっても物理には約1部——動的リンクのメモリ効率はこの機構の直接の恩恵である。書き込みを伴う `.data`/GOT はプロセスごとに CoW で分岐する。
4. **TLS (Thread-Local Storage)**: スレッドローカル変数のアクセスは**モデル**で速さが変わる。実行ファイル本体と起動時ロードのライブラリは **initial-exec**（TLS ブロックの位置が起動時に確定し、セグメントレジスタ FS からの固定オフセットでアクセス）で済むが、`dlopen` されうるライブラリは **general-dynamic**（`__tls_get_addr()` 呼び出しでモジュール ID とオフセットから動的に引く）を強いられ、1参照ごとに関数呼び出し相当のコストを払う。ここでも「後から来る者ほど間接化が深い」という動的リンクの一般法則が現れる。
5. **IFUNC (indirect function)**: `STT_GNU_IFUNC` 型のシンボルは、再配置時に**リゾルバ関数をその場で実行**し、返ってきたアドレスを解決結果とする機構である。glibc が `memcpy` を CPU 機能 (AVX2/AVX-512) に応じて最適実装へ振り分けるのが本来の用途だが、これは「ロード時＝`main` より前に、ライブラリ提供の任意コードが走る」ことを意味する。**xz/liblzma 事件 (CVE-2024-3094, 2024)** は、この性質を悪用した公開事例である。liblzma に仕込まれた IFUNC リゾルバが、sshd プロセスのロード時（RELRO による GOT 保護が確定する前・監査の効きにくい段階）に走り、シンボル解決過程に介入して RSA 検証関数を乗っ取った。防御側の教訓は明確で、**リンク・ロード機構は受動的なデータ処理ではなく、依存物に与えるロード時実行権そのもの**として監査対象にせよ、ということである（コンストラクタ `DT_INIT`/`.init_array` も同様のロード時実行点である）。

### 5. ASLR・PIE・RELRO

- **PIC (Position-Independent Code)**: コードがどの番地に置かれても動くよう、大域参照を GOT 相対に落とす生成方式。32bit x86 には PC 相対アドレシングがなく、`call` して戻り番地を読む thunk で PC を取得し、貴重なレジスタを GOT ポインタ (EBX) に固定するため数%〜の実測コストがあり、実行ファイルを PIC にする動機が乏しかった。**x86-64 の RIP 相対アドレシング**が命令1つで PC 相対参照を実現してコストをほぼ消し、実行ファイル自体を位置独立にする **PIE (Position-Independent Executable)** が主要ディストリビューションの既定となった。
- **ASLR (Address Space Layout Randomization)**: スタック・ヒープ・mmap 領域・（PIE なら）実行ファイル本体のベースを実行ごとに乱択し、攻撃者がアドレスを事前に知り得ないようにする。エントロピーは対象と設定で異なり（Linux x86-64 の mmap ベースで 28bit 級、32bit 環境では 8〜16bit 級と大幅に低い——世代・設定依存の桁感）、**ライブラリは1ベースがずれるだけ**なので、関数ポインタ1つの漏洩でそのモジュール全体の配置が割れる。ASLR は「アドレスを秘密にする」確率的緩和であり、境界検査の代替ではない。
- **RELRO (RELocation Read-Only)**: 再配置対象領域を、再配置完了後に `mprotect` で読み取り専用へ倒す。**partial RELRO** は `.init_array` や `DT_DYNAMIC` 等を保護するが、遅延束縛用の GOT (`.got.plt`) は書き込み可能なまま残る。**full RELRO** (`-Wl,-z,relro,-z,now`) は `BIND_NOW` で**起動時に全シンボルを束縛してから GOT ごと読み取り専用化**する。遅延束縛が「起動を速くするため解決を遅らせる」機構だったのに対し、full RELRO は「GOT を凍結するため解決を早める」——同じトレードオフの正確な反転であり、起動時間と引き換えに GOT 書き換え攻撃の面を消す。現代のディストリビューションは full RELRO を既定とする方向に収斂した。

### 6. LTO とリンカの進化

- **LTO (Link-Time Optimization)**: 従来の最適化は翻訳単位に閉じ、`.o` を跨ぐインライン化や到達不能コード除去はできなかった。LTO はオブジェクトファイルに機械語ではなく**コンパイラ IR（GCC は GIMPLE、LLVM はビットコード）** を格納し、全体が初めて見えるリンク時に最適化を再実行する。「リンカ」が呼ばれるが、実体はリンカに埋め込まれたコンパイラバックエンドであり、コンパイルとリンクの境界はここで溶ける。全モジュールを1つに併合する full LTO はメモリ・時間コストが大きいため、要約情報だけを全体共有し本体は並列に最適化する **ThinLTO** が実用の主流となった。
- **リンカの世代交代**: リンクは差分ビルドでも毎回全体をやり直すためビルド時間の支配項になりやすい。GNU **BFD ld**（汎用だが低速）→ **gold**（ELF 専用化で高速化）→ LLVM **lld**（設計刷新と並列化で gold 比数倍と公称）→ **mold**（ほぼ全工程の並列化で lld 比さらに数倍、BFD ld 比では桁違いと公称）と、駆動要因は一貫して**並列性の徹底**である（倍率はいずれも各プロジェクトの公称値であり、対象バイナリとハードウェアに強く依存する）。シンボル解決というグローバルな逐次処理をいかに並列分解するかが設計の中心問題となった。

### 7. プラットフォーム対比 — dyld・Android linker・PE/COFF

- **macOS/iOS (Mach-O + dyld)**: 全システムライブラリを事前リンクして固定配置の1ファイルに焼き込む **dyld 共有キャッシュ (dyld shared cache)** が中核。個々の .dylib のロード・再配置・束縛をビルド時に済ませた完成品を全プロセスが mmap するため、プロセス起動時のリンク作業が激減する（`../ios/platform-architecture.md` — Zygote なき iOS で「全プロセス物理1部」を実現する機構として詳述）。近年は遅延束縛を廃し、署名検証と両立する **chained fixups** で起動時一括修正に移行した。
- **Android**: Linux ELF だが、独自の bionic linker が **linker namespaces** で「どのライブラリがどの名前空間から見えるか」を強制する。アプリから内部ライブラリへの `dlopen` を遮断し、system/vendor 分離 (Treble) をリンカ層で貫く（`../android/art-runtime-internals.md` の ClassLoader 階層と対をなす）。
- **Windows (PE/COFF)**: **インポートテーブル (IAT: Import Address Table)** が GOT に相当するが、シンボルは「DLL 名 + 関数名/序数」で二段修飾され、ELF の平坦な大域スコープと違い**どの DLL から取るかが束縛に固定される**（介入が構造的に起きにくい）。乱数化は ASLR だが、歴史的には DLL ごとの推奨ベースアドレスへの**リベース (rebase)** が先にあり、ブート時に決めたベースをプロセス間で共有する設計が特徴。

| | Linux (ELF) | macOS/iOS (Mach-O) | Windows (PE/COFF) |
|---|---|---|---|
| 遅延束縛 | PLT/GOT（full RELRO では放棄） | 旧: lazy pointer → 現: chained fixups で起動時一括 | IAT は原則ロード時束縛（遅延ロードはリンカのオプション機能） |
| 乱数化 | ASLR + PIE（実行ごと） | ASLR + 共有キャッシュは端末単位でスライド | ASLR（ベースはブート単位で共有される傾向） |
| システムライブラリ戦略 | 個別 .so + ページキャッシュ共有 | dyld 共有キャッシュ（事前リンク済み固定レイアウト） | 個別 DLL + 推奨ベース/リベース |
| 介入の容易さ | 高い（大域スコープ + LD_PRELOAD） | 中（DYLD_INSERT_LIBRARIES、SIP/署名で制限） | 低い（二段修飾、Detours 等はパッチ方式） |

## セキュリティ考察 (Security Considerations)

リンク・ロード機構は「アドレスを書き換え可能な表に集約し、外部から供給されるコードを実行前に走らせる」機構であり、その柔軟性の一つひとつが攻撃面に対応する。以下すべて防御的観点からの整理である。

- **GOT 書き換え (GOT overwrite)**: GOT は「関数ポインタの表」そのものであり、任意書き込みが1つあれば GOT エントリを攻撃者制御のアドレスに向けて制御フローを奪える、古典的なハイジャック標的である。緩和は **full RELRO**（GOT の読み取り専用化）であり、遅延束縛の放棄という明確なコストと引き換えに、この標的を消す。
- **環境変数経由の注入**: `LD_PRELOAD` / `LD_LIBRARY_PATH` は正当な拡張点だが、攻撃者が環境変数を制御できる状況では任意コード注入経路になる。このため ld.so は **secure-execution モード**（setuid/setgid バイナリや capability 付与時、`AT_SECURE` 補助ベクタで通知）では `LD_PRELOAD` 等の危険な環境変数を無視・制限する。特権昇格境界では「環境は攻撃者入力」として扱う、という原則の実装である (ld.so(8))。
- **検索パス乗っ取り (search-path hijacking)**: RPATH に相対パスや書き込み可能ディレクトリが焼かれていると、攻撃者が同名 .so を先回りで置ける。Windows で古典的な「DLL プランティング」（アプリのカレントディレクトリから DLL を拾う）と同型の問題であり、監査ツールで RPATH/RUNPATH を検査し、絶対パス・`$ORIGIN` の慎重な使用に限定するのが定石。
- **サプライチェーンとロード時実行 — xz の教訓**: 技術詳細 4 で述べたとおり、xz 事件は IFUNC・コンストラクタという**ロード時実行点**が、依存ライブラリに与えている暗黙の実行権を悪用した。依存を1つ足すことは「`main` より前に走るコードの提供者を1者増やす」ことである。緩和は単一の技術ではなく、依存の最小化、ビルドの再現可能性 (reproducible builds) による成果物検証、ロード時実行点（IFUNC/`.init_array`/`DT_NEEDED` の変化）の差分監査の組み合わせになる。
- **ロード時コード署名との対比**: Linux の ld.so はロードする .so の出所を検証しない（検証は パッケージ管理・IMA 等の別層の責務）。対照的に macOS/iOS はロード時に**コード署名 (code signing)** を検証し、iOS では実行可能ページの生成自体を署名済みコードに限定する。dyld の chained fixups が遅延束縛を捨てた一因も、ページ内容を署名検証と両立する形で確定させるためであり、「柔軟な束縛」と「検証可能なコード」の緊張関係がプラットフォーム設計を分けている（`../ios/platform-architecture.md`）。
- **ASLR 回避の構造**: ASLR は秘密（ベースアドレス）に依存する確率的防御であり、(a) 情報漏洩 (info leak) でポインタが1つ漏れればモジュール単位で無効化される、(b) 32bit 環境ではエントロピー不足で総当たりが現実的、(c) forkサーバ型プロセスは子が同一配置を継承するため試行で削れる。ゆえに ASLR は単独では成立せず、スタック保護・W^X・CFI 等との**多層防御 (defense in depth)** の一層として設計されている。

## 結論 (Conclusions)

- リンカの仕事はシンボル解決と再配置の2操作に還元でき、これは分割コンパイルという抽象の代金である。静的リンクと動的リンクの違いは操作の種類ではなく**支払時期**（ビルド時 / ロード時 / 初回呼び出し時）の違いにすぎない。
- ELF の二重ビュー（リンカのためのセクション、ローダのためのセグメント）は「同じバイト列を工程ごとに別の地図で読む」設計であり、`.bss` の filesz=0 のような一見奇妙な性質もこの分離から自然に導かれる。
- 遅延束縛・シンボル介入・IFUNC といった動的リンクの柔軟性は、GOT 書き換え・LD_PRELOAD 注入・xz 型サプライチェーン攻撃という攻撃面と表裏一体である。full RELRO や chained fixups への収斂は、「柔軟性を削って束縛を早期に凍結する」方向への業界全体の再設計と読める。
- ASLR/PIE は再配置機構（PC 相対参照・GOT 間接化）の防御的転用であり、x86-64 の RIP 相対アドレシングというハードウェアの進化が、ソフトウェア側の既定値 (PIE by default) を変えた好例である。
- リンカは LTO によって最適化基盤へ、mold 系によって並列システムへと進化しており、「コンパイル」と「リンク」の境界は溶けつつある。それでも中心にあるのは依然として、シンボルを解決し穴を埋めるという2つの操作である。
