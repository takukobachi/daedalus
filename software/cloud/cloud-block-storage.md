# クラウドブロックストレージ (Cloud Block Storage: EBS-style Volume Virtualization)

## 概要 (Overview)

**ブロックストレージ (block storage)** は、計算機に最も古くからある記憶の抽象（固定長ブロックの配列に対する LBA 指定の read/write）を、ネットワーク越しの分散システムとして再実装したものである。AWS EBS (Elastic Block Store)、Azure Managed Disks、GCP Persistent Disk がこの製品カテゴリであり、ゲスト OS からは 1 本の NVMe/virtio-blk デバイスに見えるが、実体は複数のストレージサーバに複製・ストライプされた**仮想ボリューム**である。

[`../object-storage/object-storage-architecture.md`](../object-storage/object-storage-architecture.md) が「POSIX を捨てて惑星規模を買った」システムだとすれば、ブロックストレージはその対極にいる。**単一ライター・強一貫・マイクロ秒〜ミリ秒レイテンシ・書き込み順序**というローカルディスクの意味論を一切値切らずにネットワークへ持ち出し、代わりにスケールの単位を「ボリューム 1 本」に限定した。本ドキュメントの中心テーゼは 2 つ。(1) この契約の下では複製に**チェーン複製 (chain replication)** 型の強一貫プロトコルが適合し、難しさはデータ経路ではなく**構成管理**（どのレプリカが正か）へ凝縮される。[`cloud-control-planes.md`](cloud-control-planes.md) で扱った Physalia はまさにここで生まれた。(2) ブロックストレージの価値の本体は速さではなく**故障ドメインの分離**、つまり計算 (インスタンス) と記憶 (ボリューム) の運命を切り離すことであり、スナップショット・付け替え・停止/再開というクラウドの運用モデル全体がこの分離の上に立つ。分析深度は Level 3。

## 方法論 (Methodology)

- ブロックデバイスの契約（意味論）を最初に固定し、各機構を「契約のどの条項を守るための実装か」として読む。[`../object-storage/object-storage-architecture.md`](../object-storage/object-storage-architecture.md) と同じ座標系を使い、対極の設計点として常時対比する。
- **出典階層上の注意**: EBS には Aurora/DynamoDB のような包括的なシステム論文が存在しない。本書は、査読付きの部分文書（Physalia NSDI '20 がデータ経路の複製方式に言及、SRD の IEEE Micro 論文）、チェーン複製の原典 (OSDI '04)、2011 年障害の公式ポストモーテム（ベンダー一次資料だが、事故記述としては最良の公開資料）、および現行仕様のベンダー文書を組み合わせ、それぞれの出典等級を明示する。
- ゲスト側の入口 (NVMe/virtio, ブロック層) は [`../../hardware/hw-sw-interface/storage-nvm-interface.md`](../../hardware/hw-sw-interface/storage-nvm-interface.md) と [`../operating-systems/block-io-stack.md`](../operating-systems/block-io-stack.md) に、Nitro カードによる I/O 仮想化は [`../virtualization/hardware-virtualization-containers.md`](../virtualization/hardware-virtualization-containers.md) に委ね、本書はネットワークの向こう側に集中する。

## 発見事項 (Findings)

1. **ブロックストレージの契約はオブジェクトストレージの正反対であり、設計もすべて逆になる。** 強一貫・低レイテンシ・書き込み順序・単一ライターという契約は、地理分散・結果整合・巨大スケールという S3 型の選択肢を最初から排除する。複製は同一 AZ 内に閉じ（レイテンシと分断確率のため）、名前空間は「ボリューム」単位に分割され（グローバル索引が不要）、クライアントは常に 1 つ（マルチライターは例外的オプション）。**スケールはボリューム数の水平方向にだけ広げ、1 本のボリュームの意味論は縦に守る**。「貧しい API で惑星規模」の S3 と「豊かな意味論で局所規模」の EBS は、同じ耐久性目標を逆の道具立てで達成する双対である。

2. **強一貫の複製にはチェーン複製が適合し、その難しさは構成変更に凝縮される。** チェーン複製 (OSDI '04) は書き込みを先頭→末尾へ順に流し、読み取りを末尾で行うことで、クォーラム読みなしの強一貫と高スループットを両立する。この方式は、ブロックデバイスの「ack した書き込みは以後必ず見える」という契約に最短距離で一致する。ただしチェーンはメンバー故障のたびに**構成 (どのノードがどの順で鎖を成すか) の強一貫な変更**を要求し、これはチェーン自身では解けない（合意が要る）。EBS の実装ではボリュームデータの複製がこの型であり、構成の権威を外部の合意ストア Physalia が持つ (NSDI '20)。**データ経路は単純に速く、構成の合意は小さく別置きに**という分業は、[`cloud-control-planes.md`](cloud-control-planes.md) のコントロール/データプレーン分離がボリューム 1 本の粒度で起きたものである。

3. **2011 年の EBS 大規模障害は「再ミラーリングの嵐」というメタステーブル障害の古典であり、以後の設計思想の出自になった。** 公式ポストモーテム（ベンダー一次資料）によれば、ネットワーク変更ミスで複製トラフィックが低容量経路へ流れ込み、多数のレプリカペアが同時に切断→**大量のボリュームが一斉に再ミラー先を探索**→空き容量の枯渇→再試行の嵐が制御プレーンを飽和させ、障害が AZ を越えて API 全体へ波及した。トリガ（ネットワーク変更）除去後も過負荷が自己維持した点で、後年定式化されるメタステーブル障害 (HotOS '21) の教科書事例である。ここから「制御プレーンの分割と近接配置 (Physalia)」「容量ヘッドルームの事前確保（静的安定性）」「リトライの抑制」という [`cloud-control-planes.md`](cloud-control-planes.md) の原則群が、事故の経験から直接導出された。

4. **スナップショットは「ブロックデバイスの時間軸をオブジェクトストレージへ射影する」機構である。** スナップショットは変更ブロック追跡 (changed-block tracking) に基づく増分チャンクの集合として S3 型ストアへ置かれ、各スナップショットは「チャンクへの参照表」として**論理的には完全・物理的には増分**になる。ユーザから full/incremental の区別が消えるのはこの間接層のためであり、途中のスナップショットを削除しても他が使えなくならないのは参照カウントの帰結である。復元は全チャンクのダウンロードを待たず、**読まれたブロックからオンデマンドに埋める** (lazy restore)。これは [`serverless-faas-internals.md`](serverless-faas-internals.md) のコンテナイメージ遅延ロードと同じ「ダウンロードするな、ページインせよ」の型である。初回読み取りのレイテンシ税を先払いする事前ウォーム（高速スナップショット復元）がオプションとして売られるのも同型。

5. **性能の次元（容量・IOPS・スループット・レイテンシ）は分離して売られるようになった。ボリュームの仮想化が価格の仮想化を可能にする。** 物理ディスクでは容量と IOPS は同じスピンドルに縛られるが、仮想ボリュームは多数のサーバへのストライプなので、各次元を独立に割り当てられる。gp3 型の「容量と IOPS を別々に購入する」価格モデルは、この実装の自由度をそのまま製品面に露出したものである（ベンダー仕様）。残る床はネットワーク RTT であり、これを削る戦線がトランスポート (SRD: マルチパスで順序保証を捨てたデータセンター特化プロトコル, IEEE Micro 2020) と、プロトコル処理の Nitro カードへのオフロードである。[`../networking/virtual-networks-overlay.md`](../networking/virtual-networks-overlay.md) の「ネットワーク税を専用ハードへ」という流れのストレージ版が、並行して進んでいる。

6. **インスタンスストアとの対立軸は速度ではなく運命の共有である。** ホスト直結の NVMe (インスタンスストア) は最速だが、インスタンスの停止・故障・移動とともにデータが消える。つまり計算と記憶が運命共同体になる。EBS はネットワーク越しのレイテンシ税を払う代わりに、ボリュームの寿命をインスタンスから独立させ、付け替え (別インスタンスへの attach)・停止/再開・インスタンスタイプ変更・AZ 内での計算の自由な再配置を可能にする。**クラウドの運用モデル (イミュータブルな計算＋永続する記憶) は、この故障ドメイン分離の帰結**であり、Aurora の計算と記憶の分離 ([`cloud-databases-aurora-dynamodb.md`](cloud-databases-aurora-dynamodb.md)) は同じ原理をデータベースの粒度で反復したものである。

7. **耐久性は等級化された商品であり、等級の実体は複製戦略である。** 標準ボリュームと高耐久ボリューム (io2 型) の年間故障率の差（ベンダー提示の設計目標値）は、レプリカ数・配置・修復速度の構成差から来る。[`../../foundations/mathematics/probability-statistics/reliability-theory.md`](../../foundations/mathematics/probability-statistics/reliability-theory.md) の語彙で言えば、AFR と MTTR の掛け算を製品ラインごとに変えて売っている。耐久性がハードウェアの性質ではなく**設計パラメータの選択**であることを、価格表がそのまま示している。なお AZ 内複製である以上、AZ 全損はボリュームの故障モードに含まれる。AZ を跨ぐ耐久性はスナップショット (S3 側の複製) が担うという責任分界が、契約の重要な但し書きである。

## アーキテクチャ (Architecture)

### 貫通経路 — ゲストの write がディスクに落ちるまで

```
 ┌─ EC2 ホスト ──────────────────────────┐
 │  Guest OS                             │
 │   └ NVMe ドライバ (ボリューム=1 デバイス) │      [`../operating-systems/block-io-stack.md`]
 │      │ NVMe キュー (ハードウェア直通)     │
 │  ┌───▼───────────────┐                │
 │  │ Nitro カード        │ ホスト CPU を   │
 │  │  NVMe 終端・暗号化   │ 経由しない      │
 │  │  SRD トランスポート  │                │
 │  └───┬───────────────┘                │
 └──────┼────────────────────────────────┘
        │ AZ 内ネットワーク (マルチパス)
        ▼
   ┌─ ボリュームのレプリカ群 (同一 AZ 内・強一貫複製) ─────────┐
   │   replica A ──▶ replica B   (チェーン型: 全レプリカ書込後 ack) │
   └───────────────┬──────────────────────────────────────┘
                   │ 故障時のみ: 「正しい構成はどれか」を照会
                   ▼
        ┌──────────────────────┐          ┌──────────────┐
        │ Physalia セル         │          │ S3            │
        │ (ボリューム毎の合意)    │          │ スナップショット │◀─ 増分チャンク
        └──────────────────────┘          └──────────────┘
          コントロールプレーン                バックアップ平面
```

- 平時のデータ経路に合意も索引照会もない。構成が安定している限り、レプリカへの直行だけで完結する。構成ストアが要るのは**故障・移行の時点だけ**であり、その時点で確実に応えられるように Physalia の設計全体が組まれている。
- 暗号化は Nitro カード上で行われ、鍵はボリューム単位（KMS エンベロープ）。ゲストにもストレージサーバにも平文鍵の常駐を強いない位置に暗号化点が置かれている。

### 対比表 — 記憶の抽象の分業

| 軸 | インスタンスストア | EBS 型ブロック | S3 型オブジェクト |
|---|---|---|---|
| 契約 | ローカルディスク意味論 | ローカルディスク意味論 (ネットワーク越し) | PUT/GET, 結果整合→強一貫 |
| レイテンシ | 数十〜百 µs | サブ ms〜ms | ms〜数十 ms |
| 寿命 | インスタンスと同一 | インスタンスから独立 (AZ 内) | リージョン級・11 ナイン |
| 共有 | 不可 | 原則 1 ライター | 無制限の読者・書き手 |
| スケール | ホスト内 | ボリューム単位 (垂直上限あり) | 事実上無限 (水平) |
| 典型役割 | 一時領域・キャッシュ | DB のデータ領域・ルートボリューム | 永続の最終地・バックアップ |

## 技術詳細 (Technical Details)

### 1. チェーン複製の力学

チェーン複製では、更新は head で受理され鎖を順に流れ、**tail が ack した時点で全レプリカが持つ**ことが保証される。そのため、読み取りを tail に限定すれば、追加の調整なしに線形化可能性 (linearizability) が出る（[`../distributed-systems/consistency-models.md`](../distributed-systems/consistency-models.md)）。クォーラム系より読みが安く、スループットはパイプライン化で伸びる。代償は 2 つ：(a) レイテンシが鎖長に比例する（ゆえに実装は 2〜3 レプリカの短い鎖を使う）、(b) 故障時に鎖の再構成が必要で、その間書き込みが止まる。再構成の正しさ（新旧構成の混在で 2 つの「正」が生まれない事）は外部の構成マスタの合意に依存し、EBS ではこれが Physalia の仕事である。「データ複製は合意なしで速く、メンバーシップだけ合意で守る」という分業は、Aurora のエポック式構成変更 ([`cloud-databases-aurora-dynamodb.md`](cloud-databases-aurora-dynamodb.md)) と同じ判断の別実装である。

### 2. 再ミラーリングの嵐の解剖 (2011-04, US-East)

公式ポストモーテムの記述を機構として整理すると：(1) 定常時、各ボリュームはレプリカペアを保ち、片方を失うと即座に新しいミラー先を探して**再ミラー (re-mirror)** する。(2) 誤ったネットワーク変更で主経路の複製トラフィックが低容量の副経路へ流れ、輻輳で**多数のペアが同時に切断**された。(3) 復旧後、大量ボリュームが一斉に再ミラー先を探索した。その結果、空き容量が枯渇し、見つからないボリュームは探索を再試行し続けた (「stuck」状態)。(4) この探索・再試行の負荷が EBS 制御プレーンを飽和させ、AZ を越えて API 全体が劣化した。教訓は普遍である：**復旧動作こそ最大の負荷源になりうる** (修復の同時多発は平時に存在しない負荷パターン)、**再試行は総量制御がなければ嵐になる**、**制御プレーンの共有は障害の越境経路になる**。Physalia のセル化・近接配置、AZ 単位の制御プレーン分離、容量ヘッドルームの常備は、この 4 段の各々への直接の対策として読める。

### 3. スナップショットの参照構造

スナップショットの実体は「ブロック範囲 → S3 上のチャンクオブジェクト」の参照表である。スナップショット S1 以後に変更されたブロックだけが新チャンクとして書かれ、S2 の参照表は未変更部分について S1 と同じチャンクを指す。この構造の含意：(a) 削除はチャンクの参照カウント減算であり、どの順で消しても残りは完全なまま、(b) 復元・別 AZ/リージョンへのコピーはチャンク集合の転送であり、AZ 障害に対する耐久性の実体はここで S3 の複製 ([`../object-storage/object-storage-architecture.md`](../object-storage/object-storage-architecture.md)) に引き継がれる、(c) AMI (マシンイメージ) はルートボリュームのスナップショット＋メタデータであり、「イメージからの起動」は lazy restore されたボリュームからのブートに他ならない。起動直後のディスクが遅い（初回読み取りは S3 からのページイン）のは、この機構が外から観測できる形で現れたものである。

### 4. レイテンシ戦線 — SRD と Nitro オフロード

ブロック I/O のレイテンシ床はネットワークにあるため、改善はトランスポートに向かう。SRD (Scalable Reliable Datagram, IEEE Micro 2020) は、(a) データセンターの Clos ファブリック ([`../../engineering/datacenters/datacenter-fundamentals.md`](../../engineering/datacenters/datacenter-fundamentals.md)) を前提に**多数の経路へ同時にスプレー**し、(b) パケット順序保証を捨てて (順序はブロック層の上で回復) 再送を高速化し、(c) 輻輳制御をハードウェア (Nitro カード) に実装する。これは、TCP が汎用性のために払う税（単一経路・厳密順序・OS スタック）を、閉じたファブリックを前提にすべて返上した設計である。EBS の高性能ボリューム (io2 Block Express 型) はこの上に NVMe 終端までカードへ収め、ゲストから見た「ローカル NVMe との差」をサブミリ秒域まで圧縮する（ベンダー実証値）。[`../networking/tcp-transport-congestion.md`](../networking/tcp-transport-congestion.md) の輻輳制御の一般論に対する、「環境を限定すれば前提から作り直せる」という対照実験でもある。

### 5. ボリュームの垂直限界とその先

1 本のボリュームには容量・IOPS の上限があり、それを超える要求はストライピング (RAID 0 相当をゲストで組む)・シャーディング・あるいは設計の変更 (DB なら [`cloud-databases-aurora-dynamodb.md`](cloud-databases-aurora-dynamodb.md) の分散側へ) で吸収する。ここには明確な設計思想が読める：**ブロックデバイスという抽象は単一ライターの垂直スケールに最適化されており、水平スケールが要る時点で抽象ごと乗り換えるべき**である。1 つの抽象に両方を約束させると [`../object-storage/object-storage-architecture.md`](../object-storage/object-storage-architecture.md) が捨てた複雑さ (分散 POSIX) が戻ってきてしまう。クラウドのストレージ製品群が「用途別の抽象の品揃え」になっているのは、単一の万能ストレージの否定という設計判断そのものである。

## セキュリティ考察 (Security Considerations)

- **公開スナップショットは古典的な漏えい経路である**: スナップショットはアカウント間で共有でき、「公開」設定も存在する。公開スナップショットを走査して鍵・資格情報・個人情報を回収できることは独立研究 (DEF CON 27) が実証しており、原因は常に共有設定の誤りである。対策は [`cloud-iam-authorization.md`](cloud-iam-authorization.md) の議論と同型であり、機械検証（公開リソースの継続監査）と、アカウント全体でのブロック設定（公開共有の一括禁止）というガードレールに収束する。
- **attach 権限はデータアクセス権限である**: ボリューム・スナップショットへの IAM 上の操作権限 (attach, snapshot 作成, 共有変更) は、ファイルシステム層の権限を全て迂回してデータへ到達する。ブロック層はゲスト OS のアクセス制御より**下**にあり、「インスタンスに入れないから安全」は成立しない。暗号化 (KMS) はこの経路への第二の柵であり、スナップショット共有時にも鍵への grant が別途必要になる。データの移動と鍵の移動を分離する設計が、共有誤設定の被害を止める最後の防衛線になる。
- **暗号化点の位置が信頼境界を決める**: 暗号化が Nitro カード上で行われるため、ストレージサーバ・ネットワーク経路・ストレージ運用者は平文に触れない。ボリューム鍵は KMS のエンベロープ構造で保護され、鍵の無効化がボリュームの実質的なリモート消去 (crypto-erase) として機能する。テナント側から見ると「物理メディアの廃棄を信頼する」必要が消え、[`../../hardware/security/side-channels-tee-secure-boot.md`](../../hardware/security/side-channels-tee-secure-boot.md) が扱う「インフラ運用者を信頼モデルから外す」潮流の一部を成す。
- **共有ストレージフリートのテナント隔離**: ボリュームは共有サーバ群にストライプされるため、隔離は (a) 仮想化層のアドレス変換 (他ボリュームのブロックは名指しできない)、(b) テナント毎の暗号鍵、(c) IOPS のアドミッション制御 (noisy neighbor 対策、[`cloud-control-planes.md`](cloud-control-planes.md)) の三層で担保される。性能隔離の破れ (隣人の負荷でレイテンシが揺れる) はセキュリティ境界の破れではないが、サイドチャネル (アクセスパターンのタイミング観測) の理論的な入口ではあり、専有オプションが最終的な緩和である点は計算側と同じ構図である。

## 結論 (Conclusions)

- ブロックストレージは「意味論を守り、スケールを絞る」という、オブジェクトストレージと正反対の取引で成立している。両者は競合ではなく分業であり、スナップショットという橋 (ブロックの時間軸をオブジェクトへ射影する) が 2 つの世界を接続する。
- 強一貫複製の難しさはデータ経路ではなく構成管理に凝縮される。「データは単純なプロトコルで速く流し、構成の合意は小さく別置きする」という分業は、EBS (チェーン + Physalia)、Aurora (LSN 水位線 + エポック構成変更) に共通する、クラウドストレージの基本形である。
- 2011 年の再ミラーリングの嵐は、単なる障害事例ではなく設計思想の転換点である。復旧動作の総量制御・制御プレーンの分割・静的安定性という現代クラウドの原則は、この種の事故からの帰納であり、[`cloud-control-planes.md`](cloud-control-planes.md) の理論編と本書の事例が対を成す。
- 「計算と記憶の故障ドメイン分離」がこの製品の本体である。レイテンシでは常にローカル NVMe に負けるにもかかわらずクラウドの既定がネットワークストレージであるのは、速度より**運用モデル (イミュータブルな計算・永続する記憶・自由な再配置)** が買われているからであり、同じ分離が上の層 (Aurora, [`serverless-faas-internals.md`](serverless-faas-internals.md) の状態外部化) で繰り返される。クラウドの設計パターンは少数であり、層を変えて何度も再演される。
