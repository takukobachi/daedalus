# イベント駆動アーキテクチャとワークフロー (Event-Driven Architecture: Queues, Sagas & Workflow Orchestration)

## 概要 (Overview)

**イベント駆動アーキテクチャ (event-driven architecture)** の商品は「疎結合」という曖昧な美徳ではない。売っているのは**時間的独立 (temporal decoupling)** である。送信側は受信側が今稼働しているか・速いか・混んでいるかを知らずに送れ、受信側は自分のペースで処理できる。キューはこの独立を実現する速度差の吸収体であり、[`cloud-control-planes.md`](cloud-control-planes.md) の語彙で言えば「バックプレッシャの物質化」である。SQS・SNS・EventBridge・Kinesis、そして Step Functions は、この独立の異なる形 (仕事の分配・通知の拡散・ルーティング・再生可能な履歴・明示的な状態機械) を製品化したものだ。

代金も明確である。時間的独立を買った時点で、**分散トランザクションは失われる**。複数サービスに跨る「全部成功か全部失敗か」は、ロックを持ったまま他者を待つことを意味し、時間的独立と論理的に両立しない。ゆえにイベント駆動の実務は、Pat Helland が定式化した規律 (CIDR '07) の上に立つ：**at-least-once 配送を受け入れ、受信側を冪等にし、原子性は saga (補償の連鎖, SIGMOD '87) で近似する**。重複・順序逆転・部分失敗は異常系ではなく正常系であり、それを前提に正しさを組み立てる技法 (冪等受信・outbox・DLQ・オーケストレーション) が本ドキュメントの主題である。[`../messaging/distributed-logs-delivery-semantics.md`](../messaging/distributed-logs-delivery-semantics.md) が配送意味論の一般理論を扱ったのに対し、本書はその理論が AWS の製品群と設計パターンにどう着地するかを読む。分析深度は Level 3。

## 方法論 (Methodology)

- 配送保証 (at-most/at-least/exactly-once)・順序・ログの理論は [`../messaging/distributed-logs-delivery-semantics.md`](../messaging/distributed-logs-delivery-semantics.md) に依拠し、本書では再導出しない。
- 4 つの抽象 (キュー・トピック・イベントバス・ログ) を「誰が読むか・いつまで残るか・順序は誰に約束されるか」の 3 軸で分類し、製品はその座標上の点として扱う。
- 理論の一次資料は saga の原典 (Garcia-Molina & Salem 1987)、Helland の一連の定式化 (CIDR '07, ACM Queue 2012)、状態機械型ワークフローの学術的対応物 (Durable Functions, OOPSLA '21)。AWS 製品の意味論はベンダー文書 (SQS/EventBridge/Step Functions の**ベンダー一次資料**) に依る。

## 発見事項 (Findings)

1. **キューの本体は速度差の吸収であり、その容量は「時間の借金」である。** 生産者と消費者の瞬間速度は一致しない。キューは差分を在庫として持ち、両者を独立にスケールさせる。ただし在庫は遅延そのものであり (Little の法則: 滞留 = 到着率 × 待ち時間, [`../../foundations/mathematics/probability-statistics/markov-chains-queueing.md`](../../foundations/mathematics/probability-statistics/markov-chains-queueing.md))、無限に溜まるキューは「いつか誰も待っていない仕事を処理する系」になる ([`cloud-control-planes.md`](cloud-control-planes.md) のバックログ論)。ゆえに実務のキューには必ず**上限と溢れの設計** (最大保持期間・DLQ・負荷制限) が要る。キューは障害の吸収体であって、容量計画の代替ではない。

2. **4 つの抽象は「読み手の数」と「記憶の長さ」で直交に分類できる。** (a) **キュー** (SQS 型): 競合消費。1 メッセージは 1 消費者が処理し、消えれば終わり。仕事の分配。(b) **トピック** (SNS 型): ファンアウト。全購読者へ複製し、届けば終わり。通知の拡散。(c) **イベントバス** (EventBridge 型): 内容ベースルーティング。ルール (パターンマッチ) が宛先を決める。組織内・SaaS 間の配電盤。(d) **ログ** (Kinesis/Kafka 型): 追記され、読んでも消えず、**過去へ巻き戻せる**。読み手ごとの独立な進行 (オフセット) と再生 (replay)。前三者は「配ったら忘れる」、ログだけが「記録し続ける」。そのため、再処理・遅延参加・複数の独立した読者が要件に入れば、答えはログ側に決まる ([`../messaging/distributed-logs-delivery-semantics.md`](../messaging/distributed-logs-delivery-semantics.md))。

3. **Exactly-once は端から端では買えない。買えるのは「at-least-once + 冪等な受信」だけである。** 配送の重複は、ack の喪失という物理 (受信側は処理したが、その報告が消えた) から必然に生まれる。SQS の可視性タイムアウト (処理中は隠し、ack がなければ再出現) はこの必然の実装であり、**重複と順序逆転は正常系**である。Helland の規律 (ACM Queue 2012) が実務の答えになる：受信側を冪等にすることである。具体的には、自然な冪等 (同じ値の上書き)、重複検出 (処理済み ID の記録)、条件付き適用 ([`cloud-databases-aurora-dynamodb.md`](cloud-databases-aurora-dynamodb.md) の条件付き書き込み) がある。FIFO キューの「順序と重複排除」も、パーティション (message group) 内・重複排除窓内という**スコープ付きの約束**であり、その代金はスループットの直列化である。グローバルな順序は分散系では常に高価である。

4. **分散トランザクションの代替は saga であり、原子性を「補償の連鎖」で近似する。** Garcia-Molina & Salem (1987) の saga は、長時間トランザクションを「各段はローカルにコミットし、途中失敗なら**補償トランザクション** (逆操作) を逆順に走らせる」形に分解する。予約→課金→発送が発送で失敗したら、返金し予約を取り消す。原子性 (途中状態が見えない) は失われ、**中間状態が観測される** (「予約済みだが未課金」を他者が見る) ため、中間状態を語彙として設計する (PENDING という状態を第一級にする) ことが saga 設計の実体である。補償不能な操作 (送ってしまったメール、[`infrastructure-as-code.md`](infrastructure-as-code.md) のロールバック不能と同型) は、順序で守る。つまり、補償できない段を最後に置く。

5. **オーケストレーションとコレオグラフィの対立は、K8s で見た「指揮者の有無」の再演である。** **コレオグラフィ** (イベント連鎖: 各サービスがイベントに反応して次のイベントを出す) は自律的でスケールするが、プロセス全体の因果がどこにも書かれていない。「注文処理の全体像」はログを横断して再構成するしかない ([`container-orchestration-kubernetes.md`](container-orchestration-kubernetes.md) の振り付けなし協調の代償と同一)。**オーケストレーション** (Step Functions 型: 状態機械が明示的に次を呼ぶ) は因果が一箇所に書かれ、タイムアウト・リトライ・補償を宣言でき、実行履歴がそのまま監査証跡になる。代償は中央の状態機械への結合と、その定義の変更管理である。実務の均衡は「**境界内 (1 つの業務プロセス) はオーケストレーション、境界間 (チーム・ドメインを跨ぐ) はイベント**」という二層に収束しつつある。

6. **ワークフローエンジンの本質は「実行状態の耐久化」であり、コードとして書くか状態機械として書くかは表現の問題である。** 数日かかるプロセス (人の承認待ち・外部応答待ち) をプロセスのメモリで待つことはできない。待ちのたびに状態を耐久ストアへ退避し、イベントで再開する必要がある。Step Functions はこれを明示的な状態機械 (JSON の遷移定義) として、Durable Functions (OOPSLA '21) は「普通のコードに見えるが、await のたびに履歴を記録し、再開時は**履歴の再生 (replay)** で状態を復元する」形で提供する。後者は使い慣れた言語で書ける代わりに、**コードが決定的でなければならない** (再生のたびに同じ経路を辿る必要があり、乱数・時刻・外部呼び出しはフレームワーク経由に縛られる) という新しい正しさの公理を課す。[`serverless-faas-internals.md`](serverless-faas-internals.md) のスナップショット安全性と同族の、「再実行される前提のコード」という規律である。

7. **「DB 更新とイベント発行」の二重書き込みは整合性を失う。outbox が答えであり、これは「ログこそデータベース」の再演である。** 注文を DB に書き、続けてイベントを発行する。この 2 操作の間で落ちれば、DB とイベントの世界が食い違う (dual write 問題)。原子性はどちらか一方のシステムの中でしか買えないので、答えは**イベントを DB の同一トランザクションで outbox テーブルに書き、別プロセスが outbox を読んで配送する** (または CDC で WAL から直接イベントを起こす。これは [`data-lakehouse-analytics.md`](data-lakehouse-analytics.md) の CDC と同じ機構である)。イベントは「DB の変更ログの投影」になり、[`cloud-databases-aurora-dynamodb.md`](cloud-databases-aurora-dynamodb.md) の「ログこそデータベース」がアプリケーション統合の層で三たび現れる。DynamoDB Streams のような「テーブル自身が変更ストリームを吐く」機能は、outbox をプラットフォーム側が内蔵した形である。

## アーキテクチャ (Architecture)

### 4 つの抽象の座標

```
                 読み手の数
                 1 (競合消費)                N (独立購読)
        ┌──────────────────────┬──────────────────────────┐
 配ったら │ キュー (SQS)          │ トピック (SNS)             │
 忘れる   │  仕事の分配・負荷平準化 │  通知のファンアウト          │
        │                      │ イベントバス (EventBridge)  │
        │                      │  ルールによる内容ルーティング  │
        ├──────────────────────┼──────────────────────────┤
 記録し  │ (FIFO キュー:         │ ログ (Kinesis/Kafka)       │
 続ける  │  グループ内順序)       │  巻き戻し・再生・遅延参加     │
        └──────────────────────┴──────────────────────────┘
  典型構成: SNS/EventBridge (拡散) → 各購読者の前に SQS (吸収) → 消費者
  = 「通知の拡散」と「速度差の吸収」を別の抽象に分担させる定石
```

## 技術詳細 (Technical Details)

### 1. 可視性タイムアウトの力学と冪等受信の実装

SQS の受信は「削除」ではなく「一定時間の不可視化」である。消費者が処理を終えて明示的に削除しない限り、メッセージはタイムアウト後に再出現する。ここから実務の三角形が決まる：タイムアウトが処理時間より短ければ**処理中の重複**が起き、長ければ**障害時の再処理が遅れる**。ハートビート (処理中のタイムアウト延長) が中間解になる。冪等受信の実装は 3 段の強度がある：(a) 操作自体が冪等 (set 型の上書き)、(b) 冪等キーを使い、イベント ID を処理済みテーブルに条件付き書き込みし、勝った場合だけ処理する (重複検出の窓は保持期間との相談)、(c) 状態機械的検証、すなわち「この注文は PENDING のときだけ課金する」という状態遷移ガード (重複しても遷移条件が二度目を弾く)。(c) が最も頑健である。重複だけでなく、順序逆転・古いイベントの再配送にも同じガードが働くからである。

### 2. EventBridge 型バスの位置——組織の配電盤

イベントバスの差別化は配送ではなくルーティングにある：イベントの内容 (JSON パターン) に対する宣言的ルールが宛先 (Lambda・SQS・API・別バス) を決める。設計上の含意は 2 つ。(a) **送信側は宛先を知らない**。宛先の追加はルールの追加であり、送信側の変更ゼロで購読者が増える。組織のドメイン間結合が「イベントのスキーマ」だけに縮退する。(b) ゆえに**スキーマが公開 API になる**。スキーマレジストリと互換性規律 (後方互換な追加のみ・破壊的変更は新バージョンのイベント) が、サービス間の API バージョニングと同じ重みを持つ。イベントの命名も設計である。「注文が作成された」(事実の通知) と「課金せよ」(命令の委譲) は同じ配管に流れるが、責務の置き場所が逆であり、事実通知型のほうが送信側の中立性を保つ (命令型は宛先を知る結合の再導入である)。

### 3. Step Functions の実行モデルと標準/Express の二相

状態機械の各遷移は耐久ストアに記録され、失敗時は記録済みの位置から再開する。[`container-orchestration-kubernetes.md`](container-orchestration-kubernetes.md) の「記録が真実」の原則がワークフローの粒度で再演される。設計上の要点：(a) **リトライとタイムアウトの宣言**が各状態に付き、[`cloud-control-planes.md`](cloud-control-planes.md) のリトライ規律 (バックオフ・上限) を宣言的に埋め込める、(b) コールバックパターン (トークンを外部に渡し、応答イベントで再開) が「人間の承認待ち・外部システム待ち」を数日単位で耐久化する、(c) 標準ワークフロー (厳密な 1 回実行の記録・低頻度長時間向け) と Express (高頻度短時間・at-least-once) の二相は、**耐久化の粒度と単価の交換**であり、課金モデル (遷移課金 vs 実行時間課金) がそのまま実装の違いを映す (ベンダー仕様)。ワークフロー定義は IaC ([`infrastructure-as-code.md`](infrastructure-as-code.md)) の管理対象であり、「業務プロセスの変更がコードレビューを通る」というガバナンス上の副産物は、状態機械型を選ぶ実務的理由の中で過小評価されがちな一つである。

### 4. DLQ・毒メッセージ・再処理の運用

処理が恒常的に失敗するメッセージ (毒, poison pill) を放置すると、リトライが消費能力を使い尽くし、後続の正常なメッセージを道連れにする。これは [`cloud-control-planes.md`](cloud-control-planes.md) の毒テナント問題のメッセージ版である。**DLQ (dead-letter queue)** は「N 回失敗したら隔離する」という宣言的な検疫であり、設計の要点は隔離後にある：(a) DLQ は監視対象である (溜まる DLQ は気づかれにくい障害)、(b) 再処理 (redrive) の前に原因を分類する。一時障害 (依存先のダウン) なら一括再投入、恒久欠陥 (パースできないスキーマ) なら修正後に再投入、真の毒 (不正データ) なら破棄と上流修正。(c) 順序付きストリーム (Kinesis 型) では毒の意味論が変わる。シャード内順序を守る限り毒を追い越せず、**1 つの毒がシャード全体を止める** (head-of-line blocking)。バイパス (毒だけ DLQ へ逃して続行) は順序保証の意図的な破棄であり、順序が本当に必要かの再確認を迫る。ここでも保証の強さと可用性の交換が現れる。

### 5. パターンの合成——イベントソーシングとの距離

outbox (発見事項 7) の先には、**イベントソーシング** (状態そのものを持たず、イベント列を唯一の記録とし、状態は畳み込みで導出する) がある。ログこそデータベースの純粋形だが、実務の採用は限定的である：スキーマ進化 (過去イベントの読み替え)、スナップショット (畳み込みの高速化)、削除義務 ([`data-lakehouse-analytics.md`](data-lakehouse-analytics.md) の不変性と消去の衝突) という運用課題が重い。多くのシステムの均衡点は「**現在状態は DB、変更の事実は outbox/CDC 経由のイベント**」という混成であり、状態の問い合わせは DB の得意、統合と履歴はログの得意、と役割を分けた形である。パターンは階段状に採用できる：dual write の排除 (outbox) → 統合のイベント化 (バス) → プロセスの明示化 (saga/オーケストレーション) → 必要な集約だけイベントソーシング、と進む。一段ごとに複雑さの対価を確認しながら登るのが、経験則としての安全経路である。

## セキュリティ考察 (Security Considerations)

- **イベントは認可の間接層を作り、「誰が引き金を引いたか」が薄まる。** 同期 API では呼び出し元の資格情報が [`cloud-iam-authorization.md`](cloud-iam-authorization.md) の評価にそのまま乗るが、イベント経由では「バスに書けた者」の行為が「購読者の実行ロール」の権限で実行される。つまり、confused deputy の構造がアーキテクチャに内蔵される。防御は (a) バス・キューへの書き込み権限を資源ポリシーで厳密に絞る (誰がこのバスに置けるか)、(b) イベントに由来 (発生源・元 principal) を運び、購読者側で検証する、(c) 購読者の実行ロールを最小化する (イベント 1 種に必要な権限だけ)。
- **メッセージ本文は保存される秘密である。** キュー・ログの中身は暗号化 ([`cloud-kms-confidential-computing.md`](cloud-kms-confidential-computing.md)) の対象であり、保持期間はデータ保持ポリシーの対象である。「一時的な配管」という直感に反して、ログ型は特に長期の記録になる。個人データをイベントに載せる設計は、消去義務との衝突 (ログからの選択的削除は高価) を最初から抱える。そのため、イベントには識別子を載せ、実体は消去可能なストアに置く、という分離が定石になる。
- **DLQ は機微データの吹き溜まりになる。** 失敗したメッセージ (しばしば異常な・攻撃的な・パースできない入力) が集まる場所であり、アクセス制御と保持期間を本流と同等以上に扱う。再処理の経路 (redrive) も本流と同じ認可・検証を通し、「隔離からの復帰」を無審査の裏口にしない。
- **スキーマ検証は入力検証である。** 内容ベースルーティングとイベント処理は、外部由来のデータ構造をパースして分岐する行為であり、インジェクション・型混乱の入口になりうる。スキーマレジストリによる構造検証を「互換性管理」だけでなく「境界での入力検証」として位置づけ、購読者は「バスは信頼するがイベントは検証する」姿勢を既定にする。バスに書ける主体の集合は、時間とともに設計者の想定より広がるからである。

## 結論 (Conclusions)

- イベント駆動の取引は明確である：時間的独立を買い、分散トランザクションを手放す。その差額を埋める技術 (冪等受信・saga・outbox・DLQ) は場当たりの技巧ではなく、「重複・順序逆転・部分失敗は正常系である」という一つの前提からの体系的な演繹である。
- 抽象の選択は 2 軸で決まる：読み手の数 (分配か拡散か) と記憶の長さ (配ったら忘れるか、再生できるか)。そして調整の形がもう 1 軸であり、境界内はオーケストレーション (因果の明示)、境界間はイベント (自律性) となる。K8s で見た「指揮者の有無」のトレードオフが業務プロセスの層で再演される。
- 最も価値のある一行は outbox である：状態の変更とイベントの発行を 1 つのトランザクションに入れ、配送を変更ログの投影にする。「ログこそデータベース」は、ストレージ (Aurora)・分析 (CDC→レイクハウス)・統合 (outbox→バス) と、本領域で三度現れた。これはクラウド設計の少数パターンの再利用性の、最後の実証である。
- ワークフローの耐久化 (Step Functions/Durable Functions) は「待つことの外部化」であり、FaaS の状態外部化・スナップショット安全性と同じ系譜の規律 (決定性・再実行前提) を課す。プロセスの明示化は性能のためではなくガバナンスのため (因果が読め、履歴が残り、変更がレビューを通る) という評価軸で選ぶのが実務的である。
