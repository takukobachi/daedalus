# クラウドの可観測性 (Cloud Observability: Metrics Economics, Audit Trails & Telemetry as a Product)

## 概要 (Overview)

[`../observability/observability-performance-engineering.md`](../observability/observability-performance-engineering.md) は可観測性の一般理論（三つの信号 (メトリクス・ログ・トレース)、計装点、SLO、測定方法論）を扱った。本ドキュメントはその理論が**マネージドサービスとして製品化されたとき何が変わるか**を扱う。CloudWatch・CloudTrail・X-Ray を走る事例に、変わる点は 3 つある。

第一に、**計器がプラットフォームに内蔵される**。ハイパーバイザ・ロードバランサ・API ゲートウェイ・キューは、利用者が何も計装しなくても自らを計測して報告する。そのため、「アプリが自分について語る」内部計装に対して、「プラットフォームが外から見た真実」という第二の視点が無償で手に入り、両者の食い違い自体が診断情報になる。第二に、**課金がテレメトリの形を規定する**。メトリクスは時系列 (名前 × 次元の組合せ) 単位、ログは取り込みバイト単位で課金され、この価格構造は時系列データベースの物理 (カーディナリティがコストの支配項。Monarch VLDB '20, Gorilla VLDB '15) をそのまま利用者へ転嫁したものである。「何でも測る」は技術的にではなく経済的に破綻する。第三に、**監査と運用が別の系に分離される**。CloudTrail (誰が何をしたかの改竄困難な記録) と CloudWatch (系がどう振る舞ったかの集約) は、要求される性質（完全性・否認防止 vs 集約効率・低遅延）が異なるがゆえに別製品であり、この分離は [`cloud-iam-authorization.md`](cloud-iam-authorization.md) の認可アーキテクチャの観測面の続きとして読める。分析深度は Level 3。

## 方法論 (Methodology)

- 信号の一般論・計装技術・SLO 設計は [`../observability/observability-performance-engineering.md`](../observability/observability-performance-engineering.md) に委ね、本書は「マネージド化・課金・監査・自動化への接続」というクラウド固有の層に集中する。
- 時系列ストアの物理は査読付き論文 (Gorilla VLDB '15, Monarch VLDB '20)、分散トレーシングの系譜は Dapper (2010)、計装の標準化は OpenTelemetry 仕様 (CNCF。ベンダー中立の一次資料) に接地する。CloudWatch/CloudTrail の意味論はベンダー文書 (**ベンダー一次資料**) に依る。
- 課金構造を「実装コストの外部化」として読む。価格表から逆に内部実装を推定する手法は [`spot-capacity-economics.md`](spot-capacity-economics.md) と同じ姿勢である。

## 発見事項 (Findings)

1. **外形計測 (プラットフォーム視点) と内部計装 (アプリ視点) は別の真実であり、食い違いが最良の診断情報である。** ロードバランサが記録するレイテンシはキュー待ち・TLS・再送を含む「利用者が体感した時間」、アプリが記録するのは「ハンドラが走った時間」であり、両者の差は、アプリの外 (接続受理・GC 停止・ホストの steal time) で失われた時間の直接測定になる。クラウドの標準メトリクス (agent 不要・改竄不能・課金と同じデータ源) は前者を無償で提供し、[`serverless-faas-internals.md`](serverless-faas-internals.md) の外形測定 (ATC '18) が研究手法として使った「外から見る」を、運用の既定装備にした。**まず外形で異常の存在を確定し、内部で原因を絞る**。この順序が、計装の穴や自己申告バイアス ([`../observability/observability-performance-engineering.md`](../observability/observability-performance-engineering.md) の楽観バイアス) に騙されない実務の型である。

2. **メトリクスの敵はカーディナリティであり、課金はその物理の正直な転嫁である。** 時系列ストアの支配コストは点の数ではなく**系列の数** (メトリクス名 × 次元値の組合せ) である。Gorilla (VLDB '15) の差分圧縮は点を数バイトに圧縮するが、系列ごとのインデックス・メモリ常駐は減らせず、Monarch (VLDB '20) の設計もカーディナリティ管理 (集約の事前定義・系列の階層集約) を中核に置く。CloudWatch がカスタムメトリクスを「ユニークな時系列単位」で課金するのは、この物理の価格化である。実務の帰結：**ユーザ ID・リクエスト ID を次元にしてはならない** (無限カーディナリティ)。個体を識別したい問いはログ・トレース (行単位課金の信号) へ、集合の傾向はメトリクス (系列単位課金) へ振り分ける。この**問いの種類で信号を選ぶ**という規律は、快適さではなく請求書が強制する。

3. **三つの信号は相互変換可能であり、単価の差が変換の方向を決める。** 構造化ログからメトリクスを抽出する (メトリクスフィルタ・EMF: ログとして書き、メトリクスとして集計される埋め込み形式)、トレースからレイテンシ分布を導出する、メトリクスの異常からログ・トレースへ掘る。このように信号は独立の三本柱ではなく、**同じ事実の異なる圧縮**である。設計指針もここから出る：最も情報量の多い形 (構造化イベント) で一度だけ記録し、安い集約 (メトリクス) は導出する。逆方向 (集約から個別を復元) は不可能なので、「何を残すか」の決定だけが不可逆である。[`data-lakehouse-analytics.md`](data-lakehouse-analytics.md) の語彙で言えば、テレメトリもまた「ログ (事実) からの導出データ」の体系であり、実際に S3 へのエクスポート + Athena という分析基盤との合流が標準経路になっている。

4. **監査 (CloudTrail) と運用 (CloudWatch) の分離は、要求性質の分離である。** 監査記録に要るのは完全性 (取りこぼさない)・改竄困難性・長期保全・法的証拠能力であり、集約効率や低遅延は二の次である。CloudTrail が全 API 呼び出し ([`cloud-iam-authorization.md`](cloud-iam-authorization.md) の認可判定と同じ粒度) を記録し、組織トレイルとして**別アカウントの書き込み専用バケットへ**送られるのは、[`multi-region-global-architecture.md`](multi-region-global-architecture.md) の隔離バックアップと同じ「攻撃者が消せない場所」の設計である。運用観測に要るのは逆に集約・サンプリング・短期高解像度であり、完全性は要らない (1% のメトリクス欠落は運用上無害、監査上は致命的)。この 2 系を 1 つのパイプラインで賄おうとする設計は、どちらかの要求を気づかないうちに損なう。

5. **アラームは「観測に基づく状態機械」であり、欠損データの意味論が設計の急所である。** CloudWatch アラームは OK/ALARM に加えて**データ不足 (INSUFFICIENT_DATA)** という第三状態を持ち、欠損をどう扱うか (breaching/notBreaching/ignore/missing) を宣言させる。これは観測系における fail-open / fail-closed の選択そのものである。「データが来ない」は「正常」ではない。計測対象の障害はしばしば**テレメトリの停止として**現れる (ホストごと落ちればエラーメトリクスは上がらず、消える)。ゆえに heartbeat 型の監視 (来るはずのものが来ない事を検知) と、[`cloud-control-planes.md`](cloud-control-planes.md) の一定作業パターン (テレメトリ量を負荷と無関係に一定へ) が、欠損の曖昧さを消す側の設計になる。

6. **アラーム→イベント→自動化の配線は、可観測性を調停ループの感覚器に変える。** アラーム状態遷移は EventBridge ([`event-driven-architecture.md`](event-driven-architecture.md)) のイベントとして流れ、オートスケーリング・自動復旧・チケット起票へ配線される。こうして観測は「人間に見せる計器盤」から「機械が読む感覚器」へ役割を広げる。ここには [`cloud-control-planes.md`](cloud-control-planes.md) の警告がそのまま適用される：観測に基づく自動化はフィードバックループであり、遅延したメトリクス × 積極的な自動化は発振する (HPA のばたつきと同型)。自動化の入力にするメトリクスには、人間が見るダッシュボード以上の品質規律（遅延の把握・欠損の意味論・単調性）が要る。

7. **OpenTelemetry の標準化は「計装の脱ベンダー化」であり、レイクハウスと同じ構図の開放である。** 計装 (SDK・自動計装・collector) が OTel というベンダー中立仕様に収束したことで、「どう測るか」と「どこに送り・どう分析するか」が分離した。テレメトリのフォーマットがオープンになり、バックエンド (CloudWatch・X-Ray・サードパーティ・自前) が交換可能な競争層になる。[`data-lakehouse-analytics.md`](data-lakehouse-analytics.md) で見た「オープンフォーマットがエンジンを競争にさらす」の観測版であり、「データはエンジンより長生きする」に対応する教訓は「**計装コードはバックエンドより長生きする**」である。計装は書き直しコストが最も高い資産であり、そこを標準に載せることが可搬性投資の要諦である。

## アーキテクチャ (Architecture)

### 二重の視点と信号の変換経路

```
              利用者のリクエスト
                   │
 ┌─ プラットフォームの計器 (外形・agent 不要) ──────────────────┐
 │  LB のレイテンシ/エラー ・ API GW ・ キュー深さ ・ Lambda 実行  │──┐
 │  ハイパーバイザの CPU/ネットワーク (課金と同じデータ源)         │  │
 └──────────────────────────────────────────────────────────┘  │
                   │ (アプリの外で失われた時間 = 両者の差)          │
 ┌─ アプリの計装 (内部・OTel SDK/collector) ────────────────────┐  │
 │  構造化ログ ──(メトリクスフィルタ/EMF)──▶ メトリクス            │  ▼
 │      │                                   │            ┌─────────┐
 │      └──(trace id で結合)──▶ トレース      ├───────────▶│ アラーム  │
 └──────────────────────────────────────────┼────────────│(状態機械) │
                    長期保存・分析へ:          │            └────┬────┘
                    S3 エクスポート → Athena ◀─┘                 │ 状態遷移イベント
                    (レイクハウスと合流)                          ▼
                                                    EventBridge → 自動化/通知
 ── 別系統 (監査) ──────────────────────────────────────────────────
 CloudTrail: 全 API 呼び出し → 別アカウントの書き込み専用ストアへ (完全性・改竄困難)
```

### 信号の経済 — 問いと単価の対応

| 信号 | 課金の単位 | 得意な問い | カーディナリティ耐性 |
|---|---|---|---|
| メトリクス | ユニーク時系列数 | 集合の傾向・閾値・SLO | 低 (次元爆発が破綻点) |
| ログ | 取り込み・保存バイト | 個別事象の事実確認 | 高 (行に何を書いてもよい) |
| トレース | サンプリングされた記録数 | 因果・区間の内訳 | 中 (サンプリングが前提) |
| 監査証跡 | 記録数 (完全記録) | 誰が・何を・いつ | 対象外 (完全性が要件) |

## 技術詳細 (Technical Details)

### 1. 時系列ストアの物理と次元設計

Gorilla (VLDB '15) は「直近数時間の時系列はメモリに置き、タイムスタンプは delta-of-delta、値は XOR 差分で圧縮する」ことで点あたり平均バイト級の格納を示した。つまり**点は安い**。一方、系列は名前解決のインデックス・メモリ上の状態・スキャン対象として残り続ける。つまり**系列は高い**。Monarch (VLDB '20) はさらに、収集時の事前集約 (クライアント側で分布に集約する)・階層的な集約木・クエリのプッシュダウンで「惑星規模のカーディナリティ」を管理する設計を示した。利用者側の次元設計の規律はこの物理から直接出る：次元は**有界な集合** (AZ・インスタンスタイプ・API 名・エラー種別) に限る、分布が欲しければ percentile を事前計算した集約 (あるいは分布型メトリクス) を使う、個体識別はトレース/ログの exemplar (メトリクスから代表トレースへのリンク) で橋渡しする。

### 2. トレーシングの系譜とサンプリングの二相

Dapper (2010) が確立した形（trace id の文脈伝播・スパン木・**サンプリング前提**）は OTel にそのまま継承されている。サンプリングの設計は二相ある：**head-based** (開始時に決める。安いが「面白い」リクエストを選べない) と **tail-based** (完了後に、遅い・失敗したものを優先して残す。選別できるが全スパンの一時バッファが要る = collector 側のコスト)。X-Ray 型のマネージドはこの選別と保存を製品化し、OTel collector は選別ロジックを利用者の管理下に置く。どちらでも、「100% 保存」はコスト構造上の例外 (短期・低トラフィック・デバッグ時) であり、**トレースは統計であってログではない**という前提が実務の出発点になる。サービスマップ (トレースから導出されるトポロジー) は、[`../networking/service-mesh.md`](../networking/service-mesh.md) のメッシュ計測と重なる領域であり、「どちらの層で測るか」は計装の所有権 (アプリチーム vs プラットフォームチーム) の問題として決まることが多い。

### 3. CloudTrail の意味論 — 監査ログの設計要件

CloudTrail のイベントは「認可判定を通った (または拒否された) API 呼び出し」の記録であり、principal・呼び出し元 (IP・user agent・経由サービス)・リクエストパラメータ・応答の要約を含む。これは [`cloud-iam-authorization.md`](cloud-iam-authorization.md) の「毎リクエスト認可」の裏面としての「毎リクエスト記録」である。設計要件は運用ログと逆転する：(a) **管理イベントは既定で記録** (オプトアウトさせない方向)、データイベント (S3 オブジェクト単位等) は量が桁違いなので選択制であり、完全性と経済の妥協点が「制御面は完全・データ面は選択」に引かれている、(b) 組織トレイルで**全アカウント分を集中** (メンバーアカウントの侵害者が自分の痕跡を消せない)、(c) ログファイルの完全性検証 (ハッシュ連鎖)。侵害調査の第一資料はほぼ常に CloudTrail であり、「攻撃者の最初の行動はログの無効化」という定石への対抗（停止操作自体の検知・SCP ([`cloud-iam-authorization.md`](cloud-iam-authorization.md)) による停止の禁止）までが監査設計に含まれる。

### 4. 保持の階層とコストの時間構造

テレメトリの価値は急速に減衰する (5 分前の p99 は運用の宝、5 ヶ月前のそれは統計) が、監査・コンプライアンス・キャパシティ計画は長期保持を要求する。その答えが温度階層である。高解像度メトリクスは自動で粗い解像度へロールアップされ (ベンダー仕様の保持段階)、ログは高価な検索可能ストアから S3 へエクスポートして Athena で読む ([`data-lakehouse-analytics.md`](data-lakehouse-analytics.md) との合流)、トレースは短期保持が既定。設計の規律は「**問いから逆算する**」ことである。「どの質問に、どの鮮度で、どの頻度で答える必要があるか」を列挙し、それぞれを最安の層に割り当てる。全部を検索可能に保つ構成は、[`../object-storage/object-storage-architecture.md`](../object-storage/object-storage-architecture.md) の温度階層を無視して全データを最上段に置くのと同じ過剰設計である。

### 5. クロスアカウントと組織の観測トポロジー

マルチアカウント戦略 ([`cloud-network-topology.md`](cloud-network-topology.md) の組織の写像) は観測にも写像される：各アカウントが自分のテレメトリを持ち、中央の観測アカウントへ集約する (クロスアカウント観測・メトリクスストリーム)。集中の理由は相関 (障害はアカウント境界を無視して伝播する) と専門化 (観測基盤チーム) であり、リスクは [`cloud-network-topology.md`](cloud-network-topology.md) の共有サービスと同じである。観測アカウントは全システムの内部が見える特権点であり、その侵害は偵察の宝庫になる。テレメトリに何を載せるかの規律 (次節) と、観測アカウント自体の防御 (最小の人間アクセス・強い認証) が対になる。

## セキュリティ考察 (Security Considerations)

- **テレメトリは機密の漏洩経路である。** ログへの秘密の混入 (認証ヘッダ・トークン・個人情報) は最頻の事故類型であり、防御は多層になる：構造化ログでのフィールド単位の設計 (自由文字列への例外メッセージ丸ごと出力が主犯)、収集パイプラインでのマスキング、そして「ログを読める権限」自体の管理である。観測基盤は事実上の全システム読み取り権限であり、[`cloud-iam-authorization.md`](cloud-iam-authorization.md) の最小権限がテレメトリの読み手にも適用される。[`infrastructure-as-code.md`](infrastructure-as-code.md) で見た「plan 出力のログ流出」はこの類型の一例である。
- **監査ログは攻撃の第一目標であり、隔離が防御である。** 痕跡の削除・記録の停止は侵害の標準手順であり、対抗は技術詳細 3 の通り「別アカウント・書き込み専用・停止禁止の SCP・完全性検証」であり、記録の経路と削除の権限を、侵害されうる環境から構造的に切り離す。ここでも「認可の誤りが単独で事故にならない独立の柵」([`cloud-network-topology.md`](cloud-network-topology.md)) の原則が働く。
- **可観測性は検知の基盤である (drift・異常・不変条件)。** 侵害の多くは「正規の資格情報による、いつもと違う行動」として現れ、外形メトリクスの異常 (深夜の大量読み出し・見知らぬリージョンの API)・CloudTrail のパターン (列挙系 API の連打)・IaC drift ([`infrastructure-as-code.md`](infrastructure-as-code.md)) がシグナルになる。運用のための計器と防御のための計器はデータ源を共有しており、分離すべきは (要求性質が異なる) 保存と権限であって、収集ではない。
- **観測の自動化は攻撃面でもある。** アラーム→自動修復の配線は、偽の入力 (メトリクスの汚染・イベントの偽造) で誤動作を誘発できる系である。自動化の入力となるイベントの発行元検証 ([`event-driven-architecture.md`](event-driven-architecture.md) のバス書き込み権限)、破壊的な自動修復 (インスタンス終了・切替) へのレートリミットと承認ゲートが、[`cloud-control-planes.md`](cloud-control-planes.md) の「復旧動作こそ最大の負荷源」のセキュリティ版として要る。

## 結論 (Conclusions)

- クラウドの可観測性の第一の特徴は「外形計測の内蔵」である。プラットフォームが見た真実を無償の基準線とし、内部計装との差分を診断に使う。計装の第一歩はコードを書くことではなく、既に測られているものを知ることである。
- 課金構造は嫌がらせではなく物理の転嫁である。系列単位のメトリクス課金・バイト単位のログ課金・サンプリング前提のトレースは、時系列ストアとインデックスの実装コストをそのまま映しており、「問いの種類で信号を選ぶ」規律を経済が強制する。最も不可逆な決定は「何を記録するか」であり、豊かな形で一度記録し、安い形は導出する。
- 監査と運用の分離、欠損の意味論、自動化ループの発振という形で、本領域の原則群 (隔離バックアップ・fail-open/closed・調停とフィードバック) が、観測というメタな層にもそのまま適用される。可観測性は系の外の傍観者ではなく、それ自体が設計対象の分散システムである。
- OTel への計装の標準化は、この層の最も戦略的な決定である。計装コードはバックエンドより長生きする。測り方をオープン仕様に載せ、送り先を交換可能に保つことが、レイクハウスの「データはエンジンより長生きする」と並ぶ、長期の可搬性投資になる。
