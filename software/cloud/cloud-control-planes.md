# クラウドのコントロールプレーン設計 (Cloud Control Plane Design: Cells, Shuffle Sharding & Static Stability)

## 概要 (Overview)

クラウドのあらゆるサービスは、**コントロールプレーン (control plane)**——リソースの作成・変更・削除という「状態を変える」系——と、**データプレーン (data plane)**——作られたリソースが実際に働き続ける系——の 2 つに割れる。EC2 ならインスタンス起動 API が前者、起動済みインスタンスが走り続けることが後者。この分離は実装の都合ではなく**可用性の非対称を工学的に作り出すための設計**である：データプレーンの停止は全顧客の本番停止だが、コントロールプレーンの停止は「新しい変更ができない」に留まる。ゆえにクラウドは「データプレーンはコントロールプレーンなしで走り続けられるか」を設計の第一審査項目に置く。

本ドキュメントの中心テーゼは、クラウドの信頼性パターン群——コントロール/データプレーン分離、**静的安定性 (static stability)**、**セルベースアーキテクチャ (cell-based architecture)**、**シャッフルシャーディング (shuffle sharding)**、ジッタ付きバックオフ、アドミッション制御——が、すべて **「相関の破壊」という単一の原理の異なる実装**だということである。分散システムの理論（[`../distributed-systems/`](../distributed-systems/)）は個々の故障を扱うが、大規模障害の実態は「多数の要素が**同時に・同じ理由で**壊れる/過負荷になる」という相関故障であり、上記パターンはそれぞれ空間（セル・シャード）、時間（ジッタ・一定作業）、因果（静的安定性・リトライ抑制）の軸で相関を切断する。AWS の公開設計文書 (Amazon Builders' Library) と査読付き論文 (Physalia NSDI '20, DynamoDB ATC '22, メタステーブル障害 HotOS '21) を突き合わせて機構を追う。分析深度は Level 3。

## 方法論 (Methodology)

- 各パターンを「どの軸の相関を切るか」で分類し、単発の tips 集ではなく一つの原理の系として整理する。
- **出典階層上の注意**: 信頼性パターンの多くは Amazon Builders' Library というベンダー自身の設計解説を通じて公開されている。これらは**ベンダー提示 (vendor-presented)** と明示し、査読付き論文 (NSDI/ATC/HotOS/OSDI) と独立系の障害研究（メタステーブル障害の実例調査 OSDI '22、Google SRE 本のカスケード障害章）で相互検証する。障害パターン自体は特定ベンダーに依存しない普遍構造なので、複数社の資料が同じ結論に達していること自体が傍証になる。
- 合意・複製・一貫性の語彙は [`../distributed-systems/consensus.md`](../distributed-systems/consensus.md) / [`consistency-models.md`](../distributed-systems/consistency-models.md) から借用し再導出しない。確率の議論は [`../../foundations/mathematics/probability-statistics/probability-random-variables.md`](../../foundations/mathematics/probability-statistics/probability-random-variables.md) の独立性・組合せの語彙で行う。

## 発見事項 (Findings)

1. **コントロール/データプレーン分離とは「変更する系」と「動き続ける系」の依存の向きを固定することである。** 分離の実体は、データプレーンがコントロールプレーンの出力（設定・ルーティング表・配置）を**ローカルに保持した最後の既知状態 (last known good)** で動き続けられること、すなわち障害時にコントロールプレーンへの同期呼び出しが存在しないことである。DNS の権威応答はゾーン変更 API が死んでいても返り続け、起動済みインスタンスは起動 API が死んでいても走り続ける。分離が破れている箇所（データプレーンが要求のたびに制御系を引く設計）が、そのまま大規模障害の伝播経路になる。

2. **静的安定性とは「障害のさなかに新しいことをしない」という原則である。** AZ 障害への正しい備えは「障害を検知してから容量を起動する」ことではなく、**残存 AZ で全負荷を吸収できる容量を平時から確保しておく**ことである（3 AZ なら各 AZ は定常負荷の 50% 増しを持ち、1 AZ 喪失を無操作で吸収する）。障害時のスケールアップはコントロールプレーン（それ自体が障害の影響下にありうる）への依存であり、最も容量が必要な瞬間に最も混雑する経路に賭けることになる。事前確保のコストは、障害時に制御系が完璧に動くという仮定を捨てるための保険料である（ベンダー提示, Builders' Library）。

3. **ブラストラディウス（爆発半径）は設計変数であり、Physalia はそれを座標にした実例である。** EBS の複製設定を保持する合意ストア Physalia (NSDI '20) は、巨大な単一の合意クラスタではなく、**ボリューム 1 本ごとに 7 ノードの小さな合意セル**を無数に作る。さらにセルの物理配置をクライアント（そのボリュームを使うインスタンス）の近くに置き、ネットワーク分断が起きても「クライアントとセルが同じ側に残る」確率を最大化する。可用性を系全体の平均ではなく「**各クライアントから見た自分のデータへの可用性**」として定義し直し、故障の影響を受けるペアの数を最小化する——ブラストラディウスの最小化を目的関数に昇格させた設計である。背景には 2011 年の EBS 大規模障害（制御系の過負荷が全リージョンへ波及）という実事故がある。

4. **シャッフルシャーディングは組合せ論で隔離を買う。** n 台のワーカーから各テナントに k 台の組（シャッフルシャード）をランダムに割り当てると、2 テナントが**完全に同じ組**を共有する確率は 1/C(n,k) に落ちる。n=8, k=2 で 28 分の 1、n=100, k=5 なら約 7,500 万分の 1。悪性の負荷（poison pill リクエスト、暴走テナント）が k 台を焼いても、完全一致シャードを持つテナント以外は少なくとも一部のワーカーが生きており、リトライで生きた側へ逃げられる。物理的には同じ台数のまま、**仮想的な隔離度だけが組合せ爆発で増える**——追加コストほぼゼロで「専有に近い隔離」を売る技術であり、Route 53 は 2048 の仮想ネームサーバから各ホストゾーンへ 4 つを割り当てる形でこれを実装している（ベンダー提示）。

5. **リトライは分散システム最大の増幅器であり、メタステーブル障害はその極限である。** 層をまたいでリトライが重なると、深さ d・各層リトライ数 r で最悪 r^d 倍に仕事が増幅される。過負荷 → タイムアウト → リトライ → さらなる過負荷という正帰還が閉じると、**トリガが除去された後も過負荷が自己維持する**——これがメタステーブル障害 (metastable failure, HotOS '21) であり、「再起動しないと直らない」大規模障害の多くがこの型である（実例調査 OSDI '22）。対策は正帰還の利得を 1 未満に保つこと：ジッタ付き指数バックオフ（時間軸の相関破壊）、リトライ予算（クライアント側トークンバケット）、デッドライン伝播、そして**先頭での拒否（アドミッション制御）は奥での崩壊より常に安い**という原則である。

6. **一定作業 (constant work) パターンは「負荷に比例する挙動」そのものを捨てる。** Route 53 のヘルスチェック集約は、変化があったときだけ差分を伝えるのではなく、**変化の有無にかかわらず全チェック結果の全表を固定周期でプッシュし続ける**（ベンダー提示, Builders' Library）。差分方式は平時に安く見えるが、大規模障害時——差分が最大になる瞬間——に未検証のコード経路と最大負荷が同時に来る。一定作業方式はコストが常に最悪ケースで一定であり、障害時の挙動が平時と同一になる。「動的な賢さ」を捨てて「退屈な予測可能性」を買う、静的安定性の時間軸版である。

7. **DynamoDB のアドミッション制御の変遷は、隔離と統計多重化の緊張の縮図である (ATC '22)。** 初期設計はテーブルのスループットをパーティションへ**静的に等分割**した——完全な隔離だが、アクセスが偏ると割当が実負荷と乖離し、顧客はホットパーティションのために全体を過剰プロビジョンさせられた。その後のバースト許容 → 適応容量 → **グローバルアドミッション制御 (GAC)**（リクエストルータ群がテーブル単位のトークンを中央サービスから借りる）への移行は、割当の単位を物理（パーティション）から論理（テーブル）へ引き上げ、隔離の保証を保ったまま多重化の効率を取り戻す過程である。クォータ・スロットリングは課金の道具ではなく、**マルチテナント系の安定性を守る本質的機構**だと分かる。

## アーキテクチャ (Architecture)

### 分離と依存の向き

```
            管理 API (低頻度・強い一貫性・複雑)
 Operator ──────────▶ ┌────────────────────────┐
                      │ Control Plane           │  望ましい状態 (desired state)
                      │  検証・記録・調停        │  を記録し、実状態との差分を
                      └───────────┬────────────┘  調停ループで埋める
                                  │ push (非同期・冪等・再送可能)
                                  ▼
                      ┌────────────────────────┐
 End users ─────────▶ │ Data Plane              │  受け取った構成の最後の既知状態
   (高頻度・単純)      │  (ローカル状態で自立動作) │  で、制御系なしで動き続ける
                      └────────────────────────┘

  依存の向きの規則: Data Plane → Control Plane の同期呼び出しを持たない。
  Control Plane の停止 = 「変更の凍結」であり「停止」ではない。
```

- 構成は「望ましい状態の宣言 + 調停ループ (reconciliation loop)」で伝播する。命令の逐次実行と違い、取りこぼしは次周期の全量比較で自己修復する（Kubernetes のコントローラと同型の普遍パターン）。
- 伝播は結果整合でよい（[`../distributed-systems/consistency-models.md`](../distributed-systems/consistency-models.md)）。データプレーンに要るのは最新性ではなく**単調な収束**である。

### セルとシャッフルシャード

```
 セルベース: 系を同型のセルに割り、顧客をセルへ固定的に張り付ける
 ┌─ thin router (最小・退屈・変更しない) ─┐
 │   cell-1      cell-2      cell-3      │   1 セルの障害 = 全体の 1/N
 │  [完結した   [完結した   [完結した     │   セルは大きくしない——増やす
 │   スタック]    スタック]    スタック]     │   新規顧客は既存セルへ、溢れたら増設
 └────────────────────────────────────────┘

 シャッフルシャード: n=8 ワーカーから各テナントへ k=2 の組を割当
   worker:      1    2    3    4    5    6    7    8
   tenant A:    ●         ●                            shard {1,3}
   tenant B:         ●              ●                  shard {2,5}
   tenant C:    ●                        ●             shard {1,6}
   A が worker1 を焼いても、C は worker6 で生存(部分重なり)。
   完全一致シャードの確率 1/C(8,2)=1/28。組合せ C(n,k) が仮想的な隔離単位。
```

## 技術詳細 (Technical Details)

### 1. Physalia — ブラストラディウスを目的関数にした合意ストア

EBS は書き込みをレプリカ鎖で複製し、その**構成（どのレプリカが正か）** を強一貫なストアで管理する。この構成ストアが Physalia である。設計の要点：(a) **ボリュームごとに独立の 7 ノード Paxos セル**を張る——合意の単位を細分化し、1 セルの障害が他ボリュームへ波及しない。(b) セルのノードはそのボリュームのクライアントの**物理的近傍**に配置し、分断時に「クライアントと構成ストアが同じ側」に残る確率を上げる。(c) 数百万セルの管理（配置・修復・監視）自体は結果整合の外側の系が担う——強一貫性が要るのは各セルの中だけ、という一貫性の局所化。全体として「大きな信頼できる 1 個」ではなく「小さな信頼できる無数」を作る選択であり、[`../distributed-systems/consensus.md`](../distributed-systems/consensus.md) の合意機構を可用性の**幾何学**（誰の近くに置くか）と組み合わせた点が新しい。

### 2. シャッフルシャーディングの数理と設計パラメータ

テナント 2 者のシャードが完全一致する確率は 1/C(n,k)。**部分重なり**まで許すと、共有ワーカー数 j の分布は超幾何分布 P(J=j) = C(k,j)C(n−k,k−j)/C(n,k) に従う（[`../../foundations/mathematics/probability-statistics/probability-random-variables.md`](../../foundations/mathematics/probability-statistics/probability-random-variables.md)）。設計は次の綱引きになる：k を増やすと 1 テナントの容量・冗長性は上がるが、他テナントとの重なりも増える。クライアントが「失敗したら同一シャード内の別ワーカーへリトライする」ことが前提であり、リトライ機構（技術詳細 3）と組で初めて成立する。また割当が**固定**（シャッフルは初回のみ）である点が本質——リクエストごとに引き直すと、悪性負荷が確率的に全ワーカーへ拡散し、隔離が消える。

### 3. リトライの力学 — 増幅・ジッタ・予算

- **増幅**: 深さ d の呼び出し連鎖で各層が r 回リトライすると最悪 r^d 倍。3 層 × 3 リトライで 27 倍——平時の余裕 (headroom) を桁で食い潰す。対策の第一は「リトライは 1 箇所（できるだけ端）で行う」という配置の規律。
- **ジッタ**: 同時に失敗したクライアント群が同じバックオフ表で再送すると、再送が**同期して**波になる（thundering herd）。full jitter（待ち時間を [0, base·2^attempt] の一様乱数にする）は再送時刻の相関を破壊し、シミュレーション上、完了時間と総呼び出し数の双方を改善する（ベンダー提示, Brooker 2015）。
- **予算**: バックオフしても、故障が長引けばリトライ総量は積み上がる。クライアント側トークンバケット（成功で補充、リトライで消費——AWS SDK の adaptive retry 等）は「失敗が多い間はリトライ自体を諦める」ことで正帰還の利得を強制的に 1 未満へ落とす。サーキットブレーカはその二値近似である。
- **キュー**: 過負荷時の FIFO キューは「もう誰も待っていない古い要求」を律儀に処理して goodput をゼロにする。deadline 伝播と、バックログ時の LIFO 化・load shedding（[`../../foundations/mathematics/probability-statistics/markov-chains-queueing.md`](../../foundations/mathematics/probability-statistics/markov-chains-queueing.md) の待ち行列の語彙で、λ>μ の定常解は存在しない——入口で λ を削るしかない）が対になる。

### 4. メタステーブル障害の構造

HotOS '21 の定式化では、系は (a) 脆弱状態（負荷が回復閾値を超えているが、正帰還はまだ閉じていない）で通常運転しており、(b) **トリガ**（一時的な負荷スパイク、部分障害、デプロイ）が正帰還ループ——リトライ増幅、キャッシュヒット率低下（キャッシュが落ちると origin への負荷が定常状態の数倍になり、キャッシュが温まる前に origin が死ぬ）、GC スパイラル、コネクション再確立の嵐——を閉じ、(c) トリガ除去後も**持続効果 (sustaining effect)** が系を過負荷に固定する。回復には正帰還の腕を物理的に切る操作（トラフィックの大幅遮断、再起動、キャッシュのプレウォーム）が要る。OSDI '22 の実例調査は公開ポストモーテムの相当数がこの型に合致することを示した。設計上の含意：平時の性能試験は脆弱状態の存在を検出できない——**「トリガ+持続効果」の注入試験**（カオスエンジニアリング）だけが検出手段になる。

### 5. セルベースアーキテクチャの設計判断

- **セルサイズ**: 小さいほど爆発半径と試験可能性（本番同型の負荷で 1 セルを試験できる）が良く、大きいほど運用対象数と最大顧客の収容が楽。「最大テナントが 1 セルに収まるか」が下限制約になり、収まらない巨大テナントのために結局シャーディングが要る——セルは万能ではなく、シャッフルシャーディングと併用される。
- **ルータは薄く**: セルの手前の振り分け層は全セル障害の共通依存 (single point of correlation) なので、「顧客 ID → セル」の静的表引き程度まで削ぎ、複雑さをセル内へ押し込む。
- **セル間の非依存**: セルをまたぐ同期呼び出しを禁じる。またいだ瞬間、爆発半径の算術が壊れる。
- AWS はこの構造を whitepaper で公式パターン化しており（ベンダー提示）、Physalia のセル、Route 53 のシャッフルシャード、AZ という物理セルまで、粒度の異なる同型が積層している。

### 6. 静的安定性の実装形

- **容量の事前確保**: N AZ 構成で各 AZ に定常負荷の 1/(N−1) 増しを常備（3 AZ なら 150%）。オートスケーリングは平時の需要追従の道具であり、AZ 障害吸収の道具ではない。
- **構成のローカル保持**: データプレーンは構成をローカルディスク/メモリに持ち、制御系が沈黙しても TTL 切れで自壊しない（「更新が来ないなら現状維持」——fail-static)。ここはセキュリティの fail-closed 原則と緊張関係にあり、セキュリティ考察で扱う。
- **依存の棚卸し**: 「障害からの回復経路上にあるコントロールプレーン依存」を列挙して潰す。回復に DNS 変更・インスタンス起動・IAM 変更が要る設計は、それらの制御系が同時に混雑している最悪時に賭けている。

## セキュリティ考察 (Security Considerations)

- **コントロールプレーンは最高権限の攻撃対象である**: データプレーンの侵害は 1 リソースの侵害だが、コントロールプレーンの侵害は全テナントのリソースの作成・削除・付替えを許す。管理 API の認証認可（[`cloud-iam-authorization.md`](cloud-iam-authorization.md)）・監査ログ・変更の多者承認は、可用性設計と同じ重みの必須要件である。セル分割は侵害の水平移動も 1 セルに制限する——爆発半径の議論は障害とセキュリティで同型に働く。
- **スロットリングは DoS 防御を兼ねる**: アドミッション制御・クォータは安定性機構であると同時に、単一テナントによる資源枯渇攻撃（意図的な poison pill を含む）への防御線である。シャッフルシャーディングは DDoS 吸収にも同じ算術で効く——攻撃者が焼けるのは自分のシャードだけであり、Route 53 の耐 DDoS 設計の中核はこれである（ベンダー提示）。
- **fail-static と fail-closed の緊張**: 可用性は「制御系が沈黙したら最後の既知状態で動き続けろ」と言い、セキュリティは「認可情報が検証できないなら拒否しろ」と言う。実務の解は境界ごとの選択である——認可の失効（クレデンシャル無効化）は期限付きトークンの**期限で**保証し（即時性を諦める）、認可判定そのものはローカルキャッシュで静的安定にする。[`cloud-iam-authorization.md`](cloud-iam-authorization.md) の結果整合な IAM はこの妥協の実装である。
- **調停ループは改竄検知器でもある**: 望ましい状態との全量比較を回し続ける系は、攻撃者による実状態の改変（不正な設定変更・野良リソース）を次周期で検出・巻き戻す。宣言的管理は運用の道具であると同時に、ドリフト検知という受動的なセキュリティ監視でもある。

## 結論 (Conclusions)

- クラウドの信頼性パターンは「相関の破壊」という単一原理の系である：空間の相関はセル・シャッフルシャード・AZ が切り、時間の相関はジッタ・一定作業が切り、因果の相関（障害が制御系依存を通じて増幅する経路）は静的安定性・リトライ予算・アドミッション制御が切る。個々の tips として暗記するより、この 3 軸のどこを切る道具かで整理する方が応用が利く。
- コントロール/データプレーン分離の本質は依存の向きの規律である。「データプレーンは制御系なしで走り続けるか」「回復経路に制御系依存はないか」という 2 つの問いが、アーキテクチャレビューの最初の審査項目になる。
- 隔離と統計多重化は恒久的な緊張関係にあり、Physalia（合意の細分化）、シャッフルシャーディング（組合せ論的隔離）、DynamoDB の GAC（割当の論理化）は、いずれも「物理を共有したまま論理的な隔離を最大化する」という同じ問いへの異なる答えである。マルチテナントの経済はこの緊張の上に立っている。
- メタステーブル障害の教訓は「平時の試験は脆弱状態を検出できない」こと。正帰還の利得を設計段階で 1 未満に抑える（リトライ予算・入口拒否・一定作業）ことと、トリガ注入試験だけが対策であり、これは可用性工学が「平均性能の工学」から「最悪時挙動の工学」へ軸足を移したことを意味する——[`../embedded/`](../embedded/) が単機で辿った道の、分散版の再演である。
