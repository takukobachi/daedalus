# 分散システムの一貫性モデル (Consistency Models in Distributed Systems)

## 概要 (Overview)

分散システムでは、同じデータの**複製 (replica)** を複数ノードに置く。理由は単純で、可用性 (availability) と耐障害性 (fault tolerance)、そして読み出しのスケールのためである。だが複製した時点で、ハードウェアのマルチコアと**まったく同じ矛盾**が生まれる。すなわち「同じデータのコピーが複数箇所に同時に存在し、片方を書き換えると他方が陳腐化 (stale) する」という矛盾である。

`../../hardware/cpu/cache-coherence.md` は、私有キャッシュ (private cache) と共有メモリ (shared memory) の同居というこの矛盾を、ハードウェアが**自動で**吸収する機構を扱った。本ドキュメントはその概念的なスケールアップである。ノードを「コア」、ネットワークを「相互接続バス」、複製を「キャッシュライン」と読み替えると、問題の構造は一致する。違いは規模ではなく**前提**にある。分散系では (1) 通信が遅く不確実で、(2) **ネットワーク分断 (network partition)** によって一部ノードが到達不能になり、(3) その間も各複製が**並行 (concurrent)** に更新を受け付けうる。ハードウェアが「数十ナノ秒で全コアに無効化が届く」ことを暗黙の前提にできるのに対し、分散系はその前提を失う。結果として、ハードウェアでは透過的だった一貫性が、分散系では**明示的に選択する設計パラメータ**になる。

**一貫性モデル (consistency model)** とは、この複製されたデータに対する操作 (operation) が、どのような順序・可視性で観測されることを保証するか、という契約である。強いモデルほどプログラマにとって直感的だが、レイテンシと可用性を犠牲にする。本ドキュメントは、線形化可能性 (linearizability) から結果整合性 (eventual consistency) までを強い順に整理し、それぞれが何を保証し、何を捨てているかを Level 3 で記述する。

## 方法論 (Methodology)

- まず**コヒーレンス (coherence)** と**コンシステンシ (consistency)** の区別を、ハードウェアの議論からそのまま持ち込む。`../../hardware/cpu/cache-coherence.md` の発見事項 1 が述べたとおり、コヒーレンスは「単一アドレスの収束」、コンシステンシは「複数操作間の順序」であり、この**軸は分散規模でも保存される**。本ドキュメントは主に後者を扱う。
- 一貫性モデルを**強さで全順序化せず、束 (lattice)** として捉える。多くのモデルは互いに比較可能だが、一部（セッション保証など）は直交し、半順序をなす。
- 各モデルを「**履歴 (history)**」（操作の呼び出し (invocation) と応答 (response) の時系列）の上で定義する。あるモデルを満たすとは、その履歴がモデルの許す**逐次順序 (sequential order) へ並べ替え可能**であることをいう。これはハードウェアのメモリモデルが「実行を許される順序の集合」で定義されるのと同形である。
- CAP / PACELC を「定理」ではなく**設計上のトレードオフの言語**として用い、各モデルがこの座標のどこに位置するかを示す。
- 評価軸は終始 **「保証の強さ」対「レイテンシ・可用性のコスト」**。強い一貫性は調整 (coordination) を要し、調整は往復通信を要し、往復は分断時に停止する。

## 発見事項 (Findings)

1. **コヒーレンスとコンシステンシの区別は分散規模でも保存される。** 単一キー (single key) について全複製が最終的に同じ書き込み順に収束するか（コヒーレンス相当 = 結果整合性の核）と、複数キー・複数操作間の順序を跨いで保証するか（コンシステンシ相当 = 因果一貫性以上）は別問題である。ハードウェアでコヒーレンスが順序を保証しなかったのと同様、結果整合性は複数オブジェクト間の順序を保証しない。

2. **線形化可能性は「分散版の逐次一貫性 + 実時間順序」である。** ハードウェアの逐次一貫性 (sequential consistency, SC) が「ある全順序が存在し各スレッドのプログラム順を尊重する」だったのに対し、線形化可能性 (linearizability) は加えて**実時間 (real-time) 順序**を尊重する。操作 A が応答した後に操作 B が呼ばれたなら、全順序でも A が B より前に来なければならない。

3. **強い一貫性は調整コストとして必ず支払われ、分断時に可用性と衝突する (CAP)。** 線形化可能性は全複製の合意 (consensus) ないしクォーラム (quorum) 往復を要する。ネットワーク分断時、線形化可能性を保つには応答を止める (CP) か、応答を続けて一貫性を捨てる (AP) かの二択を迫られる。これが **CAP 定理**の核である。

4. **因果一貫性は「分断時にも可用なまま保てる最強のモデル」とされる。** 因果順序 (causal order) は局所的に決まる関係であり、全体合意を要しない。論理時計 (logical clock)、とりわけベクトルクロック (vector clock) で捕捉でき、分断中でも各複製が更新を受け付けつつ因果を保てる。可用性と意味のある順序保証の境界線上にある。

5. **結果整合性は「収束」しか約束しない。衝突解決が設計の本体になる。** 「更新が止まれば最終的に全複製が同一値に至る」だけでは、途中の読みも、衝突した並行更新の決着も規定されない。**CRDT (Conflict-free Replicated Data Type)** は、更新操作を**可換 (commutative)・結合的・冪等 (idempotent)** に設計することで、順序や重複に関わらず決定的に収束させる。すなわち結果整合性を「収束する」ものへ格上げする道具である。

6. **一貫性の弱さは機能バグでなく整合性バグを生む。** stale read による二重支払い・在庫の二重販売、認可判定の取りこぼしなど、**個々のノードは正常動作しているのに全体として不正**という障害は、ほぼ一貫性モデルの選択ミスに帰着する（セキュリティ考察を参照）。

## アーキテクチャ (Architecture)

### 複製・分断・並行 — 問題の発生源

```
       Client A                         Client B
          │ write x=1                       │ read x
          ▼                                 ▼
     ┌─────────┐      ╳ partition ╳    ┌─────────┐
     │ Replica1│◀────── network ──────▶│ Replica2│
     │  x = 1  │     (一時的に切断)     │  x = 0  │  ← まだ陳腐 (stale)
     └─────────┘                       └─────────┘
   write は届いた             read は古い値 0 を返しうる
```

ハードウェアでは Replica1→Replica2 の無効化は数十 ns で必ず届く。分散系ではその伝播が遅延・喪失・順序入れ替えを起こし、かつ分断中も両系が独立に書き込みを受けうる。「いつ・どの順で・どの複製まで」可視になるかを規定するのが一貫性モデルである。

### 一貫性モデルの束 (Consistency Lattice / Hierarchy)

上ほど強く（保証が多くコストが高い）、下ほど弱い（可用・低レイテンシ）。縦の実線は包含（上が下を含意）、点線は直交関係を表す。

```
              ┌─────────────────────────────┐
   強い       │  線形化可能性 Linearizability │  実時間順序を尊重・単一オブジェクト
   (CP寄り)   └──────────────┬──────────────┘
              ┌──────────────┴──────────────┐
              │ 逐次一貫性 Sequential Consist.│  全順序+プログラム順 (実時間は不問)
              └──────────────┬──────────────┘
              ┌──────────────┴──────────────┐
              │   因果一貫性 Causal Consist.  │  分断耐性のある最強 (調整不要)
              └──────────────┬──────────────┘
              ┌──────────────┴──────────────┐
              │ セッション保証 (直交群):       │  …… RYW / Monotonic Reads /
              │  read-your-writes ┄┄ など     │     Monotonic Writes / WFR は
              └──────────────┬──────────────┘     互いに半順序 (lattice)
              ┌──────────────┴──────────────┐
   弱い       │ 結果整合性 Eventual Consist.  │  収束のみ保証・CRDTで決定化
   (AP寄り)   └─────────────────────────────┘
```

注意: 厳密にはセッション保証は逐次一貫性より弱く、結果整合性より強い**直交した束**を成す。線形 ⊃ 逐次 ⊃ 因果 ⊃ {因果+各セッション保証} ⊃ 結果整合 という包含が大枠だが、セッション保証群（read-your-writes, monotonic-reads, monotonic-writes, writes-follow-reads）は相互に独立で、必要なものだけを選んで合成できる。

### 履歴 (History) と非線形化可能なスケジュール

線形化可能性の有無は、操作の**呼び出し-応答区間**を1点へ畳めるかで判定する。下図は**非線形化可能**な履歴の例。

```
時間 ───────────────────────────────────────────▶
ClientA:  [── write(x,1) ──]
ClientB:                       [── read(x)→0 ──]      ✗ 非線形化可能
                               ^ A の応答後に B が開始したのに
                                 B が古い値 0 を観測 (実時間順序違反)

ClientA:  [── write(x,1) ──]
ClientB:                       [── read(x)→1 ──]      ✓ 線形化可能
                                 A 完了後の read は 1 を返さねばならない

ClientA:  [──── write(x,1) ────]
ClientB:       [── read(x)→0 ──]                       ✓ 線形化可能でありうる
               ^ 区間が重なる間は 0 でも 1 でも可
                 (まだ「効いた瞬間」を A の区間内に置ける)
```

要点は、**操作が重なっていない**（A が応答してから B が呼ばれた）場合に実時間順序を破ると線形化可能性が壊れること。重なっている間はどちらの順でも「効いた瞬間」を区間内に取れるため自由度がある。これはハードウェアの SC が「実時間を見ない」のに対し、線形化可能性が「重ならない操作には実時間を強制する」という1点だけ強いことの図解である。

## 技術詳細 (Technical Details)

### 1. ハードウェアのメモリ一貫性との対応関係

| 観点 | ハードウェア (multicore) | 分散システム |
|---|---|---|
| 複製の単位 | キャッシュライン (64B) | レコード / キー / オブジェクト |
| 単一アドレスの収束 | コヒーレンス (cache coherence) | 単一キーの結果整合性 |
| 複数操作の順序 | メモリコンシステンシ (SC/TSO/弱順序) | 一貫性モデル (linearizable…eventual) |
| 伝播機構 | 無効化/更新トランザクション | 複製プロトコル (gossip, quorum, log ship) |
| 最強モデル | sequential consistency (SC) | linearizability (= SC + 実時間) |
| 順序の緩和理由 | 性能 (store buffer, OoO) | 可用性・レイテンシ・分断耐性 |
| 順序強制の道具 | メモリバリア / `fence` | 合意 (Paxos/Raft), クォーラム, 論理時計 |

`../../hardware/cpu/memory-ordering-atomics.md` のメモリバリアは「ここまでの書き込みを先に可視化せよ」という局所的な順序強制だった。分散系の合意・クォーラムはそのグローバル版であり、同じく「**順序を強制するには調整(往復)が要り、調整は遅い**」という不等式の上にある。ハードウェアが弱順序+バリアを選んだのと同じ理由で、分散系も弱い既定 + 必要箇所だけ強化、という設計に向かう。

注意すべき非対称: ハードウェアの SC は実時間を**見ない**（store buffer により自分の書き込みすら遅れて他コアに見える）。分散の linearizability は実時間を**見る**ため、むしろハードウェアの SC より強い。「分散の最強 = ハードの最強」ではなく、「分散の最強 = ハードの最強 + 実時間」である。

### 2. 線形化可能性 (Linearizability) の厳密な定義

履歴 H（呼び出しイベントと応答イベントの列）が**線形化可能**であるとは、次を満たす逐次履歴 S が存在することをいう。

1. **正当性 (sequential validity)**: S は各オブジェクトの逐次仕様 (sequential specification) を満たす。すなわち各 read は「直前の write」を返す。
2. **実時間順序の保存 (real-time order)**: H で操作 `op1` の応答が `op2` の呼び出しより前に起きた（`op1 ≺ op2`）なら、S でも `op1` が `op2` より前に並ぶ。
3. **同値性**: S は H と同じ操作・同じ戻り値からなる（H の重なり順だけを並べ替える）。

直感的には「各操作は呼び出しと応答の**間のある一瞬**にアトミックに効く (linearization point) ように見える」。重要な性質を以下に示す。

- **局所性 (locality / composability)**: 各オブジェクトが個別に線形化可能なら、システム全体も線形化可能。逐次一貫性にはこの合成性がない。分散系で「オブジェクトごとに」一貫性を語れる根拠であり、ハードのコヒーレンスが「アドレスごと」に閉じていたことと符合する。
- **非ブロッキング**: 線形化可能性は待機を要求しない（定義は履歴の性質であって実装制約ではない）。

### 3. 逐次・因果・結果整合・セッション保証

- **逐次一貫性 (sequential consistency)**: 全操作のある全順序が存在し、各クライアントから見た自分の操作順 (program order) を保つ。**実時間は不問**であり、別クライアント間で「後から呼んだのに先に見える」が許される。Lamport の元定義そのもの。線形化可能性から実時間条件だけを外したもの。

- **因果一貫性 (causal consistency)**: **因果関係 (happens-before, `→`)** で順序づけられた操作だけは、全複製で同じ順に見える。並行 (concurrent) な操作（互いに因果のない操作）は複製ごとに別順でよい。「投稿してからその返信を書いた」なら、誰の目にも投稿→返信の順になるが、無関係な2投稿の順序は揺れてよい。**分断時にも可用なまま維持できる最強のモデル**（合意不要、論理時計で局所判定できるため）。

- **結果整合性 (eventual consistency)**: 「更新が停止すれば、いずれ全複製が同一状態に収束する」だけ。途中の読みも、並行更新の決着規則も規定しない。最も可用・最も低レイテンシ。DNS、多くの AP 型 KVS が該当。

- **セッション保証 (session guarantees)** — クライアント1セッション内で成り立てばよい、実用上の弱い保証群である。
  - **read-your-writes (RYW)**: 自分が書いた値は、その後の自分の読みで必ず見える。プロフィール更新直後に古い値が見える事故を防ぐ。
  - **monotonic-reads**: いったん新しい値を読んだら、以後それより古い値へ後退しない（時間が巻き戻らない）。
  - **monotonic-writes**: 同一セッションの書き込みは、その順に複製へ適用される。
  - **writes-follow-reads (WFR)**: 読んだ値に因果的に依存する書き込みは、その読んだ値より後に順序づけられる。

  これらは互いに**直交**し、必要なものだけ選んで合成できる（束をなす）。「ユーザは自分の更新だけ即時に見えればよく、他人の更新は遅れてよい」という現実的妥協を、形式的に表現したもの。

  実装の要点は次のとおりである。

  - クライアントが自分の最後の書き込みのバージョン（ベクトルクロック断片や単調 token）を持ち回る。
  - 読み出し先の複製がそのバージョン**以上**を持つまで待つ、または持つ別複製へ切替える。
  - これで RYW（自分の write を含む複製しか読まない）と monotonic-reads（読んだ最大バージョンを後退させない）を満たす。

  全体合意を要さないため、結果整合な基盤の上に**クライアント側のメタデータだけ**で載せられるのが利点である。サーバ側の一貫性は弱いまま、セッション粒度で必要な直感性を回復する。

### 4. CAP 定理と PACELC

**CAP 定理** (Brewer; Gilbert & Lynch による形式化): ネットワーク分断 (Partition) が起きたとき、線形化可能な一貫性 (Consistency) と可用性 (Availability) の**両方は同時に保てない**。

```
   分断 P 発生中、複製間が通信不能:
     ┌─ CP を選ぶ: 一貫性を守るため、合意できない側は応答拒否 (停止)
     └─ AP を選ぶ: 応答を返し続けるが、複製がズレる (stale/衝突を許す)
   ※ 「分断しない」という選択肢は無い。P は与件 (環境が決める)。
```

CAP の誤解されがちな点: 「3つから2つ選ぶ」ではない。**分断は選べない前提**であり、現実の選択は「分断時に C を捨てるか A を捨てるか」だけ。さらに CAP は**分断中の挙動しか語らない**。分断がない平常時のトレードオフを無視している。

**PACELC** はこの欠落を埋める拡張である。

```
   if Partition:   choose  A  (可用性)  or  C  (一貫性)     ← CAP と同じ
   Else (平常時):  choose  L  (低レイテンシ) or C (一貫性)   ← CAP が見落とした軸
```

平常時ですら、線形化可能性はクォーラム往復を要するため**レイテンシ (L) を払う**。例: 強一貫を志向する Spanner は分断時も平常時も一貫性優先 (PC/EC)、Dynamo 系は分断時も平常時も可用性・低レイテンシ優先 (PA/EL)。設計の本質は「分断時」だけでなく「常時」一貫性にいくら払うかである。

### 5. 論理時計による因果順序の捕捉

因果一貫性は「どの操作がどの操作に**先行 (happens-before)** するか」を機械的に判定できて初めて実装できる。物理時計はクロックずれ (clock skew) のため信頼できない。そこで論理時計を使う。

- **Lamport クロック (Lamport timestamp)**: 各イベントに単調増加のスカラ `C` を付す。送信時 `C++` を載せ、受信時 `C = max(local, recv)+1`。性質: `a → b ⇒ C(a) < C(b)`。**ただし逆は成り立たない**。`C(a) < C(b)` でも `a` と `b` は並行かもしれない。因果の**必要条件**しか与えず、並行と因果を区別できない。

- **ベクトルクロック (vector clock)**: 各ノード `i` がベクトル `V[1..n]` を持つ。自イベントで `V[i]++`、メッセージに `V` を載せ、受信で要素ごとに `max`。比較規則は次のとおりである。

```
   // 例示 (illustrative)。3ノード a,b,c。
   V(x) ≤ V(y)  ⟺  ∀i. V(x)[i] ≤ V(y)[i]
   x → y   ⟺  V(x) < V(y)            // 真に小さい (因果先行)
   x ∥ y   ⟺  V(x) ≰ V(y) ∧ V(y) ≰ V(x)  // 並行 (衝突候補)
   // 例:  V(x)=[2,0,1], V(y)=[2,1,1]  →  x → y
   //      V(p)=[1,2,0], V(q)=[2,1,0]  →  p ∥ q  (並行: 衝突解決が必要)
```

  ベクトルクロックは因果を**完全に**捉える（必要十分）。代償はサイズ O(ノード数) で、ノードが動的だと管理が重い。

- **ハイブリッド論理時計 (HLC: Hybrid Logical Clock)**: 物理時刻 (NTP) の上位ビットと論理カウンタを合成する。`HLC = (pt, l)`。物理時刻に近い読みやすさを保ちつつ、`a → b ⇒ HLC(a) < HLC(b)` を保証する。クロックがわずかにずれても論理カウンタが因果を救う。物理時計の単調性に依存しないため、後述のクロック改ざんに対しても**因果は崩れない**（順序の意味は守られる）。CockroachDB 等が採用。

```
   Lamport  : スカラ・軽い・並行を区別できない (因果の必要条件のみ)
   Vector   : ベクトル・並行を完全に区別・O(N) のサイズ
   HLC      : 物理時刻+論理・人間可読・因果保証・clock skew に頑健
```

### 6. クォーラム (Quorum) と一貫性

複製数 `N`、書き込み定足数 `W`、読み出し定足数 `R` のとき、

```
   R + W > N   ⟹  読みクォーラムと書きクォーラムが必ず1ノード以上で重なる
                  ⟹ 最新の書き込みを含むノードに必ず触れる (強い一貫性の核)
   W > N/2     ⟹  書き込み同士が重なる ⟹ 並行書き込みの順序を一意化できる
```

`R+W>N` は線形化可能性の**必要条件であって十分条件ではない**。読み修復 (read repair)、書き込み時の同期、リーダー経由の直列化などを伴って初めて線形化可能になる。素朴な Dynamo 型クォーラムは「**sloppy quorum**」や read-repair の競合で、`R+W>N` でも一時的に stale を返しうる。逆に `R+W≤N`（例 `R=W=1`）は最大可用・最低レイテンシだが結果整合性どまり。クォーラムは「重なりを作るかどうか」で一貫性とレイテンシを連続的に調整するノブである。これはハードのクォーラムに相当する概念が無い点で分散固有だが、「順序を強制するには重なり=調整が要る」という構造はバリアと同型。

### 7. CRDT による結果整合性下での収束

結果整合性の「最終的に同じ値」を、**衝突解決ロジックなしに保証**するのが CRDT である。鍵は、複製への適用操作を**可換・結合的・冪等**にすることである。すると到着順・重複に関わらず同じ状態へ収束する (strong eventual consistency)。

- **状態ベース (CvRDT)**: 各複製が状態を持ち、マージ関数 `merge` が**結合束 (join-semilattice) の上限 (LUB)** であること。例: G-Counter は要素ごと `max` でマージ。`merge` が可換・結合的・冪等なので gossip 順序を問わない。
- **操作ベース (CmRDT)**: 操作を配り、操作が（並行な操作と）可換であること。重複配送を防ぐ配送層が要る。

```
   // 例示 (illustrative)。G-Counter (増加のみカウンタ) の収束。
   //   各ノード i は配列 P[]、自分の増加は P[i] のみ加算。
   //   value = Σ P[k]
   //   merge(a, b)[k] = max(a.P[k], b.P[k])     // 要素ごと max = LUB
   // ノードを跨いだ increment が任意順・重複で届いても、
   // max は可換・結合的・冪等 ⟹ 全複製が同一 value に収束。
```

CRDT は「並行更新を**衝突させない代数**へ押し込む」発想であり、Last-Write-Wins (LWW) のような**情報を捨てる**衝突解決（時計順で片方破棄）と対比される。LWW はクロックに依存し、クロックずれで「新しい更新が古いものに負ける」事故を起こす。HLC やベクトルクロックはここでも有効である。

### 8. 線形化可能性の検査 (Linearizability Checking / Jepsen 視点)

「強一貫を謳う実装が本当に線形化可能か」は経験的に検査できる。

- **手法**: クライアント群に並行操作を流し、各操作の (呼び出し時刻, 応答時刻, 引数, 戻り値) を**履歴**として記録。その履歴を実時間制約の下で逐次順へ並べ替え可能か探索する。一般には NP 完全だが、Wing-Gong / Knossos / Porcupine 等の探索器が、重ならない操作の実時間制約で探索空間を刈り込み実用的に解く。
- **不確定性の扱い**: クライアントが応答前にクラッシュした操作（呼び出しはあるが応答が無い）は、効いたとも効かなかったとも確定できない。検査器はこれを「どちらでもよい」として両可能性を探索に含める。`R+W>N` のクォーラム実装でも、この未確定操作と read-repair の絡みで stale が露出しうる。
- **Jepsen 的視点**: 検査を**ネットワーク分断・クロックずれ・プロセス停止を注入しながら**行う。多くの「強一貫」実装は平常時は正しく、**分断・再構成時にのみ**線形化可能性違反（消えた書き込み、stale read、split-brain による二重リーダー）を露呈する。障害注入下での履歴検査が、宣伝と実態の差を暴く。
- 含意: 一貫性は「コードを読めば分かる」ものでなく、**障害下の観測可能な振る舞い**として検証すべき性質である。ハードのメモリモデルを litmus test で検証するのと同じ姿勢を、分散系では Jepsen が担う。

## セキュリティ考察 (Security Considerations)

一貫性の弱さは、個々のノードが正常でも**システム全体としては不正**な状態を許す。これは可用性のための意図的な緩和が、そのままセキュリティ・整合性の穴になる典型である。

- **stale read による二重支払い・在庫の二重販売 (double-spend / oversell)**: 残高や在庫の判定を結果整合な複製で行うと、分断中に両複製が独立に「残高十分」「在庫あり」と判定し、**同じ資源を二重に確定**してしまう。`../apis/stripe-connect-specification.md` が扱う決済整合性はまさにこの問題で、資金移動 (movement) の追跡・突合 (reconciliation) は「各操作が一度きり (exactly-once 相当) に確定する」ことを要求する。実務上は (a) 残高更新をリーダー経由で線形化する、(b) **冪等キー (idempotency key)** で再試行・重複適用を吸収する、(c) 確定操作を条件付き書き込み (compare-and-set, `R+W>N` クォーラム) にする、で守る。「結果整合な読みで金額判定をしてはならない」が鉄則。

- **stale read による認可判定の穴 (authorization bypass)**: 権限剥奪・トークン失効・ブロックリスト追加といった **「禁止」の伝播**を結果整合な複製に頼ると、失効が伝わる前の複製が古い許可を返し、剥奪済みの主体がアクセスできる時間窓が生まれる。許可 (allow) より**失効 (revoke) の伝播こそ強い一貫性を要する**。失効は read-your-writes だけでは不足で、全読み手に対する monotonic かつ即時の可視性が要る。対策は失効を線形化点に通す、短い TTL でフェイルクローズ、失効チェックをリーダー/権威ノードへ集約する。

- **クロック改ざんと HLC (clock tampering)**: LWW 衝突解決や物理時計ベースの順序付けは、**ノードの時計を進める攻撃**に弱い。攻撃者が未来の timestamp で書けば、以後の正当な更新を「古い」として恒久的に負かせる（書き込みの抹消・固定化）。ハイブリッド論理時計 (HLC) やベクトルクロックは**因果関係そのもの**で順序づけるため、物理時刻の改ざんに対して因果順序を保つ。HLC は物理時刻の有界なずれを論理カウンタで吸収し、`a → b` の意味を守る。一方、純粋な物理時刻 LWW は単一の悪意ある時計で全系の整合性を破壊しうる。**順序の根拠を物理時刻に置かない**ことが防御の核。

- **split-brain による権威の二重化 (split-brain)**: 分断時に AP を選ぶと両側がリーダーとして振る舞い、後の統合 (merge) で矛盾を生む。リーダー選出を**フェンシング (fencing token, 単調増加するエポック番号)** で守り、古いリーダーの遅延書き込みを拒否する。これはハードの LL/SC が「途中で誰かが触ったら SC を失敗させる」のと同型であり、古い世代の操作を**機構的に無効化**する発想である（`../../hardware/cpu/cache-coherence.md` の LL/SC 節を参照）。

教訓: 可用性のために一貫性を緩めることは、そのまま「正常なノードが正常に振る舞った結果としての不正」を招き入れる。**金額・在庫・認可・失効**という「一度きり・後退不可」を要する判定は、結果整合の上に置いてはならない。どこで線形化点を通すか、どこで冪等性とフェンシングで守るかが、整合性の防御線である。

## 結論 (Conclusions)

- 分散の一貫性問題は、`../../hardware/cpu/cache-coherence.md` の「私有キャッシュと共有メモリの矛盾」を、**遅く・不確実で・分断する**ネットワーク前提へ拡大したものである。ハードウェアが透過的に吸収した一貫性は、分散系では明示的に選択する設計パラメータになる。
- コヒーレンス（単一キーの収束）とコンシステンシ（複数操作間の順序）の区別は規模を越えて保存される。前者は結果整合性の核、後者が因果一貫性以上を要する。
- モデルは線形化可能性 ⊃ 逐次一貫性 ⊃ 因果一貫性 ⊃ セッション保証群 ⊃ 結果整合性 という束をなす。線形化可能性は「逐次一貫性 + 実時間順序」で局所性 (composability) を持つ唯一の強モデル、因果一貫性は「分断時にも可用なまま保てる最強」、結果整合性は「収束のみ」で CRDT が決定化する。
- 強い一貫性は調整 (合意・クォーラム往復) として必ず支払われ、CAP は分断時の、PACELC は平常時のトレードオフを言語化する。これはハードの「順序強制にはバリア=コストが要る」と同型の不等式である。
- 因果と衝突解決の基盤は論理時計（Lamport / vector / HLC）であり、クォーラム `R+W>N` と CRDT が結果整合の上に必要なだけの強さを足し戻す。
- セキュリティ上、stale read は二重支払い・認可バイパスを、物理時計依存はクロック改ざんを招く。金額・在庫・認可・失効は線形化点・冪等キー・フェンシング・因果時計で守る。
