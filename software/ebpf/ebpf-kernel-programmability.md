# eBPF — カーネル内プログラマビリティの基盤 (eBPF: In-Kernel Programmability)

## 概要 (Overview)

カーネルを拡張したいとき、選択肢は長らく2つしかなかった。**カーネルモジュール (kernel module)** はカーネル特権で直接動くため速いが、1つのバグが即座にカーネルパニックや権限奪取に直結し、カーネル内部 API に依存するためバージョン間の可搬性もない。**ユーザ空間 (userspace)** での実装は安全だが、イベントのたびにコンテキストスイッチとデータコピーの往復コストを払う——パケット1つ、システムコール1回ごとに境界を跨ぐのでは、観測やフィルタリングの対象そのものより高くつく。「速いが危険」か「安全だが遅い」か。この二律背反がカーネル拡張の永遠のトレードオフである。

**eBPF (extended Berkeley Packet Filter)** はこれに対する第三の道である: ユーザが書いたプログラムを**検証器 (verifier)** が静的解析で安全と証明できた場合に限り、カーネルコンテキストでネイティブ実行する。信頼の根拠を「コードの出自（署名されたモジュールか）」から「コードの性質（安全性が機械的に証明できたか）」へ移した点が本質である。`../virtualization/hardware-virtualization-containers.md` が扱った隔離スペクトラムの言葉で言えば、gVisor がカーネルのロジックをユーザ空間へ引き上げて攻撃面を狭めたのに対し、eBPF はユーザのロジックをカーネルへ持ち込んで境界越えコストを消す——**同じカーネル/ユーザ境界を、正反対の方向に越える**2つの解である。

本ドキュメントは検証器を中心に、実行機構 (JIT)、フック分類、マップ、可搬性 (CO-RE)、エコシステムまでを機構レベルで扱う。分析深度は Level 3。

## 方法論 (Methodology)

- eBPF を「言語」や「ツール」ではなく、**ロード時検証 + カーネル内実行 + 制約付きインタフェース（ヘルパ・マップ）** という3要素からなる実行基盤として定式化し、各要素が「カーネルモジュールの何を禁じ、ユーザ空間の何を回避したか」の差分で説明する。
- 検証器を本書の中心に置く。何を**証明**し (soundness)、その代償として何を**棄却**するか (completeness の放棄) を、抽象解釈 (abstract interpretation) の枠組みで整理する。
- フック（アタッチポイント）は列挙ではなく、**ネットワーク経路・実行トレース・セキュリティ境界・資源境界**の4系統に分類し、「カーネルサブシステムが1つずつ eBPF 差し替え可能になっていく」軌跡として読む。
- 数値（命令数上限、性能倍率など）は桁感 (order of magnitude) であり、カーネルバージョン・設定 (JIT 有効か、ハードニングの有無) に強く依存する。本文ではバージョン依存を都度明記する。
- 一次資料はカーネル文書 (Documentation/bpf/) と原論文 (McCanne & Jacobson 1993, Høiland-Jørgensen et al. 2018, Gershuni et al. 2019) に置く。

## 発見事項 (Findings)

1. **eBPF の本質は「実行前の証明と引き換えに、カーネル特権での実行を許す」という信頼モデルの転換である。** カーネルモジュールは「管理者が信頼したから」動かし、ユーザ空間は「何をしても壊せないから」動かす。eBPF は「検証器が安全性を証明できたから」動かす——信頼の単位が主体 (who) から性質 (what) へ移り、これがサードパーティのコードをカーネルに入れる社会的障壁を消した。

2. **検証器は健全性 (soundness) を取り完全性 (completeness) を捨てる。ゆえに「安全だが弾かれる」プログラムが必ず存在する。** すべての危険なプログラムを拒否するために、検証器は証明できないものをすべて拒否する。開発者は「コンパイラを通ったのに検証器に落ちる」体験を通じ、境界チェックの書き方やループ構造を**検証器に証明しやすい形**へ書き換える——「検証器と戦う (fighting the verifier)」は現実の開発工程である。

3. **フックの分類こそが eBPF の応用地図である。** ネットワーク経路 (XDP → tc → socket)、実行トレース (kprobe/tracepoint/fentry)、セキュリティ境界 (LSM/BPF)、資源境界 (cgroup)、そしてスケジューラ (sched_ext)。歴史的経緯はパケットフィルタだが、現在の eBPF は「カーネルのあらゆる境界に置ける汎用フック機構」であり、サブシステムが1つずつプラガブルになっていく軌跡の途中にある。

4. **マップ (map) がデータプレーンであり、eBPF を「フィルタ」から「システム」に変えた。** プログラム自体はイベント駆動で状態を持てないが、マップがカーネル↔ユーザ空間・プログラム↔プログラム間の共有状態を提供する。percpu マップによる競合回避は、`../../hardware/cpu-architecture/cache-coherence.md` の「同一ラインに触るコア数を減らす」教訓の eBPF 版である。

5. **可搬性はカーネルが自分の型情報 (BTF) を持ち歩くことで解決された (CO-RE)。** カーネル構造体のレイアウトはビルドごとに異なるため、旧来 (BCC) は実行先でヘッダ付きコンパイルするしかなかった。BTF + libbpf の再配置 (relocation) は「コンパイル済みバイナリをロード時にその場のカーネルへ合わせて修正する」方式で、コンパイラを本番ホストから追放した。

6. **検証器は単一障害点 (single point of failure) である。** 安全性の全根拠が検証器の正しさに集中するため、検証器のバグはそのまま権限昇格になる。主要ディストリビューションが非特権 BPF を既定で無効化している (`kernel.unprivileged_bpf_disabled`) のは、この構造的リスクの直接の帰結である。

## アーキテクチャ (Architecture)

### プログラムのライフサイクル

eBPF プログラムは通常 C（の制約付きサブセット）で書かれ、LLVM が BPF バイトコードへコンパイルし、`bpf(2)` システムコールでロードされる。カーネルは検証器を通過したものだけを JIT コンパイルし、フックへアタッチする。

```
  ユーザ空間                              カーネル空間
 ┌────────────────────────┐   ┌───────────────────────────────────┐
 │  C ソース (制約付き)      │   │                                   │
 │      │ LLVM (clang -target bpf)        │                        │
 │      ▼                  │   │                                   │
 │  BPF バイトコード (.o)   │   │                                   │
 │      │ bpf(BPF_PROG_LOAD)              │                        │
 │      └──────────────────┼──▶│  検証器 (verifier)                 │
 │                         │   │   全実行パスの抽象解釈              │
 │                         │   │   却下 ──▶ エラー (ロード失敗)      │
 │                         │   │   通過 │                          │
 │                         │   │        ▼                          │
 │                         │   │  JIT コンパイラ (per-arch)         │
 │                         │   │        │ ネイティブコード           │
 │                         │   │        ▼                          │
 │  制御アプリ (libbpf 等)  │   │  フックへアタッチ                  │
 │      ▲                  │   │  (XDP / kprobe / LSM / cgroup...) │
 │      │ bpf(MAP_LOOKUP/UPDATE)          │        │ イベント発火    │
 │      └──────────────────┼───┼──▶ ┌─────▼─────┐                 │
 │   （設定投入・結果回収）   │   │    │  マップ    │◀── プログラムが │
 │                         │   │    │ (共有状態) │    read/write   │
 └────────────────────────┘   └────└───────────┘──────────────────┘
```

マップが両世界を橋渡しする点が要である。プログラムはカーネル内で完結して高速に動き、ユーザ空間は非同期にマップを読み書きして設定投入と結果回収を行う——ホットパスから境界越えが消える。

### カーネル内フックポイントの地図

```
        ユーザ空間プロセス
     ────┬────────────────┬────── syscall 境界 ──────────────
         │                │
   [seccomp (cBPF)]   [tracepoint: syscalls] [uprobe: ユーザ関数]
         │                │
 ┌───────▼────────────────▼──────────────── カーネル ─────────┐
 │                                                            │
 │  セキュリティ境界: [LSM/BPF (KRSI)] ── フック多数            │
 │  資源境界:        [cgroup hooks] ── sock/dev/sysctl 等      │
 │  スケジューラ:     [sched_ext] ── ポリシー差し替え            │
 │  任意の関数/イベント: [kprobe] [tracepoint] [fentry/fexit]   │
 │                     [perf event (サンプリング)]              │
 │                                                            │
 │  ネットワークスタック:                                        │
 │     socket 層   [socket filter] [sockmap / sk_msg]          │
 │        ▲                                                    │
 │     L3/L4 処理                                              │
 │        ▲                                                    │
 │     tc (traffic control) [tc BPF: ingress/egress]           │
 │        ▲  sk_buff あり                                       │
 │  ───────────────────────────                                │
 │     ドライバ受信路 [XDP] ← sk_buff 割り当て前・最速           │
 └────────▲───────────────────────────────────────────────────┘
          │
        NIC (ハードウェア。XDP offload 対応 NIC は NIC 内実行も)
```

同じ言語・同じ検証器・同じマップ機構が、パケット経路の最下層 (XDP) からセキュリティ判定 (LSM) やスケジューラ (sched_ext) まで、まったく異なる境界に共通に差し込まれる——この**フックの普遍性**が eBPF を単なるパケットフィルタの後継から「カーネルの拡張基盤」へ変えた。

## 技術詳細 (Technical Details)

### 1. 系譜: classic BPF から eBPF へ

- **classic BPF (cBPF)**: McCanne & Jacobson (1993) が tcpdump のために設計した**パケットフィルタ用擬似機械 (pseudo-machine)**。2レジスタ・単純な命令セットのインタプリタで、「パケットを受け入れるか捨てるか」だけを計算する。ユーザ空間へ不要パケットをコピーする前にカーネル内で選別する、という動機は現在の eBPF とすでに同型である。seccomp のフィルタ言語が cBPF なのはこの系譜の名残である（`../virtualization/hardware-virtualization-containers.md` の seccomp-BPF 参照）。
- **eBPF (2014, Linux 3.18〜, Alexei Starovoitov)**: 擬似機械を汎用化した。**64bit レジスタ 10 本 + フレームポインタ**（実マシンのレジスタへ 1:1 で写像しやすく JIT 効率が高い）、命令セットの拡張、**マップ (map)** による状態保持、**ヘルパ関数 (helper function)** によるカーネル機能への型付きアクセス。この時点で「パケットフィルタ」は名前だけになり、実体は**検証可能な汎用カーネル内 VM** となった。

### 2. 検証器 — 本書の心臓部

検証器はロード時 (`BPF_PROG_LOAD`) にバイトコードを静的解析し、以下を**すべての実行パスについて**証明する。証明できなければロード自体を拒否する。

**証明する性質:**

- **メモリ安全性 (memory safety)**: 全レジスタについて「スカラか、どの領域を指すポインタか」という**ポインタ来歴 (pointer provenance)** を追跡し、デリファレンスは「既知の領域 + 境界チェック済みオフセット」の場合のみ許す。パケットポインタは `data_end` との比較を通過した範囲しか読めない。
- **停止性 (termination)**: 制御フローグラフが後方エッジを持たないこと (DAG) を基本とし、ループは**有界 (bounded)** と証明できる形（カーネル 5.3 以降の bounded loop、`bpf_loop` ヘルパ等）のみ許す。カーネルコンテキストで無限ループは即システム停止だからである。
- **カーネルポインタの非漏洩**: カーネルアドレスをそのまま戻り値やマップ経由で非特権ユーザへ返す経路を禁じる（KASLR 迂回の防止）。
- **ヘルパ引数の型検査**: 各ヘルパ関数は「第1引数はマップポインタ、第2引数は境界証明済みメモリ」のような型シグネチャを持ち、呼び出し時点のレジスタ状態がそれを満たすかを検査する。プログラムタイプごとに呼べるヘルパ集合も制限される。

**証明の方法 — 抽象解釈:**

検証器は全パスを模擬実行し、各レジスタの**抽象状態**を追跡する。スカラは値そのものではなく**取りうる範囲**（符号付き/なし境界と、既知ビットを表す **tnum: tristate number**）で表現する。分岐 (`if (x < 64)`) を通ると、その辺の先では x の範囲が絞り込まれ、絞り込まれた範囲がポインタ演算の境界証明に使われる。パス数の爆発は**状態等価性による枝刈り (state pruning)**——「この地点をより一般的な状態で通過済みなら再探索しない」——で抑える。それでも解析には予算があり、命令数上限は初期の約 4K 命令から、特権ロードでは約 1M 命令クラスへ緩和された（カーネル 5.2 前後〜。バージョン・特権により異なる）。処理できる状態数にも上限があり、複雑なプログラムは「正しくても解析予算超過で」落ちる。

**根本的な緊張関係:**

停止性を含む安全性の判定は一般には決定不能 (undecidable) であるため、検証器は**過大近似 (over-approximation)** を取る——危険なものを全部弾くには、証明できない安全なものも弾くしかない。この設計は Gershuni et al. (2019) が形式的に扱ったように、抽象領域の精度と検証コストのトレードオフそのものである。開発者にとっては、コンパイラの最適化が境界チェックを検証器の認識できない形に変形して落ちる、といった事態が日常であり、「検証器に読める形で書く」技法（明示的な境界比較、ループ上限の定数化）が蓄積されている。

### 3. 実行: インタプリタ、JIT、ハードニング

- 検証通過後、バイトコードは**アーキテクチャ別 JIT** (x86-64, arm64, riscv, s390 等) でネイティブコードへ変換される。JIT 無効時はインタプリタ実行だが、主要ディストリビューションは JIT 既定有効 (`net.core.bpf_jit_enable`)、さらにインタプリタ自体を外す `CONFIG_BPF_JIT_ALWAYS_ON` 構成が一般的である（インタプリタは Spectre 系のガジェットになりうるため）。
- **定数ブラインディング (constant blinding)**: 攻撃者が即値に機械語断片を仕込み JIT 出力内に実行可能ガジェットを作る **JIT spraying** への対策として、即値を乱数と XOR した形で埋め、実行時に復元する (`bpf_jit_harden`)。
- **Spectre 緩和は検証器の中にもある**: 投機実行 (transient execution) の下では「アーキテクチャ上は到達しない」パスの読みが可能になるため、検証器はポインタ演算に**境界マスキング**（配列アクセスのインデックスを投機下でも範囲内に収める ALU 演算の挿入）や、投機経路を考慮したパス解析を行う。背景となる過渡実行攻撃の機構は `../../hardware/hardware-security/side-channels-tee-secure-boot.md` を参照。安全性の証明が「アーキテクチャ状態」だけでなく「マイクロアーキテクチャ挙動」まで拡張を迫られた例である。

### 4. プログラムタイプとフック分類

プログラムタイプ (program type) は「どこにアタッチでき、何を入力に受け、どのヘルパを呼べるか」を決める型である。主要系統を次表に示す。

| 系統 | フック | 位置と特徴 |
|---|---|---|
| ネットワーク | **XDP** | ドライバ受信路、**sk_buff 割り当て前**。DROP/PASS/TX/REDIRECT を返す。DDoS 対策・LB で毎秒数百万〜千万パケット級（構成依存; Høiland-Jørgensen et al. 2018） |
| | **tc BPF** | sk_buff 化後の ingress/egress。書き換え・リダイレクトが柔軟 |
| | socket filter / **sockmap** | ソケット単位のフィルタ、ソケット間の直接転送 (L7 プロキシの短絡) |
| トレーシング | **kprobe / uprobe** | ほぼ任意のカーネル/ユーザ関数に動的挿入。ABI 不安定 |
| | **tracepoint** | カーネル定義の静的トレース点。安定だが箇所が限定 |
| | **fentry/fexit** | **BPF トランポリン (trampoline)** 経由で関数出入口に直結 (5.5〜)。kprobe より低オーバーヘッド、BTF で型付き引数 |
| | perf event | サンプリング (CPU プロファイリング) |
| セキュリティ | **LSM/BPF (KRSI)** | LSM フックに BPF で判定ロジックを挿す (5.7〜)。MAC ポリシーのプログラム化 |
| | (seccomp) | cBPF ベースの近縁。syscall 表面の許可リスト |
| 資源境界 | **cgroup hooks** | cgroup 単位で sock 生成・bind/connect・デバイスアクセス・sysctl を制御 |
| スケジューラ | **sched_ext** | スケジューリングポリシー全体を BPF で差し替え (6.12〜) |

軌跡は明確である: パケット経路 → トレース → セキュリティ判定 → 資源制御 → そしてスケジューラという中核サブシステムまで、**カーネルの意思決定点が1つずつ eBPF プラガブルになっている**。sched_ext は「ポリシーはユーザが書き、カーネルは検証と実行だけを担う」という分業の現時点での最前線である。

### 5. マップ — データプレーンと並行性

マップはカーネル内に置かれる型付きキー/バリューストアで、プログラムとユーザ空間の双方から `bpf(2)` 経由でアクセスできる。

- **主要バリアント**: hash / array（固定長・最速）/ **LRU hash**（あふれたら追い出し。フローテーブル等）/ **ringbuf**（カーネル→ユーザへの可変長イベントストリーム、5.8〜。旧 perf buffer の後継）/ prog_array（**tail call** によるプログラム連鎖）/ map-in-map。
- **percpu バリアント**: hash/array には CPU ごとに独立したスロットを持つ percpu 版がある。全 CPU が同一カウンタを更新すると、まさに `../../hardware/cpu-architecture/cache-coherence.md` が示したキャッシュラインのピンポンとアトミック競合がボトルネックになる——percpu マップは「共有をやめて集計を読む側に寄せる」定石の eBPF 版であり、ホットパスの統計はほぼ例外なく percpu で持つ。
- **同期**: マップ本体の参照は **RCU (Read-Copy-Update)** で保護され、読み手はロックなしで走る。要素単位の排他には `bpf_spin_lock`、単調カウンタには `__sync_fetch_and_add`（アトミック RMW）を使う。ここでもコストの序列はキャッシュコヒーレンスの機構がそのまま決める。

概念例として、パケット数を送信元アドレス別に数える XDP プログラムの骨格を示す。

```c
// 例示 (illustrative)。最小の XDP プログラムの骨格。実運用コードではない。
struct {
    __uint(type, BPF_MAP_TYPE_PERCPU_HASH);   // percpu で競合回避
    __type(key, __u32);                        // 送信元 IPv4
    __type(value, __u64);                      // パケット数
    __uint(max_entries, 1024);
} pkt_count SEC(".maps");

SEC("xdp")                                     // SEC() がアタッチ先を宣言
int count_packets(struct xdp_md *ctx) {
    void *data = (void *)(long)ctx->data;
    void *end  = (void *)(long)ctx->data_end;
    struct ethhdr *eth = data;
    struct iphdr  *ip  = data + sizeof(*eth);
    if ((void *)(ip + 1) > end)                // 検証器が要求する境界証明
        return XDP_PASS;
    __u32 src = ip->saddr;
    __u64 one = 1, *cnt = bpf_map_lookup_elem(&pkt_count, &src);
    if (cnt) __sync_fetch_and_add(cnt, 1);
    else     bpf_map_update_elem(&pkt_count, &src, &one, BPF_ANY);
    return XDP_PASS;                           // 判定のみ、通過させる
}
```

`if ((void *)(ip + 1) > end)` の1行が検証器との契約である——この比較がなければ、その先の `ip->saddr` は「境界未証明のパケットメモリ読み」としてロードが拒否される。

### 6. 可搬性 — CO-RE (Compile Once, Run Everywhere)

トレーシング系プログラムはカーネル内部構造体（`task_struct` 等）のフィールドを読むが、そのオフセットは**カーネルのビルドごとに異なる**（バージョン・コンフィグ・パッチ）。

- **旧解 (BCC)**: ターゲットマシンにカーネルヘッダと LLVM を置き、**実行のたびにその場でコンパイル**する。動くが、本番ホストにコンパイラツールチェーンを常駐させ、起動のたびに数百 MB 級のメモリと秒オーダのコンパイル時間を払う。
- **新解 (CO-RE)**: カーネルが自身の全型情報を **BTF (BPF Type Format)** として `/sys/kernel/btf/vmlinux` で公開する（`CONFIG_DEBUG_INFO_BTF`、5.x 系以降の主要ディストリで既定）。開発側は BTF から生成した `vmlinux.h` に対してコンパイルし、フィールドアクセスを**再配置エントリ (relocation)** として記録する。ロード時に **libbpf** が実行先カーネルの BTF を引き、オフセットをその場で解決する。コンパイルは1回、バイナリを配るだけでよい。
- fentry/fexit の型付き引数、LSM/BPF のフックシグネチャ検査など、BTF は可搬性以外にも検証器の型情報基盤になっており、現代 eBPF の事実上の前提である。

### 7. エコシステムの見取り図

| ツール/システム | 領域 | 抽象度 | 主なプログラムタイプ | デプロイモデル |
|---|---|---|---|---|
| **bpftrace** | アドホック観測 | 最高（awk 風 DSL） | kprobe, tracepoint, perf | その場のワンライナー |
| **BCC** | 観測ツール集 | 高（Python + C 断片） | kprobe, tracepoint | 実行時コンパイル（要ヘッダ） |
| **libbpf + CO-RE** | 汎用開発基盤 | 低（C, スケルトン生成） | 全タイプ | 単一バイナリ配布 |
| **Cilium** | K8s ネットワーキング/LB/ポリシー | 高（宣言的設定） | XDP, tc, sockmap, cgroup | クラスタ常駐 (CNI) |
| **Katran** | L4 ロードバランサ | 特化 | XDP | エッジ常駐 (Meta 発) |
| **Falco** | ランタイム脅威検知 | 高（ルール DSL） | tracepoint, kprobe (旧カーネルモジュールから移行) | ホスト常駐エージェント |
| **Tetragon** | セキュリティ観測 + 強制 | 高（K8s CRD） | kprobe, tracepoint, LSM | クラスタ常駐 (Cilium 系) |

上層ほど書きやすく用途が固定され、下層ほど自由で運用が重い。実務では「探索は bpftrace、恒常運用は libbpf/CO-RE 製の常駐エージェント」という住み分けに収束しつつある。

## セキュリティ考察 (Security Considerations)

eBPF は攻撃面を減らす道具であると同時に、それ自体が新しい攻撃面である。両面を対で見る。

- **検証器は単一障害点である**: 安全性の保証は検証器の正しさに全面依存するため、検証器のバグ——範囲追跡の誤り、tnum 演算の符号拡張ミス等——はそのまま「検証済み」の顔をした任意カーネル読み書き、すなわち権限昇格になる。実際に範囲解析の欠陥を突く CVE が繰り返し公表されてきた。この構造ゆえ、主要ディストリビューションは**非特権ユーザからの BPF ロードを既定で無効化**しており (`kernel.unprivileged_bpf_disabled=1` ないし 2)、実質的に eBPF は「root（または `CAP_BPF` 等の分割ケイパビリティ）専用の機構」として運用される。「検証器があるから誰でも安全にロードできる」という初期の理想は、検証器自身のバグ率の前に後退した。
- **Spectre 系の投機ガジェット**: 検証器がアーキテクチャ的安全性を証明しても、投機実行下では棄却されたはずのパスがマイクロアーキテクチャ状態に痕跡を残す。カーネル内に「攻撃者が命令列を選べる」実行環境があること自体がガジェット合成の温床であり、緩和（検証器での境界マスキング、インタプリタ排除、非特権無効化）は `../../hardware/hardware-security/side-channels-tee-secure-boot.md` の過渡実行攻撃の一適用例として読める。
- **フックの追加 = 攻撃面の追加**: 新しいプログラムタイプ・ヘルパ・フックは、それぞれがカーネルへの新しい入力面である。sched_ext のようにカーネルの中核判断を委譲するフックほど、バグや悪意あるポリシーの影響半径は大きい（不公平スケジューリングによる DoS 等。sched_ext はウォッチドッグによる強制切り戻しを備える）。
- **eBPF マルウェア／ルートキットは観測済みの脅威クラスである**: root を取った攻撃者にとって、eBPF は理想的な常駐先になりうる——kprobe でシステムコールの戻りを書き換えて自身を隠蔽し、XDP/tc で C2 トラフィックをソケット層より下で送受信すれば、ホスト上の従来型監視から見えにくい。防御側の要点は**フックの列挙**である: `bpftool prog list` / `bpftool link list` 等でロード済みプログラムとアタッチ点を継続的に棚卸しし、想定外のプログラムを検知する。BPF の監視自体を BPF (LSM フックの `bpf(2)` 監視) で行う再帰的構成も実用されている。
- **防御側の道具としての LSM/BPF**: 従来の MAC (SELinux/AppArmor) が静的ポリシー言語だったのに対し、LSM/BPF は判定ロジックそのものをプログラムできるため、「このコンテナからの `ptrace` を文脈依存で拒否」のような動的ポリシーを、カーネル再構築なしに配備できる。Tetragon 等はこれを観測 (detection) から強制 (enforcement) へ広げつつある。
- **3つの信頼モデルの対比**: (a) **カーネルモジュール** = 全面信頼 (trust fully)——ロード時点からカーネルと同格で、事後の制約はない。(b) **WASM** = 常時サンドボックス (sandbox always)——実行中も境界チェックとメモリ隔離を払い続ける。(c) **eBPF** = 検証してから信頼 (verify then trust)——コストを全部ロード時に前払いし、実行時はネイティブ同然で走る。eBPF の性能はこの前払いの直接の配当であり、脆弱性の構造（検証器バグが即致命傷）も同じ前払いの直接の代償である。

## 結論 (Conclusions)

- eBPF は「カーネルモジュールの速度」と「ユーザ空間の安全性」の二律背反を、**ロード時の機械的証明**で切り抜けた第三の道である。信頼の根拠を主体からコードの性質へ移したことが、カーネル拡張を配布可能なソフトウェアに変えた。
- 中心機構は検証器であり、その設計は健全性のために完全性を捨てる抽象解釈である。「安全なのに弾かれる」開発体験も、「検証器バグが即権限昇格」という脆弱性構造も、非特権 BPF の既定無効化も、すべてこの一点から導かれる。
- フックの地図が示す軌跡は一貫している: パケットフィルタ → 観測 → ネットワークデータプレーン → セキュリティ判定 → スケジューラ。カーネルの意思決定点が順にプラガブルになっており、eBPF は「機構はカーネル、ポリシーはユーザプログラム」という分業の共通基盤になりつつある。
- 隔離スペクトラム上では、gVisor（カーネルロジックをユーザ空間へ）と eBPF（ユーザロジックをカーネルへ）は同じ境界の反対方向の解であり、WASM（常時サンドボックス）を加えた3つの信頼モデル——全面信頼・常時検査・検証後信頼——が、今後のシステム拡張機構を評価する座標軸になる。
