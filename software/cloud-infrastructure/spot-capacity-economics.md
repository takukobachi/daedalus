# スポット市場とクラウドの容量経済 (Spot Markets & Cloud Capacity Economics)

## 概要 (Overview)

クラウドの料金表——オンデマンド・リザーブド (Savings Plans)・**スポット (spot)**——は、値引きの階段ではない。それは「**容量計画のリスクを誰が持つか**」の契約設計である。データセンターの容量は建屋・電力・半導体という長リードタイムの投資であり ([`../../hardware/datacenter-infrastructure/`](../../hardware/datacenter-infrastructure/), [`../../hardware/semiconductor-manufacturing/`](../../hardware/semiconductor-manufacturing/))、供給は年単位でしか動かせない。一方で需要は日次・秒単位で揺れる。この時間スケールの不一致を埋めるのは必ず**誰かが持つ余剰在庫**であり、価格モデルとは、その在庫リスクの配分表に他ならない：長期コミット (リザーブド) は顧客がリスクを引き受けた対価の割引、オンデマンドは事業者がリスクを持つことへのプレミアム、そしてスポットは**余剰在庫を「いつでも回収できる権利」付きで限界費用に近く売る**仕組みである。

本ドキュメントの中心テーゼは 2 つ。(1) スポットは [`serverless-faas-internals.md`](serverless-faas-internals.md) が扱った「アイドルの転売」の、インスタンス粒度・明示的契約版である——FaaS ではプラットフォームが暗黙に行う統計多重化を、スポットでは**中断 (interruption) という契約条項**として顧客に開示し、割引と交換する。(2) ゆえにスポットで安く走れるかどうかは価格交渉の問題ではなく**アーキテクチャの問題**である——状態の外部化・中断への設計・プールの分散という、本領域の他ドキュメントが積み上げた設計原則を守った系ほど、同じワークロードが安くなる。スポット価格は、システムが「クラウドネイティブに設計されているか」を測る計器として読める。分析深度は Level 3。

## 方法論 (Methodology)

- 価格モデルを金融の語彙 (リスク移転・オプション・ポートフォリオ) で読み、技術機構 (中断通知・配分戦略・回収) を「契約の執行機構」として位置づける。
- スポットの価格決定の内部は非公開である。本書は、旧価格モデルをリバースエンジニアリングした独立研究 (ACM TEAC 2013)、現行モデルのベンダー告知 (2017 年の価格モデル変更)、および他社の同型システム (Microsoft の Harvest VM, ATC '20/'21 系) を突き合わせ、**ベンダー提示と独立検証を明示的に区別**する。
- 統計多重化・待ち行列の数理は [`../../foundations/mathematics/probability-statistics/markov-chains-queueing.md`](../../foundations/mathematics/probability-statistics/markov-chains-queueing.md) に、混載クラスタの実測は Borg 論文 ([`container-orchestration-kubernetes.md`](container-orchestration-kubernetes.md) 参考文献) に依拠する。

## 発見事項 (Findings)

1. **クラウドの利益構造は「利用率の裁定」であり、スポットはその末端の在庫処分ではなく設計の一部である。** 事業者はピーク需要 + 成長余裕 + 障害吸収余裕 ([`cloud-control-planes.md`](cloud-control-planes.md) の静的安定性が要求する容量ヘッドルーム) の分だけ物理容量を持たねばならず、定常的に大きな余剰が構造として存在する。この余剰は電力・冷却・減価償却を垂れ流す純コストであり、「いつでも返してもらえる条件付き」で売れるなら限界費用以上の価格はすべて利益改善になる。スポットとは、**静的安定性のために持たされている保険容量を、保険機能を損なわずに (=即時回収権付きで) 収益化する**装置である——可用性設計と価格設計が同じ在庫の裏表になっている。

2. **現行のスポットは市場 (オークション) ではない——「入札の時代」は終わり「中断設計の時代」にある。** 旧モデル (〜2017) は入札価格で割当と追い出しが決まる建前だったが、独立研究 (ACM TEAC 2013) は価格系列の統計から、市場清算ではなくアルゴリズム的な価格生成 (隠れた最低価格からのランダムウォーク的変動) が支配的だった時期を示した——「市場」は演出に近かった。2017 年の改定 (ベンダー告知) で建前も実態に合わせられ、価格は需給を映して緩やかに動く公示価格になり、**中断は価格競争ではなく容量回収**で起きる。利用者の最適戦略は「賢く入札する」から「**中断される前提で設計し、中断されにくいプールを選ぶ**」へ完全に移った。旧時代の入札戦略論は今日では歴史資料である。

3. **中断は「2 分前通知付きの回収権行使」という契約であり、技術要件はそこから逆算される。** 回収の 2 分前に通知 (インスタンスメタデータ / イベント) が来る——この 120 秒が、チェックポイント保存・接続ドレイン・キューへの仕事返却・置き換え起動という**退去プロトコル**の予算である。ここで本領域の原則が総動員される：状態が外部化されていれば ([`serverless-faas-internals.md`](serverless-faas-internals.md) の状態外部化、[`../messaging-streaming/`](../messaging-streaming/) のキューと再配達)、退去は「進行中の仕事を返す」だけで済む。逆に、ローカルディスクに状態を溜め、長時間のインメモリ処理を持つ設計は 120 秒では退去できない——**スポット適合性はワークロードの性質ではなく設計の性質**である。

4. **第一の緩和策は予測ではなく分散である——プール多様化は相関回避の経済版。** スポットの供給は「インスタンスタイプ × AZ」のプール単位で独立に変動し、回収はプール単位で相関する (同型インスタンスの需要増はそのプールを一斉に襲う)。単一プールに全台を置く構成は、[`cloud-control-planes.md`](cloud-control-planes.md) の語彙で言えば相関故障に全額を賭けている。配分戦略 (allocation strategy) が多数のプールへ分散し、価格と回収可能性の複合指標 (price-capacity-optimized、ベンダー提示) でプールを選ぶのは、**シャッフルシャーディングと同じ「相関の破壊」を容量調達に適用したもの**である。中断率の予測に賭けるより、中断の相関を割る方が頑健である——という判断の順序まで含めて同型である。

5. **容量ポートフォリオは金融のそれと同じ構造を持つ。** 実務の定石は層構造である：予測可能なベース負荷は長期コミット (リザーブド/Savings Plans) で最安・確実に、日中変動はオンデマンドで弾力的に、遅延耐性のあるバッチ・スケールアウト分はスポットで最安・不確実に。これは債券 (確実・低利回り)・現金 (流動性)・ハイリスク資産の配分と同じ**リスク・リターン・流動性の三軸配分**であり、「全部スポット」も「全部オンデマンド」も、単一資産への集中投資と同じ理由で誤りである。さらに On-Demand Capacity Reservation (容量の確保だけを買う) と Capacity Blocks (期間指定の確保) は、容量そのものを原資産とする**先物・オプション類似の商品**であり、価格体系が金融商品の品揃えへ収束しつつあることを示す。

6. **オーケストレータへの統合が、スポットを「運用技巧」から「宣言的属性」へ変えた。** Karpenter ([`container-orchestration-kubernetes.md`](container-orchestration-kubernetes.md)) や ASG の混合ポリシーは、「この Pod 群はスポット可・このプールから・中断時は置き換え」という宣言を調停ループに落とし込む——中断通知の受信、ドレイン、代替プール選択、詰め直し (consolidation) が全て自動化される。中断対応が人手の運用である間、スポットの割引は運用コストで相殺されていた。**調停ループが退去プロトコルを内蔵した時点で、スポットの経済性が初めて一般化した**——机上の割引率ではなく「割引 − 中断対応の限界コスト」が実効価格であり、後者を調停ループがほぼゼロにした、と読むのが正確である。

7. **スポットは「余剰がある世界」の産物であり、供給制約下では商品自体が組み替わる。** GPU のような供給制約資源 ([`../../hardware/gpu-accelerators/`](../../hardware/gpu-accelerators/), [`../ml-systems/ml-training-systems.md`](../ml-systems/ml-training-systems.md)) では、前提の「構造的余剰」が消える——余剰がなければスポットに流す在庫がなく、実際に GPU 容量は予約型商品 (期間指定の Capacity Blocks) が主形態になっている (ベンダー提示, 2026-07-30 時点)。これは価格モデルが需給レジームの従属変数であることの実証である：**余剰レジームでは回収権付き安売り (スポット) が成立し、逼迫レジームでは配給 (予約・割当) へ回帰する**。同じ事業者・同じ年に、CPU はスポット豊富・GPU は予約主体という二つのレジームが並存している事実が、本ドキュメントの枠組みの最も分かりやすい検証例になっている。

## アーキテクチャ (Architecture)

### 容量の層とリスクの配分

```
 物理容量 (年単位で固定・長リードタイム)
 ┌────────────────────────────────────────────────────────┐
 │ ← 静的安定性のヘッドルーム (AZ 障害吸収・成長余裕) →       │
 │┌──────────────┬──────────────┬─────────────────────────┐│
 ││ 長期コミット   │ オンデマンド   │ 余剰 = スポットとして販売  ││
 ││ (顧客がリスク) │ (事業者がリスク)│ (回収権付き・限界費用近傍) ││
 │└──────────────┴──────────────┴─────────────────────────┘│
 └────────────────────────────────────────────────────────┘
   需要スパイク/障害 ⇒ 右端から回収 (中断) して左を守る
   = スポットの中断は、オンデマンドの可用性保証の執行機構

 顧客側ポートフォリオ (鏡像):
   ベース負荷 → コミット / 変動分 → オンデマンド / 弾力・バッチ → スポット
```

### 中断のプロトコル — 120 秒の退去

```
 回収決定 ──▶ ① 中断通知 (2分前, IMDS/EventBridge)
                │
                ▼ (調停ループが受信: Karpenter / ASG / 自前エージェント)
             ② 新規の仕事の受付停止 (LB からのデレジスト・キュー購読停止)
             ③ 進行中の仕事の処置:
                 - 冪等・再実行可 → キューへ返却 (visibility timeout / nack)
                 - 長時間ジョブ → チェックポイント保存 (外部ストレージへ)
             ④ 代替容量の起動 (別プール優先 = 相関回避)
             ⑤ 期限到来: インスタンス回収 (猶予は延長されない)
   ②〜④が 120 秒に収まるかは、状態外部化と粒度設計で事前に決まっている
```

## 技術詳細 (Technical Details)

### 1. 旧スポットの解剖 — 「市場」の独立検証

Ben-Yehuda らの研究 (ACM TEAC 2013) は、公開されていた価格履歴だけから旧スポットの内部構造を推定した希少な独立検証である。価格が需給で清算される真の市場なら説明しにくい統計的性質——利用率と独立に見える規則的な変動、頻出する下限価格、疑似乱数的な系列——から、「隠れた最低価格 (reserve price) の上でアルゴリズムが価格を生成していた」時期が支配的だったと結論した。ここから得るべき一般教訓は 2 つ。(a) **ベンダーの語る市場メタファーは仕様ではない**——観測可能な外形 (価格系列・中断率) だけが契約の実体である ([`serverless-faas-internals.md`](serverless-faas-internals.md) の外形測定と同じ姿勢)。(b) プラットフォームの価格機構は変更されうる制度であり、それに過剰適合した最適化 (旧時代の入札ボット) は制度変更で無価値になる——アーキテクチャ側の頑健性 (中断設計) に投資する方が長持ちする。

### 2. 中断率の構造とプール選択

中断率はグローバルな定数ではなく、プール (タイプ × AZ × 時期) の関数である。世代交代期の旧世代プール・特定サイズへの需要集中・リージョン単位の容量イベントが中断を偏らせる。配分戦略の設計判断は「価格最優先 (lowest-price) はしばしば罠」という点に集約される——最安プールは往々にして「需要が薄い理由がある」プールではなく「回収が近い」プールであり、価格と回収可能性を複合評価する戦略 (ベンダー提示の price-capacity-optimized) が実効コスト (中断による再実行・遅延を含む) で勝つ。これは [`cloud-databases-aurora-dynamodb.md`](cloud-databases-aurora-dynamodb.md) の「予測可能性という商品」の裏返しでもある：スポットは予測可能性を売らない商品であり、その欠落分を利用者側の分散設計で補填する契約である。

### 3. ワークロード適合性の判定

スポット適合性は次の 3 問に還元できる。(1) **状態はどこにあるか**——外部 (S3/DB/キュー) なら適合、ローカルなら要改修。(2) **仕事の粒度は 120 秒未満で区切れるか**——リクエスト単位・タスク単位なら適合。長時間ジョブはチェックポイント間隔が実効的な粒度になる ([`../ml-systems/ml-training-systems.md`](../ml-systems/ml-training-systems.md) の分散学習チェックポイントはまさにこの設計)。(3) **遅延・再実行は事業的に許容されるか**——バッチ・CI・レンダリング・ステートレス web (背後に十分な冗長があれば) は許容側、単一障害点・強 SLA のステートフルは非許容側。この 3 問は本領域の設計原則チェックリストと一致する——**スポット化の作業は、実はクラウドネイティブ化の作業と同じもの**であり、割引はその副産物として得られる。

### 4. 他社の同型解 — Harvest VM との対比

Microsoft の Harvest VM (ATC '20/'21 系列の研究) は同じ問題への変種解である：固定サイズのスポット VM を回収する代わりに、**VM のサイズ自体を余剰に合わせて伸縮させる** (最低保証 + 余剰ぶんのコアを動的に付与・剥奪)。全損 (eviction) の頻度を下げ、部分的な資源変動に変える設計であり、「余剰の収益化」という同一目的に対して、AWS は**在庫の単位を固定して存在を不安定に**、Harvest は**存在を固定して単位を不安定に**した——多重化の自由度をどの軸で顧客へ露出するかの選択である。独立の事業者が同じ構造 (余剰の条件付き販売) に到達していること自体が、発見事項 1 の「余剰は構造的に存在する」の傍証になっている。

### 5. 会計の全体像 — 実効コストの式

スポット採用の判定は名目割引率ではなく実効コストで行う。

```
実効コスト = スポット料金
           + 中断による再実行分 (中断率 × 失われる仕事 × 単価)
           + チェックポイント等のオーバーヘッド (I/O・追加ストレージ)
           + 退去・置換の機会費用 (キュー遅延・SLA バッファ)
           + 対応機構の構築運用費 (調停ループ統合で漸近的にゼロへ)
```

複雑さは仮定 (assumption) にある：中断率は非定常でプール依存、失われる仕事はチェックポイント間隔に依存 (間隔を詰めるとオーバーヘッド項が増える——[`../ml-systems/ml-training-systems.md`](../ml-systems/ml-training-systems.md) と同じ最適化)、機会費用は事業要件依存。式自体は単純だが、各項を自分のワークロードで測ってから採用判定する——という規律が、「スポットで 7 割引」という宣伝値 (ベンダー提示・変動する) を工学の入力に変える手続きである。

## セキュリティ考察 (Security Considerations)

- **退去プロトコルは攻撃面でもある。** 中断通知に反応して状態を保存・転送する経路 (チェックポイント先のバケット、キューへの返却) は、120 秒の時間圧の下で走る特権的な処理であり、誤設定 (公開バケットへの checkpoint、暗号化なしの状態ダンプ) が定常運用より起きやすい。退去経路も平時の経路と同じ暗号化・認可 ([`cloud-kms-confidential-computing.md`](cloud-kms-confidential-computing.md), [`cloud-iam-authorization.md`](cloud-iam-authorization.md)) を通す——「緊急時の例外」を作らないことが原則である。
- **スポットの再利用インスタンスに前借主の痕跡はない、が自分の痕跡は残しうる。** ハイパーバイザ層でのメモリ・ストレージのサニタイズはテナント間の基本保証 (ベンダー一次資料) だが、利用者側の責任として、インスタンスストア上の一時データ・スワップに置いた秘密は「回収されるインスタンス」を前提に管理する必要がある——スポットは「インスタンスは突然消える」を明文化した契約であり、消える瞬間にディスク上へ何があるかは利用者の設計に依存する。
- **コスト機構は DoS の増幅器になりうる。** スポット価格・中断率の変動に自動追従する系 (積極的な置き換え・クロスリージョン退避) は、攻撃や障害による需要スパイクを自動購買の連鎖に変換しうる——コスト上限 (budget guard)・置き換えレートの制限は、[`cloud-control-planes.md`](cloud-control-planes.md) のリトライ予算と同じ「正帰還の利得を 1 未満に保つ」機構としてここでも必須である。
- **容量情報は競争・攻撃の情報にもなる。** プールごとの中断率・価格系列は事業者の在庫状態の間接観測であり、独立研究 (ACM TEAC 2013) が示した通り、外形からの内部推定は現実的な精度を持つ。利用者としての含意は「他者も同じ推定をしている」——人気の裁定プール (安くて安定) は発見されると混み、中断相関が上がる。分散戦略が単一の「賢い選択」に常に勝る理由の一つである。

## 結論 (Conclusions)

- クラウドの価格体系は容量リスクの配分契約であり、スポットは静的安定性のための保険容量を回収権付きで収益化する装置である。可用性設計 (ヘッドルーム) と価格設計 (スポット) が同じ物理在庫の裏表だという構図を掴むと、料金表が技術文書として読めるようになる。
- スポットの技術史は「入札の時代」から「中断設計の時代」への転換であり、現在の最適戦略は 3 語で足りる：**外部化・細粒度化・分散**。これは本領域の他ドキュメントが積み上げたクラウドネイティブ設計の原則そのものであり、スポット割引は「正しく設計された系への払い戻し」として機能する。
- 調停ループへの統合 (Karpenter 等) がスポットの実効コストを名目割引に近づけた。中断対応が宣言的属性になった現在、スポットを使わない理由は「ワークロードが本質的に不適合」か「設計が古い」のどちらかに絞られていく。
- ただしスポットは余剰レジームの商品である。GPU に見られる逼迫レジームでは予約型へ回帰する——価格モデルは需給の従属変数であり、特定の商品形態への過剰適合 (制度への過剰適合) より、レジーム変化に耐えるアーキテクチャの頑健性に投資すべきである。旧スポット市場の考古学 (発見事項 2) は、この教訓の最も具体的な証拠として残っている。
