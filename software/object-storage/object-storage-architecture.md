# オブジェクトストレージのアーキテクチャ (Object Storage Architecture)

## 概要 (Overview)

**オブジェクトストレージ (object storage)** は、ファイルシステムでもデータベースでもない第三のストレージ抽象である。提供するのは驚くほど貧しい API——キーを指定してオブジェクト全体を PUT し、キーを指定して GET する——であり、階層ディレクトリも、部分書き換えも、rename もない。だがこの貧しさこそが、単一の名前空間に数百兆オブジェクト・エクサバイト級のデータを保持し、「11 ナイン」の耐久性を謳うシステムを成立させた。S3、Azure Blob Storage、Ceph/RADOS、MinIO はいずれもこの抽象の実装である。

本ドキュメントの中心となる問いは4つ。(1) POSIX ファイルの何を捨てたことが惑星規模 (planetary scale) を買ったのか、(2) キー→物理位置の対応を「索引で引く」(S3) のと「関数で計算する」(Ceph/CRUSH) のとでは何が変わるのか、(3) 複製 (replication) と**イレイジャーコーディング (erasure coding)** はコストの通貨をどう交換しているのか、そして「11 ナイン」という数字はどこから来るのか、(4) S3 が 2020 年に強い一貫性へ移行できたのはなぜか。通奏低音として、オブジェクトストレージは合意・クォーラム・アンチエントロピーといった分散システムの機構一式を、**「ドルあたり耐久性 (durability per dollar)」という経済制約の下で再導出したシステム**である、という視点を採る。分析深度は Level 3。

## 方法論 (Methodology)

- API 面（オブジェクトモデル）と実装面（メタデータ層・データ層）を分離し、「何を保証しないか」から設計を逆算する。POSIX との差分を欠陥ではなく**意図的な放棄**として読む。
- メタデータ層は [`../distributed-systems/consensus.md`](../distributed-systems/consensus.md) の合意と [`../databases/storage-engines.md`](../databases/storage-engines.md) の LSM/WAL を基準系に、データ層は容量経済を基準系に、**別々の座標**で評価する——両者を同じ物差しで測ると設計が読めない。
- 耐久性は [`../../foundations/mathematics/probability-statistics/reliability-theory.md`](../../foundations/mathematics/probability-statistics/reliability-theory.md) の語彙（AFR・直列/並列合成・共通原因故障・MTTR）で定量的に扱い、宣伝値とモデル出力を峻別する。
- 一貫性の語彙は [`../distributed-systems/consistency-models.md`](../distributed-systems/consistency-models.md) から借用し、本稿では再導出しない。
- 一次資料（GFS、Ceph/CRUSH、Dynamo、Reed–Solomon、Azure LRC の各論文）に基づく。

## 発見事項 (Findings)

1. **オブジェクトストレージは POSIX を捨てることで成立した。** rename・部分書き込み・階層ディレクトリは、いずれも複数ノードに跨る**原子性か調整**を要求する——rename は 2 箇所の名前空間更新の原子化、部分書き込みは byte-range のロックと順序付け、ディレクトリは親子間の整合である。これらを全部捨て、「不変オブジェクトの全体 PUT/GET ＋ フラットなキー空間」に絞ると、各オブジェクトが独立した単位になり、調整なしに水平分割できる。スケールは機能追加ではなく**機能削除**で買われた。
2. **メタデータ層こそが分散システムであり、データ層は倉庫である。** キー→オブジェクト位置の索引は、小さいが一貫性・可用性・順序のすべてを要求する——ここに合意・複製・パーティショニングという分散システムの難所が凝縮される。一方バルクデータは、位置さえ索引が知っていればどこに置いてもよい不変の塊であり、チェックサムと修復だけが仕事の「倉庫」になる。GFS のマスタ／チャンクサーバ分離以来、この**制御平面と物理平面の非対称**がオブジェクトストレージの基本形である。
3. **Ceph/CRUSH は「探すな、計算せよ」という逆張りである。** CRUSH はキー（正確には placement group）から配置先 OSD 群を**決定的な擬似乱数関数で計算**し、中央索引そのものを消す。クライアントは誰にも聞かずに読み書き先を知る——代償は「個別オブジェクトを任意の場所に置く自由」の喪失であり、配置変更はマップ（クラスタ記述）の版数更新として全体に波及する。索引方式とは、メタデータのスケール問題を**データ移動の問題に変換**したのだと読める。
4. **イレイジャーコーディングは耐久性を容量ではなく計算と帯域で買う。** 3 複製は 3.0 倍の容量で 2 故障に耐える。Reed–Solomon の RS(k=6, m=3) は 1.5 倍の容量で 3 故障に耐える——容量効率は圧倒的だが、1 断片の修復に k 断片分の読み出しと転送が要る（**修復増幅 (repair amplification)**）。複製の修復は 1 倍読めば済む。すなわち EC は、日常の容量コストを削る代わりに、故障時の計算（Galois 体上の行列演算）とネットワーク帯域、そして修復時間の延伸（＝脆弱窓の拡大）を支払う契約である。Azure の LRC が局所パリティを足したのは、まさにこの修復コストを買い戻すためである。
5. **「11 ナイン」は測定値ではなくモデルの出力である。** 年間 10⁻¹¹ のオブジェクト喪失確率を実測するには宇宙年齢級の観測が要る。実際の数字は、ディスクの年間故障率 (AFR)・修復時間 (MTTR)・ストライプ幅から「修復が終わる前に m+1 台目が壊れる確率」を計算するマルコフモデルの出力であり、**故障の独立性を仮定**している。ファームウェアの共通バグ、同一ロット、ラック電源、AZ 単位の災害——共通原因故障 (common cause failure) はこの仮定を破る側にしか働かない。だからこそ実装は故障ドメイン (failure domain) を跨いだ配置でモデルの前提を現実に近づけようとする。
6. **静かなデータ破損が最終ボスであり、対策は端から端までのチェックサムと巡回である。** 喪失はディスク故障だけでなく、ビット腐敗・誤った上書き・ファントム書き込みという**申告なき破損 (silent corruption)** からも来る。冗長性は「どのコピーが正しいか」を知らなければ役に立たない——オブジェクト単位のチェックサムを書き込み時に固定し、読み出し時に検証し、さらに読まれないデータも**スクラビング (scrubbing)** で定期巡回する。アンチエントロピーの一形態であり、耐久性は置いた瞬間ではなく**巡回し続けることで維持される**。
7. **強い一貫性は後付けできる——ただしメタデータ層の作り直しと引き換えに。** S3 は 14 年間、上書き PUT 後の GET が古い値を返しうる結果整合性で運用し、2020 年に全操作を強い read-after-write へ移行した。API は 1 バイトも変わっていない——変わったのはメタデータ層で、キャッシュ・複製経路を含む索引の更新に全順序と可視性の保証を入れる作り直しである。一貫性がデータ層でなくメタデータ層の性質であること（発見事項 2）の、最も雄弁な実証である。

## アーキテクチャ (Architecture)

### 二層構造 — 索引と倉庫

```
  Client
    │  PUT /bucket/key  (whole object + checksum)
    ▼
 ┌───────────────┐      ┌─────────────────────────────┐
 │ API Gateway / │─────▶│ Metadata service            │  key → {stripe locations,
 │ Front-end     │      │  (partitioned index,        │        version, checksum}
 └──────┬────────┘      │   consensus-replicated)     │  ← ここが分散システムの本体
        │               └─────────────────────────────┘
        │ EC encode: object → k=4 data + m=2 parity fragments
        ▼
  Failure domain A     Failure domain B     Failure domain C   (rack / AZ)
 ┌──────┬──────┐      ┌──────┬──────┐      ┌──────┬──────┐
 │ d1   │ d2   │      │ d3   │ d4   │      │ p1   │ p2   │   ← 1 ストライプを
 └──────┴──────┘      └──────┴──────┘      └──────┴──────┘     ドメイン跨ぎで配置
   任意の 4 断片から復元可能 (RS(4,2)) — 1 ドメイン全損に耐える
```

- 読み出しは索引を引いて任意の k 断片を取得・復号する。修復 (repair) は故障検知後に残存断片から欠損分を再計算する**背景フロー**であり、前景 I/O と帯域を取り合う。
- 故障ドメインの階層（ディスク < ノード < ラック < AZ）は [`../../engineering/datacenters/datacenter-fundamentals.md`](../../engineering/datacenters/datacenter-fundamentals.md) の物理設備そのものである。

### 分岐点 — 中央索引 vs 計算配置

| 軸 | S3 型（パーティション化索引） | Ceph（CRUSH 計算配置） |
|---|---|---|
| key→位置の解決 | 索引サービスに問い合わせ | クライアントが関数で計算 |
| メタデータの実体 | 合意複製された分散索引（要スケール運用） | クラスタマップのみ（小さく、版数管理） |
| 配置の自由度 | オブジェクト単位で任意（移行・階層化が容易） | 関数の出力に拘束（個別移動は不可） |
| ホットスポット | キー接頭辞に偏るとパーティションが焼ける | ハッシュで均等散布（意図的な局所化は不可） |
| クラスタ変更 | 索引書き換えのみ（データ移動は任意） | マップ更新が**データ再配置を必然的に伴う** |
| 障害点 | 索引サービスの可用性が全体を律速 | モニタ群（マップの合意）だけが要衝 |

どちらが優れているかではなく、**メタデータをどこで払うか**の分岐である——問い合わせのたびに払うか、再配置のときにまとめて払うか。

## 技術詳細 (Technical Details)

### 1. オブジェクトモデル — 不変性・マルチパート・バージョニング

- オブジェクトは**キーと不変の値の対**であり、更新は常に「新しい値の全体 PUT」＝新バージョンの作成である。POSIX の「開いて、シークして、一部を書く」は存在しない。`/` を含むキーで疑似階層を演出するが、それは索引上の接頭辞検索にすぎず、ディレクトリという実体はない——「フォルダの rename」がオブジェクト数に比例するコピーになるのはこのためである。
- **マルチパートアップロード (multipart upload)**: 巨大オブジェクトをパートに分割して並列・再試行可能にアップロードし、最後の complete 呼び出しで**原子的に 1 オブジェクトとして出現**させる。部分書き込みの再導入ではなく、「見えるのは常に完成品だけ」という不変条件を守ったまま転送だけを分割する設計である。
- **バージョニング (versioning)**: 上書きと削除を「新バージョンの追記」に変換する。不変オブジェクトの列としてのバケットは追記専用ログの親戚であり、誤削除・ランサムウェア対策（セキュリティ考察）の土台になる。

### 2. メタデータ層 — 索引のスケーリングとその放棄

- S3 型の索引はキー範囲でパーティション化された分散 KV であり、その各パーティションの実体は [`../databases/storage-engines.md`](../databases/storage-engines.md) の LSM-tree ＋ WAL である——オブジェクトストレージの中心部でストレージエンジンがそのまま再利用されている。パーティションの複製と分割・移動の調整は [`../distributed-systems/consensus.md`](../distributed-systems/consensus.md) の合意の仕事である。
- **ホットスポット**: 辞書順パーティショニングでは、単調増加するキー接頭辞（日付、連番）が最後尾パーティションに書き込みを集中させる。S3 が長年「キーの先頭にランダム性を」と案内し、後に接頭辞単位の自動分割で緩和したのは、この索引の物理を API 利用者が透かし見ていた例である。
- **CRUSH**: オブジェクト→placement group→OSD 群を、クラスタマップと重み付き階層（ラック・ホスト）を入力とする決定的関数で導く。故障ドメイン制約（「レプリカは異なるラックへ」）は関数の探索規則として表現される。マップは小規模なモニタ群が Paxos 系合意で管理する——中央索引を消しても、**合意はより小さな制御平面に凝縮されて残る**。分散ログのデータ平面/制御平面の階層化（[`../messaging/distributed-logs-delivery-semantics.md`](../messaging/distributed-logs-delivery-semantics.md) 発見事項 3）と同じ構図である。

### 3. 耐久性の工学 — 複製・EC・ナインズの算術

- **Reed–Solomon 符号**: データ k 断片から Galois 体 GF(2⁸) 上の多項式演算でパリティ m 断片を生成し、任意の k 断片から全体を復元できる（**MDS 符号**——同じ冗長量で理論上最良の耐故障数）。体が有限体である点が要で、実数上の行列分解の数値誤差問題は存在せず、演算は正確かつテーブル駆動で高速化できる。
- **コストの通貨換算**: 3 複製は容量 3.0 倍・修復読み出し 1 倍・任意 2 故障耐性。RS(6,3) は容量 1.5 倍・修復読み出し 6 倍・任意 3 故障耐性。RS(12,4) なら容量 1.33 倍だが修復はさらに重い。**ストライプを広げるほど容量は安く、修復は高くなる**。Azure の LRC(12,2,2) はグループ局所パリティで単一故障（圧倒的多数派）の修復読み出しを 6 断片に抑えつつ 1.29 倍を達成した——「単一故障を安く、多重故障は稀だから高くてよい」という故障分布への最適化である。
- **ナインズの算術**: 耐久性はマルコフモデル「健全 → 1 故障 → … → m+1 故障（喪失）」の年間吸収確率として計算される。パラメータは AFR（実測でおよそ 1–2%/年）、修復時間、ストライプ数。修復が速いほど多重故障の窓が狭まる——**耐久性は MTTR の関数**であり、「壊れない部品」より「速い修復」が効くという [`../../foundations/mathematics/probability-statistics/reliability-theory.md`](../../foundations/mathematics/probability-statistics/reliability-theory.md) の教えの実装である。10 万台規模ではディスク故障は毎日の定常負荷であり、修復・リバランスは例外処理ではなく常時流れる背景トラフィックとして帯域予算を持つ。
- **前提の脆さ**: モデルは故障の独立を仮定するが、実際の喪失事故は相関故障——同一ファームウェア、同一 AZ、ソフトウェアのバグ——から来る。故障ドメイン跨ぎの配置は独立性の仮定を「買う」ための支出であり、AZ 跨ぎ複製はその最上位である。媒体自体の摩耗と内部冗長は [`../../hardware/storage/nand-flash-ftl.md`](../../hardware/storage/nand-flash-ftl.md) が扱う下層の同型問題である。
- **スクラビング**: 全データを周期的に読み、チェックサムを検証し、不一致を冗長性から修復する。検出されない破損は AFR に現れない喪失経路であり、巡回周期はモデルの「検知遅れ」項として耐久性に直接効く。

### 4. 一貫性 — 結果整合性からの卒業と条件付き書き込み

- 語彙は [`../distributed-systems/consistency-models.md`](../distributed-systems/consistency-models.md) の通り。初期の S3 は上書き PUT に対して結果整合性——キャッシュされた索引エントリが古い位置を返しうる——であり、利用者はリトライやマニフェストファイルで回避していた（Hadoop 系の "S3Guard" は外部 DB で索引を二重化する補装具だった）。2020 年の移行で全 GET/PUT/LIST が強い read-after-write になり、この補装具群は一夜で不要になった。
- 移行の実体はメタデータ層への**全順序の導入**である——索引更新の複製・キャッシュ可視性を、書き込み確認応答の時点で読み経路全体に保証する。可用性・性能を落とさずにこれを行うことが工学的達成であり、「強い一貫性は高くつく」の高さは固定費ではなく設計変数であることを示した。
- **条件付き書き込み (conditional write)**: `If-Match: <etag>` / `If-None-Match: *` による compare-and-swap。オブジェクトストレージ上に Iceberg 等のテーブル形式がトランザクションを組み立てる際の原子性プリミティブであり、強い一貫性と併せて「オブジェクトストレージをデータベースの土台にする」動きの前提条件である。

### 5. スケールアウトの機構 — 散らし、直し、沈める

- **負荷分散**: フロントエンドは無状態で水平複製、索引はパーティション分割・自動再分割、データはストライプ単位で全ノードに散布される。単一オブジェクトのホットスポットは断片の追加複製やキャッシュ層で吸収する。
- **リバランス**: ノード追加・故障・偏り是正に伴うデータ移動は、修復と同じ背景フロー基盤に載る。前景レイテンシと修復速度（＝耐久性）の綱引きであり、帯域スロットリングは性能設定ではなく**耐久性設定**である。
- **LIST の非対称**: GET/PUT がデータ層に散る一方、接頭辞列挙 (LIST) は索引の範囲走査であり、メタデータ層だけに負荷が集中する。「LIST は高い」という運用上の経験則は二層構造の直接の帰結である。
- **コールドティア（概観）**: アクセス頻度に応じてより広いストライプ・より遅い媒体（HDD、テープ級アーカイブ）へ沈める。取り出し遅延と引き換えに容量単価を下げる——「ドルあたり耐久性」の最適化を温度軸に拡張したものであり、階層間の移動もまた背景フローである。

## セキュリティ考察 (Security Considerations)

- **公開バケット誤設定はクラウド侵害の古典類型である**: 認証情報の窃取すら不要で、設定ミス一つで全データがインターネットに開く。数億件規模の漏えい事例が繰り返され、プロバイダ側の対策は「デフォルト非公開・公開ブロックのアカウント単位強制・公開状態の常時表示」へと、**設定の失敗を難しくする方向**に進化した。ポリシーは IAM（プリンシパル側）とバケットポリシー（リソース側）の合成で評価され、明示 Deny が常に勝つ——この評価順序の理解が監査の前提である。
- **署名付き URL (presigned URL)**: 資格情報の委譲なしに「この URL を知る者に、この操作を、この期限まで」許すケイパビリティ型の権限付与。便利さの裏で、URL がログ・リファラ・チャットに漏れればそのまま権限漏えいになる——短い有効期限と操作の最小化が規律である。
- **暗号化と鍵管理**: 転送は TLS、保存時はサーバ側暗号化（プロバイダ管理鍵／KMS 顧客管理鍵／顧客提供鍵）の選択。脅威モデルの違い——プロバイダをどこまで信頼するか——が鍵の置き場所を決める。クライアント側暗号化は最強だが、メタデータ層の機能（サーバ側の検索・処理）を放棄する。
- **オブジェクトロックと不変性**: WORM (write once read many) モードは、バージョニングの上に「保持期間中は誰も（管理者も）削除・上書きできない」を載せる。ランサムウェアの暗号化上書きとバックアップ削除への実効的防御であり、監査・規制対応（改竄不能な証跡）の要件でもある。不変性はここでは性能の道具ではなく**セキュリティ境界**である。
- **マルチテナント分離**: 同一物理基盤に全顧客のデータが同居する以上、分離はメタデータ層のアクセス制御と暗号化の正しさに全面依存する。テナント単位のクォータ・レートリミットは、隣人の暴走（大量 LIST、修復帯域の圧迫）から可用性を守る機構としてセキュリティの一部である。

## 結論 (Conclusions)

- オブジェクトストレージは POSIX の原子性・階層・部分更新を捨てることで、オブジェクトを独立な分割単位に変え、惑星規模の水平分割を可能にした。抽象の貧しさは欠陥ではなく購入代金である。
- システムの本体はキー→位置の索引（メタデータ層）にあり、合意・パーティショニング・LSM という既知の分散システム部品がそこに凝縮される。データ層は不変断片の倉庫であり、チェックサムと背景修復が守る。CRUSH は索引自体を関数に置き換える対極の設計だが、合意は制御平面に残る。
- 耐久性の設計は経済の設計である。EC は容量を計算と修復帯域で買い、LRC は故障分布に合わせて修復を買い戻す。「11 ナイン」は独立故障を仮定したモデルの出力であり、実務の仕事はその仮定（故障ドメイン、スクラビング、修復速度）を現実の側から支えることにある。
- S3 の 2020 年の強一貫性移行は、一貫性がメタデータ層の性質であることの実証であり、条件付き書き込みと併せてオブジェクトストレージを「データレイクの土台」へ押し上げた。
- 総じてオブジェクトストレージは、分散システムの機構一式——合意、クォーラム、アンチエントロピー、背景修復——を「ドルあたり耐久性」という単一の経済目的関数の下に編成し直したシステムである。
