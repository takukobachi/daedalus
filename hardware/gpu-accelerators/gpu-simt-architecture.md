# GPU アーキテクチャと SIMT 実行モデル (GPU Architecture & SIMT Execution)

## 概要 (Overview)

CPU とGPU は、同じ**メモリウォール (memory wall)**——演算は速くなるがメモリは遅いまま——への、正反対の答えである。CPU は**レイテンシ指向 (latency-oriented)**: 大容量キャッシュ・アウトオブオーダ実行 (out-of-order)・分岐予測 (`../cpu-architecture/pipeline-superscalar-ooo.md`) にダイ面積を投じ、**1本のスレッドを待たせない**ことに全力を注ぐ。GPU は**スループット指向 (throughput-oriented)**: それらの機構をほぼ捨て、浮いた面積を ALU とレジスタに転用し、**数万スレッドを同時に飛ばしてメモリ待ちを「隠す」**。あるスレッド群がメモリ待ちなら、別のスレッド群を走らせればよい——個々のスレッドは遅くてよく、総量だけを最大化する設計である。

この方式が成立するのは、対象が**データ並列 (data parallelism)** ——同じ演算を大量の要素へ一様に適用する処理（グラフィックス、行列演算、深層学習）——に限られるからである。本ドキュメントは、この設計反転を軸に、**SIMT (Single Instruction, Multiple Threads)** 実行モデルと分岐発散 (branch divergence)、SM (Streaming Multiprocessor) のマイクロアーキテクチャと**占有率 (occupancy)**、HBM を頂点とするメモリ階層とコアレッシング (coalescing)、Tensor コアと専用化のスペクトラム、ホスト-デバイス間インターフェイスまでを整理する。CPU 側の SIMD (`../cpu-architecture/simd-vector.md`) との対比、software 側の ML システム分析との接続を意識した構成とする。数値は世代・実装で大きく変動するため、絶対値ではなく**桁感 (order of magnitude)** を基準とする。

## 方法論 (Methodology)

- CPU を基準に置き、GPU を「何を捨て、何にダイ面積を再配分したか」の**差分**として説明する。個々の機構を暗記事項ではなく、スループット指向という単一の設計判断の帰結として導く。
- 実行モデル (SIMT)・マイクロアーキテクチャ (SM)・メモリ階層 (HBM)・専用演算器 (Tensor コア)・ホスト接続 (PCIe/NVLink) の5層に分解し、各層で「レイテンシ隠蔽」と「帯域」がどう現れるかを追う。
- 性能判定の共通言語として **Roofline モデル**と**演算強度 (arithmetic intensity, FLOP/byte)** を使い、計算律速 (compute-bound) かメモリ律速 (memory-bound) かで議論を分ける。
- 用語は NVIDIA 系（ワープ、SM）を主とし、AMD 系（ウェーブフロント、CU）を併記する。数値はベンダ公称値 (spec) か実測 (measured) かを都度区別し、精密なベンチマーク値は主張しない。
- 比較対象として TPU 級の行列専用アクセラレータを置き、「汎用 GPU → 行列特化 → 固定機能」の専用化スペクトラム上で GPU の位置を定める。

## 発見事項 (Findings)

1. **GPU はメモリウォールへの「もう一つの答え」である。** CPU はキャッシュと投機でレイテンシを**避け**、GPU は超多スレッドでレイテンシを**隠す**。どちらも「メモリは遅い」という同じ物理的制約から出発しており、違いは対象ワークロードの並列度の仮定だけである。データ並列が十分にあれば、制御機構に使う面積を ALU に回した方がスループットは高い。

2. **SIMT は「SIMD ハードウェアにスレッドの顔をさせる」実行モデルである。** プログラマは1スレッド分のスカラコードを書き、ハードウェアが32スレッド（**ワープ (warp)**; AMD は 64 の**ウェーブフロント (wavefront)**）を1命令で束ねて SIMD 的に実行する。明示的なレーン操作 (`../cpu-architecture/simd-vector.md`) が不要になる代わりに、その幻想の代金は**分岐発散 (branch divergence)** で払う——ワープ内で分岐が割れると両経路を逐次実行し、実効レーン利用率が落ちる。

3. **GPU ではレジスタファイルがキャッシュより大きい——これが設計反転の最も端的な現れである。** SM あたりのレジスタファイルは 256KB 級（世代依存の公称値）で、L1/共有メモリより大きい。数十ワープ分の全コンテキストをレジスタに**常駐**させておくことで、ワープ切替を**ゼロコスト (zero-cost context switch)** にし、メモリ待ちの瞬間に別ワープへ切り替えられる。常駐ワープ数＝**占有率 (occupancy)** が、レイテンシ隠蔽の予算そのものである。

4. **実効メモリ帯域はアクセスパターンが決める。** ワープ内32スレッドのアクセスが連続していれば少数のトランザクションに**コアレッシング (coalescing)** されるが、散らばれば最大32倍のトランザクションに割れる。HBM が TB/s 級（スタックあたり、HBM3(E) の公称値）の帯域を提供しても、コアレッシングと共有メモリの**バンクコンフリクト (bank conflict)** を外すと、その大半は失われる。GDDR/HBM は一貫して「レイテンシを犠牲に帯域を買う」DRAM である。

5. **Tensor コアは「行列積だけが専用化に値する」という Roofline 上の判断である。** 密行列積 (GEMM) は演算強度が行列サイズと共に伸びる稀有なカーネルで、演算器を増やすほど速くなる（計算律速に留まる）。だから FP16/BF16/FP8/INT8 の**混合精度 (mixed precision)** 行列演算器を固定機能的に置く価値がある。この論理を推し進めた極点がシストリックアレイ (systolic array) の TPU であり、GPU → TPU → 固定機能 NPU は「柔軟性を売って効率を買う」連続したスペクトラムを成す。

6. **最大のボトルネックはしばしば GPU の外——ホストとのデータ移動——にある。** PCIe の数十 GB/s に対し HBM は数 TB/s と、桁で2つ違う（世代依存）。カーネルがどれだけ速くても、データが PCIe を往復すれば計算は転送に埋もれる。NVLink・ユニファイドメモリ・そして「データを GPU に置いたままにする」ソフトウェア設計は、すべてこの断崖への対処である (`../hw-sw-interface/bus-interconnect.md`)。

## アーキテクチャ (Architecture)

### GPU 全体の俯瞰

GPU は SM (Streaming Multiprocessor; AMD では CU: Compute Unit) の複製の集合体である。各 SM が独立にワープ群を実行し、L2 と HBM を全 SM で共有する。

```
  Host CPU ══ PCIe / NVLink ══╗
                              ▼
  ┌─────────────────── GPU ─────────────────────┐
  │  ┌────┐ ┌────┐ ┌────┐        ┌────┐          │
  │  │SM 0│ │SM 1│ │SM 2│  ...   │SM N│  (数十〜百超, 世代依存)
  │  └──┬─┘ └──┬─┘ └──┬─┘        └──┬─┘          │
  │     └──────┴───┬──┴────────────┘             │
  │          ┌─────▼──────┐                       │
  │          │  共有 L2    │  (数十MB級)           │
  │          └─────┬──────┘                       │
  └────────────────┼─────────────────────────────┘
             ┌─────▼──────┐
             │HBM スタック │ ×4〜8 (2.5D インターポーザ上)
             └────────────┘
```

CPU のコアに相当する複製単位は SM だが、性格が違う。CPU コアは「1〜2スレッドを最速で」、SM は「数十ワープ（千スレッド超）を同時に住まわせて」動く。

### SM の内部構成

```
  ┌──────────────── SM (Streaming Multiprocessor) ────────────────┐
  │                                                                │
  │  ┌──────────────┐  ┌──────────────┐   ← ワープスケジューラ×4  │
  │  │Warp Scheduler│  │Warp Scheduler│ ...  毎サイクル、発行可能な │
  │  │ + Dispatch   │  │ + Dispatch   │      ワープを選んで発行     │
  │  └──────┬───────┘  └──────┬───────┘                            │
  │         ▼                 ▼                                    │
  │  ┌───────────────────────────────────────────┐                 │
  │  │   レジスタファイル (register file)          │ ← 256KB/SM 級  │
  │  │   全常駐ワープのコンテキストを常時保持       │   (L1より大きい)│
  │  └──────┬──────────┬──────────┬───────────────┘                │
  │         ▼          ▼          ▼                                │
  │  ┌──────────┐ ┌─────────┐ ┌──────────┐ ┌────────────────┐     │
  │  │ INT/FP32 │ │  FP64/  │ │ LD/ST    │ │ Tensor Core    │     │
  │  │ ALU ×32  │ │  SFU    │ │ ユニット  │ │ (行列積演算器)  │     │
  │  │ (レーン)  │ │         │ │          │ │                │     │
  │  └──────────┘ └─────────┘ └──────────┘ └────────────────┘     │
  │  ┌───────────────────────────────────────────┐                 │
  │  │  共有メモリ / L1 (shared memory, ~100-228KB │ ← SW管理       │
  │  │  級で分割可変, 32バンク構成)                 │   スクラッチパッド│
  │  └───────────────────────────────────────────┘                 │
  └────────────────────────────────────────────────────────────────┘
```

要点:

- **ワープスケジューラ (warp scheduler)**: 毎サイクル、常駐ワープの中から「次の命令が発行可能な（オペランドが揃いストールしていない）」ワープを選んで発行する。CPU のアウトオブオーダ実行が**1スレッド内**の命令を並べ替えて待ちを埋めるのに対し、GPU は**別スレッド（ワープ）**の命令で埋める。並べ替えハードウェア（リオーダバッファ等）が不要になる分、面積を ALU に回せる。
- **レジスタファイル**: 数字の逆転に注意。CPU はレジスタ数 KB : キャッシュ数十 KB〜MB、GPU の SM はレジスタ 256KB 級 : L1 は同等以下。キャッシュで「待ちを減らす」のではなく、レジスタで「待てるスレッドを大量に飼う」ことに容量を使う。
- **共有メモリ (shared memory)**: ハードウェアが自動管理するキャッシュではなく、**ソフトウェア管理のスクラッチパッド (software-managed scratchpad)**。スレッドブロック内で明示的にデータを置き、再利用する。タイル化行列積のように再利用構造が既知のカーネルでは、キャッシュの推測より確実に局所性を回収できる。

## 技術詳細 (Technical Details)

### 1. SIMT 実行モデルと分岐発散 (SIMT & Branch Divergence)

**SIMD との違い**は抽象の置き場所にある。CPU SIMD (`../cpu-architecture/simd-vector.md`) ではプログラマ／コンパイラがレーンを明示的に扱う（幅がコードに現れる）。SIMT ではプログラマは**1スレッドのスカラコード**を書き、ハードウェアが32スレッドを1ワープに束ね、1命令を32レーンで実行する。マスク処理・端数処理・gather/scatter が「スレッドごとの通常のロード／分岐」として自然に書ける——これが CUDA のプログラマビリティの核心である。

ただしハードウェアの実体は SIMD なので、ワープ内で分岐の行き先が割れると（**分岐発散**）、両経路を**アクティブマスク (active mask)** で部分実行するしかない。

```
  // if (tid % 2 == 0) { A; } else { B; }  をワープ(幅8で図示)が実行
  時刻   実行   アクティブマスク      実効レーン利用率
   t0   分岐    11111111   ← 条件評価は全レーン
   t1    A      10101010   ← 偶数スレッドのみ有効, 奇数は待機   4/8
   t2    B      01010101   ← 奇数スレッドのみ有効, 偶数は待機   4/8
   t3   再収束  11111111   ← reconvergence point で合流       8/8

  発散した区間は A と B を「順番に」実行するため、
  最悪 (32方向に発散) では実効スループットが 1/32 に落ちる。
```

- **Volta 以前**: 発散はハードウェアの**再収束スタック (reconvergence stack)** で管理され、ワープは単一のプログラムカウンタ (PC) を共有した。経路を出し切って合流点 (immediate post-dominator) で戻る方式で、**ワープ内スレッド同士がロックを取り合うと死ぬ**（片方の経路が進まないともう片方も進めない）という制約があった。
- **Volta 以降 (independent thread scheduling)**: スレッドごとに PC とコールスタックを持ち、発散した経路をインターリーブ実行できる。ワープ内の細粒度同期が正しく前進するようになったが、**発散のスループットコスト自体は消えない**（1サイクルに実行できるのは依然1経路）。また暗黙のワープ同期 (lockstep) を仮定した旧コードは `__syncwarp()` 等の明示同期が必要になった。
- 実務的帰結: 発散はワープ境界 (32) を単位に起きるため、条件分岐がワープ内で揃うよう（スレッド ID の連続範囲で分かれるよう）データとスレッドの対応を設計するのが定石である。

### 2. 占有率とレイテンシ隠蔽 (Occupancy & Latency Hiding)

レイテンシ隠蔽の成立条件は単純な算数である。メモリレイテンシが数百サイクル（桁感）で、ワープが数サイクルおきに命令を発行できるなら、**待ち時間を埋めるには数十ワープの「待機列」が要る**。SM に常駐できるワープ数の上限に対する実際の常駐数が**占有率 (occupancy)** である。

常駐ワープ数を制限するのは SM の有限資源の分配である:

```
  常駐ワープ数 = min( レジスタファイル容量 / (1スレッドのレジスタ数 × 32),
                      共有メモリ容量 / ブロックあたり使用量 × ブロックサイズ換算,
                      ハードウェア上限 (スロット数) )
```

- 1スレッドが多くのレジスタを使うカーネルは、常駐ワープが減り、メモリ待ちを隠せなくなる（**register pressure** と occupancy のトレードオフ）。逆に占有率 100% が常に最適でもない——レジスタや共有メモリを厚く使って1スレッドあたりの仕事を増やす方が速いカーネルもある。占有率は「レイテンシ隠蔽の予算」であって目的関数ではない。
- **ゼロコストコンテキストスイッチ**: CPU のスレッド切替はレジスタ退避／復帰を伴うが、GPU は全常駐ワープのレジスタが**最初からレジスタファイル上にある**ため、切替はスケジューラの選択変更だけで済む。巨大レジスタファイルはこの「退避しない」設計の対価である。

### 3. メモリ階層: レジスタ → 共有メモリ → L2 → HBM

| 階層 | 管理 | 桁感 | 備考 |
|---|---|---|---|
| レジスタ | コンパイラ | 256KB/SM 級, ~1サイクル | スレッド私有 |
| 共有メモリ / L1 | ソフトウェア / HW | ~100-228KB/SM 級, 数十サイクル | ブロック内共有, 32バンク |
| L2 | ハードウェア | 数十 MB 級, ~百サイクル級 | 全 SM 共有 |
| HBM (デバイスメモリ) | — | 数十〜百数十 GB, 数百サイクル, 数 TB/s | 帯域重視 DRAM |

（容量・レイテンシは世代・実装依存の桁感。帯域はベンダ公称値ベース。）

- **コアレッシング (coalescing)**: メモリシステムはワープ単位でアクセスを見て、32スレッドのアドレスが連続・整列していれば少数の広いトランザクション（32B/64B/128B セグメント）に併合する。ストライドアクセスや散乱アクセスはトランザクション数が膨らみ、実効帯域が数分の一〜数十分の一に落ちる。CPU の「キャッシュラインをまたぐな」に相当する第一級の最適化対象であり、AoS→SoA 変換が効くのも同じ理屈である。
- **バンクコンフリクト (bank conflict)**: 共有メモリは32バンクに分かれ、ワープ内のアクセスが別バンクに散れば1サイクルで並列処理される。同一バンクの別アドレスに複数スレッドが当たるとアクセスが直列化する。タイル配列に+1パディングを入れる古典的技法はこの回避策である。
- **なぜ GDDR/HBM か**: 汎用 DDR はレイテンシと容量のバランス型だが、GPU はレイテンシをスレッドで隠せるため、**レイテンシを捨てて帯域に全振り**した DRAM を選ぶ。**HBM (High Bandwidth Memory)** は DRAM ダイを垂直積層 (3D stacking) し TSV (Through-Silicon Via) で結び、**2.5D シリコンインターポーザ (interposer)** 上で GPU ダイと数千本級の超広幅バスで接続する。ピン数の制約をパッケージ内配線で回避する設計で、HBM3/HBM3E はスタックあたり ~0.8-1.2TB/s 級（ベンダ公称のスペック値、世代・ビン依存）に達する。
- **GPU のメモリモデル**: CPU (x86 の TSO) より**弱いコンシステンシ**を採り、既定では順序保証を最小限にして帯域を優先する。同期には**スコープ (scope)** 付きのアトミック／フェンスを使う: `cta`（同一スレッドブロック内）、`gpu`（同一デバイス内）、`sys`（ホスト・他デバイス含む全システム）。スコープを狭く指定するほど同期が安く済む——「全員に見せる必要がないなら、近所にだけ見せる」という帯域節約の思想がメモリモデルにまで貫かれている（`../cpu-architecture/memory-ordering-atomics.md` の GPU 版に相当）。

### 4. Tensor コアと専用化のスペクトラム (Tensor Cores & the Specialization Spectrum)

**なぜ行列積だけが専用ユニットを得るのか**。N×N 行列積は演算 O(N³) に対しデータ O(N²) であり、**演算強度が N と共に伸びる**。タイル化で再利用を回収すれば、演算器を増やした分だけ速くなる（計算律速に留まり続ける）稀有なカーネルである。深層学習の計算の大半が GEMM（と畳み込みの GEMM 化）に帰着することが分かった時点で、汎用レーンより桁違いに面積効率の良い**行列積専用演算器**を置く判断が成立した。

- **Tensor コア**は小行列タイル（例: 4×4〜16×16 級の断片）の積和 D = A×B + C を1命令系列で実行する。ワープ単位で協調して1タイルを処理する（warp-level matrix operation）。
- **混合精度 (mixed precision) の階段**: 入力を FP16/BF16、蓄積を FP32 で行うのが基本形で、世代とともに FP8、INT8、さらに低精度へと階段が伸びる。精度を半分にするとスループットは概ね倍（公称スペック上の関係）——深層学習が「低精度に耐える」統計的性質を持つことが、この階段を正当化する。どこまで下げられるかはモデル・学習/推論の別に依存し、ML システム側の量子化 (quantization) 設計と表裏一体である。
- **シストリックアレイとの対比**: TPU (Jouppi et al., 2017) は 256×256 の**シストリックアレイ (systolic array)** ——演算器を格子状に並べ、データを脈動的に流し込み、中間結果をレジスタ経由で戻さない——で行列積を実行する。制御・命令フェッチのオーバヘッドをほぼゼロにする極点の設計で、GPU の Tensor コアは「汎用 SIMT 機に行列エンジンを埋め込んだ中間解」に当たる。
- **専用化のスペクトラム**: 汎用 CPU → GPU (SIMT + 行列エンジン) → TPU (行列特化) → 固定機能 NPU/アクセラレータ（推論専用・特定演算のみ）。右へ行くほど電力効率・面積効率は上がり、対応できるワークロードは狭まる。どこに立つかは「対象計算の同質性と寿命」への賭けである。

| | CPU | GPU | TPU 級アクセラレータ |
|---|---|---|---|
| 設計目標 | 単一スレッドのレイテンシ | データ並列スループット | 行列演算のスループット/W |
| 並列モデル | ILP + 数十コア + SIMD | SIMT, 数万スレッド | シストリックアレイ (データフロー) |
| 制御機構 | OoO・分岐予測・投機に厚く | 最小限 (in-order, ワープ切替) | ほぼなし (決め打ちのデータフロー) |
| メモリ系 | 大キャッシュ + DDR | 中 L2 + HBM (帯域全振り) | 大型オンチップ SRAM + HBM |
| 演算:帯域バランス | 低演算強度でも粘る | 高帯域で広範囲をカバー | 高演算強度 (GEMM) に最適化 |
| 柔軟性 | 任意コード | データ並列カーネル全般 | 行列・テンソル演算にほぼ限定 |

### 5. ホスト-デバイス間インターフェイス (Host-Device Interface)

- **帯域の断崖**: デバイス内 HBM が数 TB/s に対し、ホストとの PCIe は x16 で数十〜百数十 GB/s（Gen4〜Gen6、世代依存; `../hw-sw-interface/bus-interconnect.md` の世代表参照）。**桁で1〜2つの落差**があり、GPU 計算の設計はこの断崖を渡る回数を最小化する問題だと言ってよい。**NVLink** は GPU 間（および対応 CPU との間）を専用リンクで結び、世代依存だが PCIe 比で桁ひとつ上の双方向帯域（数百 GB/s〜TB/s 級、公称値）を提供する。マルチ GPU 学習の all-reduce がこの上で動く。
- **ユニファイドメモリ (unified memory) とページマイグレーション**: ホストとデバイスで単一のアドレス空間を見せ、アクセスされたページをページフォルト契機でオンデマンド移送する。明示的 `memcpy` の管理から解放される一方、フォルト＋移送のコストは隠れているだけで消えておらず、アクセスパターンが悪いと明示転送より遅くなる。プリフェッチヒントや常駐化指示で「実質明示管理」に戻すのが実務の常である。
- **データ移動が支配する**: カーネル起動のレイテンシ（マイクロ秒級）と転送コストがあるため、小さい仕事を GPU に投げると転送と起動で元が取れない。「データを GPU に置いたままパイプラインを全部 GPU で回す」「転送と計算を非同期ストリームで重ねる」が定石であり、これは `../hw-sw-interface/bus-interconnect.md` の帯域遅延積の議論の応用形である。

### 6. Roofline モデル: どこで頭を打つか (Roofline Model)

**Roofline モデル** (Williams et al., 2009) は、カーネルの到達可能性能を2本の天井で表す:

```
  到達可能 FLOP/s = min( ピーク演算性能,  メモリ帯域 × 演算強度 )

  性能 ▲            ピーク演算性能 (演算の天井)
       │        ┌──────────────────────
       │      ／ ↑
       │    ／   大きな GEMM (高演算強度) → 計算律速
       │  ／
       │／← 帯域の斜線 (帯域 × FLOP/byte)
       │ ↑
       │ 推論デコード・帯域系カーネル (低演算強度) → メモリ律速
       └─────────────────────────────▶ 演算強度 (FLOP/byte)
```

- **演算強度 (arithmetic intensity)** = 演算量 / メモリ転送量 (FLOP/byte)。これが「機械のバランス点」（ピーク演算 ÷ 帯域）より高ければ計算律速、低ければメモリ律速で、後者ではいくら演算器を足しても速くならない。
- **大きな密行列積**は演算強度が高く計算律速——Tensor コアが効く領域。対して **LLM の自己回帰デコード**のように「巨大な重みを毎トークン読み直すが、演算はその割に少ない」処理は演算強度が低く、**メモリ帯域律速**になる。同じ GPU の同じモデルでも、学習/プリフィルは演算の天井、デコードは帯域の斜線に張り付く。この区別が、バッチング・量子化・KV キャッシュ管理といった ML システム側の最適化（software 側 ML システム分析で扱う）の出発点になる。

## セキュリティ考察 (Security Considerations)

GPU は「多数のテナントで共有される高価な資源」になったことで、CPU が歩んだ隔離とサイドチャネルの問題を、より未成熟な形で再演している。

- **競合ベースのサイドチャネル (contention-based side channels)**: 同一 GPU を共有するコンテキスト間で、L2・メモリ帯域・演算ユニットの競合が実行時間の変動として観測できる。共有キャッシュ上の Prime+Probe 系の観測や、性能カウンタ・タイマを使った推定により、同居カーネルの挙動（例: ニューラルネットの層構成の推定）を狙う研究が報告されている。原理は CPU のキャッシュサイドチャネル (`../cpu-architecture/cache-coherence.md` のセキュリティ考察) と同根で、「共有資源の状態が時間に漏れる」ことに尽きる。
- **マルチテナント隔離**: 時分割 (time-slicing) の共有は文脈切替ごとの状態消去が保証されなければ残留データ (memory remanence) が漏れうる。空間分割では **MIG (Multi-Instance GPU)** が SM・L2 スライス・メモリを物理的に分割し、**SR-IOV / vGPU** がハイパーバイザ経由で仮想機能を割り当てる。分割の粒度と強度（性能隔離まで保証するか、機能隔離のみか）は方式・世代で異なり、クラウドのテナント境界としてどこまで信頼するかは構成に依存する。
- **DMA 攻撃面と IOMMU**: GPU は強力なバスマスタであり、悪意ある／侵害されたデバイスやドライバは DMA で任意物理メモリに触れうる。**IOMMU** によるアドレス制限と ACS による P2P 制御が防御の要である点は、`../hw-sw-interface/bus-interconnect.md` の一般論がそのまま当てはまる。GPU 固有の追加面として、巨大で特権的なドライバ／ランタイムスタック自体が攻撃面になる。
- **コンフィデンシャルコンピューティング (confidential computing) の拡張**: H100 世代以降の CC モードに代表される「TEE をアクセラレータへ拡張する」動きでは、GPU メモリの暗号化・ホスト-GPU 間リンクの暗号化 (bounce buffer 経由)・デバイス証明 (attestation) を組み合わせ、**ホスト（ハイパーバイザ含む）を信頼せずに** GPU 計算を行うことを狙う。CPU 側 TEE と同様、演算内容のタイミング・電力側チャネルまでは既定では守られない点、および暗号化転送のスループットコストがかかる点は留意が要る。

教訓: GPU の設計原理「資源を大量のスレッド（そしてテナント）で共有し尽くす」は、性能面の美徳であると同時に、隔離の観点では攻撃面の列挙そのものである。共有の粒度（時分割 / MIG / 専有）と信頼境界（ドライバ・ハイパーバイザ・デバイス本体）を明示することが、GPU を含むシステムの脅威分析の出発点になる。

## 結論 (Conclusions)

- GPU は CPU と同じメモリウォールに対する**逆符号の解**である。レイテンシを避ける（キャッシュ・OoO・投機）のではなく、超多スレッドで隠す。この単一の判断から、SIMT・巨大レジスタファイル・ゼロコストワープ切替・帯域全振りの HBM・弱いメモリモデルまで、本ドキュメントの機構のほぼすべてが導かれる。
- SIMT は SIMD ハードウェアの上にスレッドプログラミングの抽象を被せたものであり、その代金は分岐発散とコアレッシング破れで払う。性能分析の第一歩は「ワープ単位で世界を見る」こと——分岐はワープ内で揃っているか、32スレッドのアクセスは併合されるか、占有率はレイテンシを隠すのに足りるか。
- 性能判定の共通言語は Roofline と演算強度である。GEMM は計算律速で Tensor コアが効き、推論デコードのような低演算強度の処理は帯域律速で HBM が効く。そして最悪の敵はしばしばデバイスの外（PCIe の断崖）にいる。
- 専用化は GPU → TPU → 固定機能のスペクトラムであり、GPU は「データ並列全般への汎用性」と「行列演算の専用効率」を1つのダイに同居させた中間解である。どの点を選ぶかは、対象計算の同質性と寿命への賭けである。
- ここまでがハードウェア側の土台であり、バッチング・量子化・並列化戦略といった上物は software 側の ML システム分析が引き継ぐ。
