# 機能安全 (Functional Safety, ISO 26262)

## 概要 (Overview)

自動車の電子制御は人命に直結する。ブレーキ、ステアリング、エアバッグ、加速制御——これらを担う E/E システム (Electrical/Electronic system) の**故障 (failure)** が、そのまま事故になりうる。**機能安全 (functional safety)** とは、システムが故障しても許容できないリスクを生じさせない性質であり、自動車分野ではその国際標準 **ISO 26262** が設計・開発・検証の全工程に要求を課す。

本ドキュメントは、ISO 26262 の中核概念（ハザード分析、ASIL、安全ライフサイクル、ハード/ソフトの安全機構）を整理し、`in-vehicle-networks.md`（車載ネットワーク）や組込みソフトの設計判断が「なぜ安全要求から逆算されるのか」を明らかにする。安全 (safety) とサイバーセキュリティ (security, ISO 21434) の関係も扱う。

## 方法論 (Methodology)

- 「ハザードの特定 → リスクの定量化 (ASIL) → 安全目標 → 安全要求 → 実装と検証」という安全ライフサイクルの流れで整理する。
- ASIL の決定要因（S・E・C）を分解し、要求の厳しさがどう決まるかを示す。
- 故障への技術的対処（冗長化、フェイルセーフ、診断）を、ハード/ソフト両面で対応づける。
- random failure（偶発故障）と systematic failure（系統故障）の区別を軸に、対策が異なることを示す。

## 発見事項 (Findings)

1. **安全は「故障しないこと」ではなく「故障しても危険にしないこと」。** 部品は必ず壊れる前提で、検出・縮退・安全状態への移行を設計する。
2. **要求の厳しさは ASIL で段階化される。** すべてを最高水準で作るのは非現実的なため、リスクに応じて開発の厳格さを配分する。
3. **2種類の故障に別々の対策が要る。** 偶発故障 (random HW failure) はハードの確率的故障 → 冗長・診断で対処。系統故障 (systematic failure) は設計/実装のバグ → プロセス（レビュー・検証・トレーサビリティ）で防ぐ。
4. **安全はプロセス全体に埋め込まれる。** 後付けでなく、要求→設計→実装→検証→運用の全段で V字プロセスとして担保される。
5. **安全とセキュリティは不可分になった。** ネットワーク化（`in-vehicle-networks.md`）でサイバー攻撃が安全を脅かすため、ISO 26262 と ISO 21434 の協調が必須。

## アーキテクチャ (Architecture)

### 安全ライフサイクルと V字プロセス

ISO 26262 は開発を V字モデルで規定する。左で要求を分解し、右で対応する検証を行う。

```
  概念フェーズ                                         検証フェーズ
   ┌─ ハザード分析(HARA) ──── ASIL 決定 ─┐      ┌── 妥当性確認(車両) ─┐
   │   安全目標 (Safety Goal)            │      │   安全目標の達成確認  │
   │     ▼                              │      │        ▲             │
   │   機能安全要求 (FSR)        ────────┼──────┼── システム統合テスト │
   │     ▼                              │      │        ▲             │
   │   技術安全要求 (TSR)                │      │   HW/SW 統合テスト    │
   │     ▼                              │      │        ▲             │
   │   HW/SW 設計 ──────────────────────┘      └── 単体テスト ────────┘
   │     ▼                                              ▲
   └──── 実装 ──────────────────────────────────────────┘
```

各左辺の成果物に、対応する右辺の検証が紐づく（トレーサビリティ, traceability）。

### ハザード分析とリスク評価 (HARA)

運用状況ごとに危険事象を洗い出し、3軸でリスクを評価して **ASIL** を決める。

| 軸 | 意味 | 段階 |
|---|---|---|
| **S (Severity, 深刻度)** | 被害の重さ | S0–S3（無傷〜致命） |
| **E (Exposure, 暴露確率)** | その状況の起こりやすさ | E0–E4（稀〜高頻度） |
| **C (Controllability, 制御可能性)** | 運転者が回避できるか | C0–C3（容易〜不能） |

S・E・C の組み合わせから **ASIL (Automotive Safety Integrity Level)** が決まる:

```
  QM  <  ASIL A  <  ASIL B  <  ASIL C  <  ASIL D
 (品質管理のみ)                        (最も厳格)
```

- **ASIL D**: 最高水準。例——電動パワーステアリング、ブレーキ、エアバッグ展開。
- **ASIL A/B**: 比較的影響の小さい機能。
- **QM (Quality Management)**: 安全要求なし、通常の品質管理で足りる。例——インフォテインメントの一部。

要点: **ASIL が高いほど、要求される手法・冗長・検証の厳格さが上がる**。リスクに応じて開発リソースを配分する仕組み。

### ASIL 分解 (ASIL Decomposition)

高 ASIL の要求を、独立した複数の要素に分割して各々の ASIL を下げる手法。例: ASIL D を、十分に独立した2系統の ASIL B(D) に分解。**独立性 (independence) と冗長 (redundancy)** が前提で、共通原因故障 (common cause failure) があると成立しない。

## 技術詳細 (Technical Details)

### 偶発故障 (Random Failure) への対策 — ハードウェア

確率的に起きる物理故障。指標と機構:

- **指標**: FIT (Failure In Time, 10⁹時間あたり故障数)、SPFM (単一点故障メトリック)、LFM (潜在故障メトリック)、PMHF (確率的ハードウェアメトリック)。ASIL D は最も厳しい数値目標を要求。
- **冗長化 (redundancy)**: 二重化・多数決 (TMR, Triple Modular Redundancy)、ロックステップコア (lockstep core, 2コアが同じ計算をし不一致を検出)。
- **診断 (diagnostics)**: ウォッチドッグ (watchdog timer)、ECC メモリ、CRC、BIST (Built-In Self Test)、センサの妥当性チェック。診断網羅率 (diagnostic coverage) が SPFM/LFM を左右する。
- **フェイルセーフ / フェイルオペレーショナル**:
  - フェイルセーフ (fail-safe): 故障時に安全状態へ移行（例: 出力遮断）。
  - フェイルオペレーショナル (fail-operational): 故障しても機能継続（自動運転で必須。冗長系で実現）。

### 系統故障 (Systematic Failure) への対策 — プロセス/ソフトウェア

設計・実装のバグは確率では語れない（同じ入力で必ず再現）。対策はプロセス:

- **コーディング規約**: MISRA C/C++（未定義動作・危険構文の排除）。`../cpu-architecture/memory-ordering-atomics.md` のデータ競合や `../hw-sw-interface/abi-syscalls.md` のメモリ安全が、ここで規約として強制される。
- **検証手法**: 要求トレーサビリティ、レビュー、静的解析、単体/統合テスト、構造網羅率 (MC/DC など ASIL に応じた基準)、フォーマル検証。
- **フリーダム・フロム・インターフェアレンス (FFI, Freedom From Interference)**: 異 ASIL の機能が同一 ECU/SoC に同居するとき、低 ASIL の不具合が高 ASIL を侵さないよう、メモリ保護 (`virtual-memory-mmu.md` の MMU/MPU)・時間分割 (time partitioning)・通信分離で隔離する。混載 (mixed criticality) の要。
- **ツール認定 (tool qualification)**: コンパイラ等のツール自体の信頼性も評価対象。

### 関連標準

- **ISO 26262**: 機能安全（E/E システムの故障に起因する危険）。
- **ISO 21448 (SOTIF, Safety Of The Intended Functionality)**: 故障ではなく**仕様の不足や性能限界**による危険（例: センサが想定外シーンを誤認）。ADAS/自動運転で重要。
- **ISO/SAE 21434**: サイバーセキュリティ（後述）。
- **ASPICE**: 開発プロセスの成熟度評価。

## セキュリティ考察 (Security Considerations)

- **セキュリティは安全の前提条件になった**: `in-vehicle-networks.md` の通り CAN は無認証で、攻撃者がブレーキ等へ偽指令を注入しうる。サイバー攻撃が安全機構を突破すれば、機能安全の前提が崩れる。
- **ISO 26262 × ISO 21434 の協調**: 安全分析（HARA）とセキュリティ分析（TARA, Threat Analysis and Risk Assessment）を相互参照し、攻撃が安全目標を脅かす経路を塞ぐ。安全機構自体が攻撃対象になりうる点に注意。
- **セキュアな安全機構**: 診断・冗長・フェイルセーフのトリガが改竄されれば誤った縮退を誘発しうる。安全関連の通信に SecOC（メッセージ認証）、ECU に HSM・セキュアブートを併用する。
- **規制**: UNECE WP.29 (R155/R156) がサイバーセキュリティ管理システム (CSMS) とソフト更新を型式認証の要件とし、安全とセキュリティの両立を法的に義務化。

## 結論 (Conclusions)

- 機能安全の本質は「故障を前提に、危険な結果を防ぐ」こと。検出・縮退・安全状態への移行を設計に組み込む。
- ISO 26262 はリスクを ASIL で段階化し、QM〜ASIL D に応じて開発の厳格さ・冗長・検証を配分する。すべてを最高水準にはしない合理的枠組み。
- 偶発故障（確率的ハード故障 → 冗長・診断）と系統故障（設計バグ → プロセス・規約・隔離）は別物で、対策も別。FFI による混載分離は CPU/メモリ保護の知見と直結する。
- ネットワーク化により安全とセキュリティは不可分となり、ISO 26262 と ISO 21434、WP.29 規制の協調が現代車載開発の必須要件である。
