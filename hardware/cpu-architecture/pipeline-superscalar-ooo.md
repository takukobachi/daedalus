# パイプライン・スーパースカラ・アウトオブオーダ実行 (Pipeline, Superscalar & Out-of-Order Execution)

## 概要 (Overview)

CPU は命令を1つずつ順番に実行しているように見えるが、実際の現代コアは1サイクルに複数の命令を発行し、プログラム順序とは異なる順で演算し、後から辻褄を合わせている。この**動的実行 (dynamic execution)** 機構こそが、同じクロック周波数でも世代ごとに性能を伸ばしてきた中心であり、ソフトウェアの実効性能を左右する。

本ドキュメントは、パイプライン (pipeline)・スーパースカラ (superscalar)・アウトオブオーダ実行 (out-of-order execution, OoO) の3層を整理し、命令レベル並列性 (ILP) がどこまで引き出せるか、命令の並びがなぜ IPC（instructions per cycle）に効くか、コンパイラやプログラマが何を意識すべきかを、ハードウェアの観点から明らかにする。分岐予測と投機実行 (speculative execution) は別ドキュメント `branch-prediction-speculation.md` で深掘りするため、ここでは投機の入口として軽く触れるに留める。

## 方法論 (Methodology)

- 命令の処理を**段 (stage)** に分解し、古典5段パイプラインを基準として、そこに「幅 (width)」（スーパースカラ）と「順序の自由度」（OoO）を順に足していく構成で説明する。
- 各機構が解こうとする問題（依存・ハザード・遅延の隠蔽）と、それが生む新たな制約（リソース、リタイア順序、誤投機の取り消し）を対応づける。
- 性能は IPC と、その上限である ILP の観点から評価する。理論上限ではなく、実プログラムで何が ILP を頭打ちにするかに焦点を当てる。
- 数値は一般的な高性能 x86-64／ARM 大型コア世代の代表値であり、世代・実装で大きく変動する。絶対値ではなく**桁感 (order of magnitude)** を理解の基準とする。

## 発見事項 (Findings)

1. **パイプラインはスループットを上げるが、レイテンシは下げない。** 5段に分ければ理想的には1サイクルに1命令完了するが、1命令が完了するまでの時間（段数×サイクル）はむしろ伸びる。深いパイプライン (deep pipeline) ほど周波数は上げやすいが、ハザードや誤投機時の損失（**パイプラインフラッシュ / pipeline flush**）も大きくなる。
2. **性能を削るのはハザード (hazard) である。** 構造・データ・制御の3種があり、フォワーディング (forwarding) で多くは救えるが、ロード遅延や分岐ミスは**ストール (stall) / バブル (bubble)** として残る。理想 IPC からの乖離はほぼハザードで説明できる。
3. **スーパースカラは「幅」を、OoO は「並べ替えの自由」を与える。** 幅だけ広げても依存で詰まるため、依存していない命令を前に出して空いた発行枠を埋める OoO が不可欠。両者は補完関係にある。
4. **OoO の本質はレジスタリネーミング (register renaming) による偽の依存の除去である。** WAR・WAW という**名前依存 (name dependency)** を物理レジスタの付け替えで消し、残った真の依存 (RAW) だけで実行順を決める。これが ILP を引き出す土台。
5. **ILP には実用上の天井がある。** 真のデータ依存、分岐予測精度、メモリ遅延、リソース（ROB／予約ステーション／物理レジスタ）の有限性が重なり、多くの実コードでは平均 IPC は1桁前半に留まる。残った遊休スロットを別スレッドで埋めるのが **SMT（ハイパースレッディング）** である。

## アーキテクチャ (Architecture)

### 古典5段パイプライン (Classic 5-Stage Pipeline)

教科書的な RISC パイプラインは命令処理を5段に分ける。各段は1サイクルで、理想時は5命令が同時に「流れて」いる。

```
   時間 (cycle) →
            1     2     3     4     5     6     7     8
  I1:      IF    ID    EX    MEM   WB
  I2:            IF    ID    EX    MEM   WB
  I3:                  IF    ID    EX    MEM   WB
  I4:                        IF    ID    EX    MEM   WB
  I5:                              IF    ID    EX    MEM   WB

  IF  = Instruction Fetch   命令フェッチ
  ID  = Instruction Decode  デコード／レジスタ読み出し
  EX  = Execute             ALU 演算／アドレス計算
  MEM = Memory Access       ロード／ストア
  WB  = Write Back          結果をレジスタへ書き戻し
```

定常状態では毎サイクル1命令が WB に達するため、理想スループットは 1 IPC。だが「5段に分けた」だけでレイテンシ（1命令あたり5サイクル）は縮まっていない点に注意。パイプラインは**スループット最適化**であってレイテンシ最適化ではない。

### ハザード (Hazards)

パイプラインの理想を崩す3種の競合:

- **構造ハザード (structural hazard)**: ハードウェア資源の取り合い。例: 単一メモリポートに IF と MEM が同時アクセス。資源の複製（命令／データキャッシュ分離など）で緩和。
- **データハザード (data hazard)**: ある命令の結果を次が使うのに、まだ書き戻されていない。
  - **RAW (Read After Write)**: 真の依存 (true dependency)。フォワーディングで多くは救えるが、ロード結果を直後で使うと**ロード・ユース遅延 (load-use latency)** が残る。
  - **WAR / WAW**: 名前依存 (name dependency)。インオーダでは問題にならないが、OoO で順序を入れ替えると顕在化する。リネーミングで除去。
- **制御ハザード (control hazard)**: 分岐の行き先が EX まで確定せず、その間どの命令をフェッチすべきか分からない。分岐予測 (branch prediction) で投機的に進め、外れたらフラッシュする（詳細は `branch-prediction-speculation.md`）。

### フォワーディングとストール (Forwarding & Stall)

```
  フォワーディング (forwarding / bypass): EX の結果を WB を待たず次段へ直送
  I1: ADD r1, r2, r3   IF ID EX─┐MEM WB
  I2: SUB r4, r1, r5      IF ID EX  ...     ← r1 を EX 出力から直接受け取り、ストール回避
                                 ▲ bypass

  ロード・ユース・ストール (load-use stall): ロード結果は MEM 後にしか出ない
  I1: LD  r1, 0(r2)    IF ID EX MEM─┐WB
  I2: ADD r3, r1, r4      IF ID ●  EX ...   ← 1サイクルのバブル (●) が避けられない
                                 stall
```

フォワーディングは「結果が計算され次第、書き戻しを待たずに横流しする」配線。だがロードのようにデータが後段でしか得られない場合、1つ以上の**バブル (bubble)** が必然的に入る。コンパイラの命令スケジューリング (instruction scheduling) は、この隙間に独立命令を詰めて埋めることを狙う。

### スーパースカラ (Superscalar)

1サイクルに複数命令を発行 (issue) する。フロントエンドを「幅 (width)」分だけ広げ、複数の実行ユニット（ALU、ロード／ストア、分岐、FP/SIMD）へ振り分ける。

```
   1サイクルあたり最大4命令を発行する4-wide スーパースカラの例
              ┌──────────────── Front End ────────────────┐
   Fetch ──▶ │  4命令/cycle フェッチ → デコード → リネーム │
              └───────────────────┬───────────────────────┘
                                  ▼
                       ┌── 発行ポート (issue ports) ──┐
                       │ Port0  Port1  Port2  Port3 …  │
                       ▼       ▼      ▼      ▼
                     [ALU]   [ALU]  [LD]   [ST]  [FP/SIMD] [BR]
                          実行ユニット (execution units, 機能ユニット)
```

ただし幅を広げても、命令同士が依存していれば同時に出せない。連続する命令が直前の結果に依存する直線的コードでは、4-wide でも実効 IPC は1に張り付く。幅を活かすには「同時に実行可能な独立命令」が十分にプログラム中に存在する必要がある＝ILP が要る。

### アウトオブオーダ実行 (Out-of-Order Execution)

依存で詰まった命令を待たせたまま、後続の独立命令を先に実行して発行枠を埋める。歴史的な基盤が **Tomasulo のアルゴリズム (Tomasulo's algorithm)**。主要部品は次の通り。

```
            ┌──── In-Order Front End ────┐
   Fetch ─▶ │ Decode → Rename → Allocate │   ← ここまでプログラム順
            └──────────────┬─────────────┘
                           ▼
        ┌──── 予約ステーション / 発行キュー ────┐
        │  Reservation Stations (RS)            │   ← オペランドが揃った
        │  オペランド待ち命令をバッファ          │      命令から順不同で発行
        └──────────────┬──────────────────────┘
                       ▼  (Out-of-Order Execute)
        [ALU] [ALU] [LD/ST] [FP/SIMD] … 実行ユニット
                       │
                       ▼ 結果を Common Data Bus 経由で配布／ROB に記録
        ┌──── リオーダバッファ (Reorder Buffer, ROB) ────┐
        │  完了した結果を保持し、プログラム順に Retire    │   ← ここで再び順序通り
        └──────────────────────────────────────────────┘
                       ▼  (In-Order Retire / Commit)
                  アーキテクチャ状態 (レジスタ／メモリ) を確定
```

- **レジスタリネーミング (register renaming)**: アーキテクチャレジスタ（命令から見える名前、例: `rax`）を、より多数の**物理レジスタ (physical register)** に動的に対応づける。これにより WAR・WAW の名前依存が消え、残るのは真の RAW 依存だけになる。マッピングは Register Alias Table (RAT) が管理する。
- **予約ステーション (reservation station, RS) / 発行キュー**: 実行待ち命令を保持し、必要なオペランドが揃ったものから実行ユニットへ送る。命令はオペランドの準備順に発行されるため、プログラム順とは無関係になる。
- **リオーダバッファ (reorder buffer, ROB)**: 命令を発行時にプログラム順で登録し、実行結果を一時保持する。先頭から順に**リタイア (retire) / コミット (commit)** し、その時点で初めてアーキテクチャ状態（プログラムから見えるレジスタ・メモリ）へ反映する。
- **インオーダ・リタイア (in-order retire)**: 実行は順不同でも、結果の確定は必ずプログラム順。これにより、例外・割り込み・分岐ミス時に「どこまでが確定済みか」を正確に巻き戻せる（**精密例外 / precise exception**）。投機的に実行された後続結果は ROB 上にあるだけで未確定なので、捨てれば「なかったこと」にできる。

要点は **「順不同で実行し、順序通りに確定する (execute out-of-order, retire in-order)」**。この分離が、ILP を引き出しつつプログラムの意味を保つ鍵である。

## 技術詳細 (Technical Details)

### 1. 名前依存とリネーミングの効果

```
; 例示 (illustrative)。リポジトリ内の実コードではない。アセンブリ風の擬似表記。
; リネーミング前: rax を3回使い回す → WAW/WAR で直列化して見える
    add  rax, rbx, rcx     ; (1) rax = rbx + rcx
    mov  [mem1], rax       ; (2) rax を格納
    add  rax, rdx, rsi     ; (3) rax = rdx + rsi   ← (1)と同じ名前だが計算は独立

; (1)と(3)は本来独立。論理レジスタ名 rax を共有しているだけ（WAW）。
; リネーミング後: 物理レジスタ p10, p11 を割り当て
    add  p10, rbx, rcx     ; (1)' 
    mov  [mem1], p10       ; (2)'
    add  p11, rdx, rsi     ; (3)'  ← p11 は p10 と無関係 → (1)'と(3)'を並列実行可能
```

名前依存はプログラマの「レジスタの使い回し」やコンパイラのレジスタ割り当てに由来する見かけ上の依存にすぎない。リネーミングはこれを物理的に分離し、真の依存 (RAW) だけを残す。**ILP のかなりの部分はこの除去で得られる。**

### 2. 命令並びが IPC に与える影響

```c
// 例示コード (illustrative)。
// 悪い例: 各反復が直前の sum に依存 → 長い依存鎖 (dependency chain) で直列化
double sum = 0.0;
for (int i = 0; i < N; i++)
    sum += a[i];          // sum ← sum + a[i] の RAW 依存が連鎖

// 良い例: 部分和でアキュムレータを分割 → 独立な依存鎖が4本 → OoO/SIMD が並列化
double s0=0, s1=0, s2=0, s3=0;
for (int i = 0; i+3 < N; i += 4) {
    s0 += a[i];  s1 += a[i+1];  s2 += a[i+2];  s3 += a[i+3];
}
double sum = s0 + s1 + s2 + s3;
```

浮動小数点加算の実行レイテンシ（例: 数サイクル）に対し、依存鎖が1本だと「次の加算は前の結果を待つ」ため、スループットが実行ユニットのレイテンシに律速される。アキュムレータを分けて独立鎖を増やすと、OoO エンジンが複数を同時進行させ、レイテンシを隠せる。**同じ計算量でも、依存構造を平たくするだけで IPC は数倍変わりうる。** これがコンパイラの命令スケジューリングやループアンロール (loop unrolling) の狙いである。

注意: 浮動小数点では分割により加算順序が変わり、丸めの結果がわずかに変化する。コンパイラが自動でこの変換を行うには `-ffast-math` 等の許可が要る（結合則を仮定してよいという指示）。**性能最適化が数値再現性とトレードオフになる**典型例。

### 3. ハザード／ストールの主な発生源と桁感

| 要因 | 典型的な損失（桁感） | 性質 |
|---|---|---|
| ロード・ユース遅延 | ~1–数サイクルのバブル | L1 ヒット前提。整数 ALU 連鎖に挟まると効く |
| 分岐予測ミス | ~10–20 サイクル（パイプライン全フラッシュ） | 深いパイプほど高コスト。詳細は別ドキュメント |
| L1 ミス → L2/L3 | ~10–40 サイクル | OoO がその間に独立命令で隠せる範囲 |
| 主記憶アクセス（LLC ミス） | ~200–300 サイクル | ROB 容量を超えると隠しきれず**ストール** |

OoO は「待っている間に他の独立命令を進める」ことで遅延を隠す。だが隠せる量は ROB／物理レジスタ／予約ステーションの容量で頭打ちになる。主記憶遅延（数百サイクル）は、ROB 数百エントリでも埋めきれず、結局フロントエンドが止まる。**メモリ遅延が ILP の最大の敵**であり、その背景は `cache-memory-hierarchy.md` に詳しい。

### 4. メモリ命令の順序とメモリ曖昧性 (Memory Disambiguation)

ロード／ストアの並べ替えは特に難しい。アドレスが実行時まで分からないため、「後続ロードが先行ストアと同じ番地か」を確定できない。コアは**ストアバッファ (store buffer)** とロード／ストアキューで管理し、安全なら後続ロードを先行させる（投機的メモリ順序）。誤れば（先行ストアと同番地と判明）ロードをやり直す。この機構は単一スレッドでは透過的だが、**マルチスレッドではメモリ順序 (memory ordering) として観測可能になる**。詳細は `memory-ordering-atomics.md`。

### 5. SMT / ハイパースレッディング (Simultaneous Multithreading)

ILP が尽きて遊休になった発行スロットを、**別スレッドの命令**で埋める手法。1つの物理コアが複数の論理スレッド（例: 2 way の Hyper-Threading）を保持し、各サイクルでどちらの命令でも空きユニットへ流せる。

- **利点**: ある1スレッドだけでは ILP・メモリ遅延で空く実行資源を、別スレッドが活用しスループットを底上げ（典型で +20〜30% 程度、ワークロード依存）。
- **限界**: 物理資源（実行ユニット・キャッシュ・ROB・帯域）は共有。両スレッドが同種資源を奪い合うと、かえって遅くなることもある（キャッシュ容量の取り合い等）。レイテンシ重視のシングルスレッド性能は上がらない。
- **設計上の含意**: SMT は ILP の限界を「スレッドレベル並列性 (TLP) で補う」発想。ILP（命令内並列）と TLP（スレッド間並列）は相補的な性能源である。

### 6. 投機実行の入口 (Speculation — pointer to深掘り)

OoO エンジンは分岐の結果を待たず、予測した経路を**投機的に**実行して ROB に積む。予測が当たればそのまま確定し、外れれば該当分岐以降の ROB エントリを破棄して正しい経路を再フェッチする（フラッシュ）。投機は ILP を引き出す要だが、**外れたときの命令も一時的には実行されてしまう**点が、マイクロアーキテクチャ状態（キャッシュ等）に痕跡を残し、後述のセキュリティ問題につながる。分岐予測器の構造と投機の深掘りは `branch-prediction-speculation.md` に委ねる。

## セキュリティ考察 (Security Considerations)

動的実行は性能機構であると同時に、近年の代表的なマイクロアーキテクチャ攻撃の土台でもある。本質は「アーキテクチャ上は取り消される投機実行が、マイクロアーキテクチャ状態には痕跡を残す」ことにある。

- **Spectre 系**: 分岐予測を攻撃者が誘導し、本来到達しないコード（境界チェックの先など）を投機実行させる。投機中に秘密値に依存したメモリアクセスを起こさせ、その痕跡をキャッシュのタイミング差から読み出す（`cache-memory-hierarchy.md` の Flush+Reload／Prime+Probe を参照）。分岐予測の悪用が中心のため、攻撃面の詳細は `branch-prediction-speculation.md` で扱う。
- **Meltdown 系**: 例外を起こすアクセスでも、例外が**リタイア時に**確定するまでの間、後続命令が投機的に秘密値を使えてしまう設計上の隙を突く。インオーダ・リタイアの「確定は遅れる」性質が逆手に取られた形。
- **MDS / ポートコンテンション系**: ストアバッファ・ロードバッファ・ラインフィルバッファ等、OoO/SMT が共有する内部バッファや実行ポートの競合から、同居スレッドの情報が漏れる（例: 実行ポートの混雑をタイミングで観測）。SMT は資源共有ゆえに**スレッド間サイドチャネル**を生みやすい。
- **緩和策 (mitigations)**: 投機バリア（`lfence` 等で投機を堰き止める）、間接分岐の制御 (retpoline、IBRS/IBPB)、信頼境界をまたぐ際のバッファクリア、セキュリティ要件の高い環境での **SMT 無効化**、ハードウェア世代での設計修正。いずれも ILP・スループットを犠牲にし、**性能と機密性が直接対立する**。

教訓: ILP を引き出す投機・順不同実行・資源共有は、そのまま情報漏洩経路になりうる。秘密を扱うコードでは、投機による余分な実行を前提に、秘密依存の分岐・メモリアクセスを排した定数時間実装 (constant-time) を選ぶ。

## 結論 (Conclusions)

- パイプラインはスループットを、スーパースカラは発行幅を、OoO は実行順序の自由を与える。3層が積み重なって「1サイクルに複数命令を、順不同で実行する」現代コアになる。
- OoO の核はレジスタリネーミングによる名前依存の除去と、「順不同で実行し順序通りに確定する (execute out-of-order, retire in-order)」分離である。ROB が精密例外と誤投機の巻き戻しを支える。
- 性能の上限は ILP であり、それを縛るのは真のデータ依存・分岐予測精度・メモリ遅延・内部資源の有限性。ソフトウェア側の鉄則は **依存鎖を短くし、独立な作業を増やし、メモリ遅延を避ける** に集約される。残りは SMT がスレッドレベル並列で埋める。
- 命令の並び（依存構造）は計算量が同じでも IPC を桁で変えうる。最適化はコンパイラのスケジューリングに任せつつ、依存を生むコード構造（長い縮約鎖、ポインタ追跡）を避けるのがプログラマの責務。
- 動的実行は強力ゆえに危険でもある。投機と資源共有はサイドチャネルを生み、緩和策は性能と引き換えになる。
