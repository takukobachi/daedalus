# 分岐予測と投機実行 (Branch Prediction & Speculative Execution)

## 概要 (Overview)

現代のCPUは命令を深いパイプライン (pipeline) で並列処理し、1サイクルに複数命令を発行するスーパースカラ (superscalar) 構造を持つ。この機構は「次に実行する命令アドレスが常に分かっている」ことを前提とするが、条件分岐 (conditional branch) はその前提を崩す。分岐の方向と飛び先は、分岐命令自身が**実行完了するまで確定しない**。

この穴を埋めるのが**分岐予測 (branch prediction)** と**投機実行 (speculative execution)** である。CPUは分岐の結果を予測し、確定前に予測経路の命令を先行実行する。予測が当たれば停止なく流れ、外れれば投機分を破棄してやり直す。命令の約5本に1本が分岐である一般的なコードでは、予測精度がそのままスループットを左右する。

本ドキュメントは、分岐予測器の構造と動作原理を整理し、予測ミスの性能コストを定量的な桁感で示し、さらに投機実行が **Spectre** 系のマイクロアーキテクチャ・サイドチャネル (microarchitectural side channel) を生む構造を明らかにする。

## 方法論 (Methodology)

- 制御ハザード (control hazard) がなぜ高コストかを、パイプライン段数とフラッシュ (flush) の観点から定量化する。
- 予測器を「方向予測 (direction)」と「ターゲット予測 (target)」の2軸に分解し、各方式（静的・動的・履歴ベース・ハイブリッド）を精度とコストで比較する。
- 投機実行とロールバック (rollback) の境界を、アーキテクチャ状態 (architectural state) とマイクロアーキテクチャ状態 (microarchitectural state) の差として捉える。
- その差を観測経路とする Spectre 系攻撃を、変種ごとに「汚染 → 投機 → 痕跡 → 観測」の4段で分解する。
- 数値は一般的な x86-64／高性能 Arm 世代の代表値であり、世代・実装で変動する。絶対値ではなく**桁感 (order of magnitude)** を理解の基準とする。

## 発見事項 (Findings)

1. **制御ハザードのコストはパイプライン深さに比例する。** 予測ミス時は投機中の全命令をフラッシュし、正しい経路を先頭から流し直す。深いパイプライン（10〜20段）では1回のミスで**10〜20サイクル超**が失われ、これは数十命令分の発行機会に相当する。
2. **動的予測 (dynamic prediction) は履歴で精度を稼ぐ。** 2ビット飽和カウンタ (2-bit saturating counter) による単純な方式でも実コードで90%前後、gshare やトーナメント (tournament) 予測器では多くのワークロードで**95〜99%超**に達する。残り数%のミスが性能の足を引っ張る。
3. **方向とターゲットは別々に予測される。** 「分岐するか (taken/not-taken)」は方向予測器が、「どこへ飛ぶか」は分岐ターゲットバッファ (BTB) とリターンアドレススタック (RAS) が担う。間接分岐 (indirect branch) はターゲットが多値で予測が難しい。
4. **予測ミスの真のコストは IPC に効く。** 予測精度 p、ミスペナルティ N サイクル、分岐頻度 f のとき、分岐に起因する追加 CPI はおよそ `f·(1−p)·N`。f=0.2, p=0.97, N=15 なら約 0.09 CPI 増——ピーク IPC が高い設計ほど相対的損失が大きい。
5. **投機実行は「なかったことにできない痕跡」を残す。** 投機結果はアーキテクチャ的にはロールバックされるが、キャッシュ・BTB・予測器といったマイクロアーキテクチャ状態には副作用が残る。これが **Spectre** の本質であり、性能機構がそのまま情報漏洩経路になる。

## アーキテクチャ (Architecture)

### 制御ハザードとパイプラインフラッシュ

分岐の解決 (resolution) はパイプライン後段（実行/分岐ユニット）で起きる。予測なしでは、フェッチ段は解決まで停止 (stall) するしかない。

```
  予測ミス時のパイプライン (深さ N 段の概念図)

  cycle →   1    2    3    4    5    6    7    8 ...
  br        IF   ID   EX*  ...                        ← EX* で「ミス」と判明
  spec1          IF   ID   EX   ← フラッシュ対象（破棄）
  spec2               IF   ID   ← フラッシュ対象（破棄）
  spec3                    IF   ← フラッシュ対象（破棄）
  correct                       IF   ID   EX  ...     ← 正しい経路を先頭から
                           └────── ペナルティ ≈ 分岐解決段までの距離 ──────┘
```

ペナルティは概ね「フェッチ段から分岐が解決される段までの距離」に等しい。フロントエンドが深く、命令窓 (instruction window) が広いほど、フラッシュで捨てる仕事は増える。

### 方向予測器の進化（精度 vs コスト）

```
  単純 ──────────────────────────────────────────► 高精度・高コスト

  [1] 静的 (static)            常に taken / コンパイラヒント
  [2] 1ビット                  直近の結果をそのまま予測
  [3] 2ビット飽和カウンタ      1回の例外でブレない（ループ末尾に強い）
  [4] 2レベル (global/local)   履歴レジスタ + パターン表 (PHT)
  [5] gshare                   GHR XOR PC でエイリアス低減
  [6] トーナメント (tournament) 複数予測器を選択器 (chooser) が切替
  [7] TAGE / 神経 (perceptron) 多長履歴・機械学習的（近年の実装）
```

### 2ビット飽和カウンタ

各分岐に2ビットの状態を持たせ、taken/not-taken の偏りを記憶する。1ビット方式が「ループ脱出のたびに2回ミスする」弱点を、ヒステリシス (hysteresis) で解消する。

```
        taken            taken            taken
   ┌──────────►┌──────────►┌──────────►┌────────┐
 ┌─┴─┐       ┌─┴─┐       ┌─┴─┐       ┌─┴─┐      │
 │ 00│       │ 01│       │ 10│       │ 11│◄─────┘taken
 │SNT│       │WNT│       │WT │       │ST │
 └─┬─┘◄──────└─┬─┘◄──────└─┬─┘◄──────└─┬─┘
   │ n-taken   │ n-taken   │ n-taken   │ n-taken
   └───────────┴───────────┴───────────┘
  予測: 上位ビット (0→not-taken / 1→taken)
  SNT=Strongly NT, WNT=Weakly NT, WT=Weakly T, ST=Strongly T
```

### 履歴と gshare

- **グローバル履歴 (global history)**: 直近 k 個の「全分岐」の taken/not-taken を**グローバル履歴レジスタ (GHR)** に詰める。分岐どうしの相関 (correlation) を捉える。
- **ローカル履歴 (local history)**: 分岐**個別**の過去パターンを保持。周期的な振る舞い（例: 3回ごとに taken）に強い。
- **gshare**: `index = GHR XOR PC` でパターン履歴表 (PHT) を引く。GHR と PC を混ぜることでエイリアシング (aliasing) を抑えつつ、相関情報を活かす。

```
   PC      ─────────────┐
                        ▼ (XOR)
   GHR ───►[ k bit ]───►(⊕)───► index ──► ┌───────────┐
                                          │  PHT      │
                                          │ 2-bit ctr │──► 方向予測
                                          │  × 2^k    │
                                          └───────────┘
```

### トーナメント予測器

グローバル予測器とローカル予測器を**両方**走らせ、各分岐ごとに「どちらが当たりやすいか」を学習した**選択器 (chooser / meta-predictor)** が選ぶ。分岐の性質（相関型か周期型か）に応じて最良の予測器を使い分け、単独方式の弱点を補う。

```
        ┌─────────────────┐
  PC ──►│ Local predictor │──┐
        └─────────────────┘  │
        ┌─────────────────┐  ├──►[ MUX ]──► 最終予測
  GHR ─►│ Global predictor│──┘     ▲
        └─────────────────┘        │
        ┌─────────────────┐        │
  PC ──►│ Chooser (meta)  │────────┘ どちらを採用するか
        └─────────────────┘
```

### ターゲット予測: BTB と RAS

方向が taken と予測されても、**飛び先アドレス**が要る。分岐命令をデコードする前にフェッチを止めないため、PC をキーにターゲットを引く。

- **分岐ターゲットバッファ (BTB)**: `PC → 予測ターゲットアドレス` のキャッシュ。フェッチ段で即座に次アドレスを供給する。容量・連想度が精度を左右する。
- **リターンアドレススタック (RAS)**: 関数呼び出し `call` 時に戻りアドレスをプッシュし、`ret` でポップする LIFO 構造。`ret` の飛び先は呼び出し元ごとに変わるため BTB では当てにくいが、RAS なら呼び出し/復帰の対応で高精度に予測できる。深い再帰やスタックの不整合でオーバーフローすると精度が落ちる。
- **間接分岐 (indirect branch)**: 関数ポインタ・仮想関数・`switch` ジャンプテーブルなど、1つの分岐から複数ターゲットへ散る。GHR を併用した**間接分岐用 BTB (indirect target predictor)** で履歴依存のターゲットを学習する。これが後述の Spectre v2 の標的となる。

## 技術詳細 (Technical Details)

### 1. 2ビット飽和カウンタの更新（疑似コード）

```c
// 説明用の例示コード (illustrative)。リポジトリ内の実コードではない。
// 各分岐エントリは 2-bit カウンタ ctr (0..3) を持つ。
uint8_t predict(uint8_t ctr) {
    return ctr >> 1;          // 上位ビット: 1=taken, 0=not-taken
}
void update(uint8_t *ctr, int taken) {
    if (taken) { if (*ctr < 3) (*ctr)++; }   // 飽和加算 (saturating)
    else       { if (*ctr > 0) (*ctr)--; }   // 飽和減算
}
// 弱点: 1つの PHT エントリを複数分岐が共有するとエイリアシングで精度低下。
// gshare は GHR を index に混ぜてこの衝突を緩和する。
```

### 2. gshare のインデックス計算（例示）

```c
// 例示コード (illustrative)
// PHT サイズ 2^k。GHR は直近 k 分岐の方向ビット列。
size_t gshare_index(uint64_t pc, uint64_t ghr, int k) {
    uint64_t mask = (1ull << k) - 1;
    return ((pc >> 2) ^ ghr) & mask;   // 下位2bitは命令アライン分捨てる例
}
// 予測後、分岐解決時に GHR を 1bit シフトして実結果を押し込む:
//   ghr = (ghr << 1) | actual_taken;
```

### 3. 予測ミスペナルティと IPC への影響

予測に起因する追加コストは、ミス率とパイプライン深さの積で効く。

```
  分岐起因の追加 CPI  ≈  f · (1 − p) · N

    f : 全命令に占める分岐の割合      (代表値 ~0.15–0.25)
    p : 分岐予測精度                  (代表値 ~0.95–0.99)
    N : 予測ミスペナルティ (cycles)   (代表値 ~10–20, 深いほど大)
```

例: f=0.2, p=0.97, N=15 → 追加 CPI ≈ 0.2 × 0.03 × 15 ≈ **0.09**。理想 CPI が 0.25（IPC=4）の高性能コアなら、これだけで実効 IPC が **約3.6** に落ちる。精度を 0.97→0.99 に上げるとペナルティはほぼ半減する。**深いパイプライン・広い発行幅ほど、予測ミス1回の損失が大きい。**

### 4. 投機実行とロールバックの境界

アウトオブオーダ実行 (out-of-order) コアでは、命令を投機的に実行し、結果を**リオーダバッファ (ROB)** に保持する。分岐が確定すると:

- **当たり**: 投機結果をリタイア (retire) し、アーキテクチャ状態（レジスタ・メモリ）へコミット。
- **外れ**: 当該分岐以降の ROB エントリと投機レジスタ（物理レジスタの割当）を破棄し、フロントエンドをフラッシュ。

ここで重要なのは、**ロールバックされるのはアーキテクチャ状態だけ**という点である。投機中に発行されたメモリアクセスがキャッシュに残したラインや、更新された BTB／予測器エントリは**巻き戻されない**。この「消し残し」が次節のサイドチャネルの起点になる。

### 5. ソフトウェアから見た指針

- **予測しやすい分岐に整える**: ループの境界条件を単純化し、データ依存で方向が乱れる分岐 (data-dependent branch) を減らす。ソートされたデータに対する条件分岐が未ソートより速い、という現象は予測精度の差で説明できる。
- **分岐を消す**: 条件move (`cmov`)・ビット演算・テーブル化・SIMD のマスク (predication) で分岐自体を排除すると、予測ミスもサイドチャネルも消える。
- **間接分岐を減らす**: ホットパスの仮想関数呼び出しは脱仮想化 (devirtualization) や `switch` の単純化で BTB 圧を下げる。
- **計測**: Linux `perf stat` の `branches`, `branch-misses`、および `perf record -e branch-misses` でミスの局在を特定する。**推測ではなく計測**で律速分岐を突き止める。

## セキュリティ考察 (Security Considerations)

投機実行は「アーキテクチャ的になかったことになる計算」を許す。だがその計算がキャッシュなどのマイクロアーキテクチャ状態に痕跡を残すため、**本来読めない秘密値を、間接的に観測できてしまう**。これが投機実行サイドチャネル攻撃 (transient execution attack) の核心であり、本ドキュメントの肝である。

攻撃は概ね4段で構成される: **(1) 予測器を汚染** → **(2) 秘密に依存した投機実行を誘発** → **(3) 投機が秘密をキャッシュ等に符号化** → **(4) 別経路（キャッシュタイミング）で復号**。観測経路（段4）は `cache-memory-hierarchy.md` の Flush+Reload / Prime+Probe そのものである。

### Spectre v1 (Bounds Check Bypass, CVE-2017-5753)

境界チェックを伴う配列アクセスを標的とする。

```c
// 例示コード (illustrative)。攻撃される側のパターン。
if (x < array1_size) {                 // ① この分岐を「成立」と誤予測させる
    uint8_t v = array1[x];             // ② 境界外の秘密 v を投機的にロード
    uint8_t y = array2[v * 64];        // ③ v に依存したアドレスをキャッシュに載せる
}
```

攻撃者は事前に正当な `x` で `if` を何度も成立させ、**方向予測器を「taken」に訓練**しておく。次に境界外の `x` を渡すと、CPU は境界チェックの解決を待たずに②③を投機実行する。`x` が範囲外でも、投機中は `array1[x]` が秘密メモリを読み、その値 `v` で `array2` の特定ラインがキャッシュに載る。分岐解決後に②③はロールバックされるが、`array2` のキャッシュ痕跡は残る。攻撃者が `array2` を Flush+Reload で走査し、ヒットしたインデックスから `v` を逆算する。

- **緩和策**:
  - **`lfence` 等の投機バリア (speculation barrier)**: 境界チェックの後に挿入し、分岐解決まで後続ロードの投機を止める。
  - **マスキング (index masking)**: `x &= (array1_size - 1)` 等でインデックスを物理的に範囲内へ丸め、投機中も境界外を読ませない。
  - コンパイラ支援 (`__builtin_speculation_safe_value` / MSVC `/Qspectre`)。

### Spectre v2 (Branch Target Injection, CVE-2017-5715)

方向ではなく**間接分岐のターゲット**を汚染する。攻撃者は自分のプロセスから BTB／間接分岐予測器に細工し、被害者の間接分岐 (`jmp [reg]` / `call [reg]`) が**攻撃者の選んだガジェット (gadget) アドレス**へ投機的に飛ぶよう仕向ける。被害者の権限で任意のコード断片を投機実行させ、秘密をキャッシュへ符号化できる。予測器が物理コア内（SMT 兄弟スレッド含む）で共有・部分タグ付けされている構造が、この**予測器の汚染 (predictor poisoning)** を可能にする。

- **緩和策**:
  - **retpoline**: 間接分岐を `call`/`ret` を使った構文へ書き換え、間接予測器に**当てさせない**。RAS を無害な無限ループ（`pause; lfence`）へ誘導し、投機の暴走を封じ込める。BTB 由来の投機ターゲット注入を構造的に回避する古典的ソフトウェア対策。
  - **IBRS (Indirect Branch Restricted Speculation)**: 高特権モードで、低特権に汚染された予測を使わせないハードウェアモード。enhanced IBRS (eIBRS) で常時有効化し性能影響を低減。
  - **IBPB (Indirect Branch Predictor Barrier)**: コンテキストスイッチ等の境界で間接予測器の履歴をフラッシュし、プロセス間の汚染を断つ。
  - **STIBP (Single Thread Indirect Branch Predictors)**: SMT 兄弟スレッド間で間接予測器を共有させない。
  - 近年は RAS を狙う **Retbleed**／分岐履歴を狙う **BHI (Branch History Injection)** など派生が報告され、retpoline 単独では不十分な世代があるため、ハードウェア緩和との併用が前提。

### その他の派生と一般原則

- **Spectre-RSB / ret2spec**: RAS（リターンスタックバッファ）をオーバーフロー／汚染し、`ret` の投機ターゲットを乗っ取る。
- **Meltdown (CVE-2017-5754)** は厳密には例外処理中の投機を突くもので分岐予測非依存だが、痕跡の観測経路（キャッシュ）は共通。ページテーブル分離 (KPTI) で緩和する。
- **一般原則**:
  - **秘密を投機の制御・アドレスに載せない** — 境界マスキングと定数時間実装 (constant-time)。
  - **予測の伝播を断つ** — バリア (`lfence`)、retpoline、IBPB によるドメイン境界の隔離。
  - **共有を減らす** — IBRS/STIBP による特権・スレッド間の予測器分離。
  - いずれも**性能と引き換え**であり、信頼境界 (trust boundary) をまたぐコード（カーネル/サンドボックス/JIT）でのみ重く適用するのが実務上の妥協点である。

教訓: 分岐予測と投機実行は「正しく当てれば速い」性能機構だが、当てる過程で履歴を学習し、外した投機の痕跡を残す。この**学習と痕跡こそが攻撃面**である。機密を扱うコードでは、予測精度を上げる最適化が、そのまま漏洩経路を太らせうることを前提に設計する。

## 結論 (Conclusions)

- 条件分岐はパイプラインの前提（次アドレス既知）を崩す制御ハザードであり、深いパイプラインほどミスのコストが大きい。分岐予測と投機実行はこの穴を埋める必須機構である。
- 予測精度は **2ビット飽和カウンタ → 履歴ベース (gshare) → トーナメント/TAGE** と進化し、実コードで 95〜99% に達する。方向は PHT、ターゲットは BTB／RAS／間接予測器が分担する。
- 予測ミスの損失は `f·(1−p)·N` の桁感で効き、高 IPC 設計ほど相対損失が大きい。ソフトウェア側は分岐を予測しやすく整えるか、`cmov`／SIMD で分岐自体を消す。
- 投機実行はアーキテクチャ状態を巻き戻すが、キャッシュ・予測器のマイクロアーキテクチャ状態は巻き戻さない。この非対称性が Spectre 系サイドチャネルの根である。緩和（バリア、マスキング、retpoline、IBRS/IBPB/STIBP）は性能と引き換えで、信頼境界に絞って適用する。
